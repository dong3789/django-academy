## 1. 환경 구축: npm ↔ uv / venv

| Node.js | Python |
|---|---|
| `nvm` | `uv python install` / pyenv |
| `node_modules/` (프로젝트 로컬) | 가상환경 `.venv/` |
| `package.json` | `pyproject.toml` |
| `package-lock.json` | `uv.lock` |
| `npm install x` | `uv add x` |
| `npx x` | `uvx x` |

Python은 기본적으로 패키지를 **인터프리터 전역 site-packages**에 설치합니다. 그래서 프로젝트마다 격리된 인터프리터 사본(가상환경)이 필요합니다.

```bash
# 표준 방식 (venv + pip)
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install django
which python                     # .venv/bin/python 인지 확인!

# 현대적 방식 (uv: Rust로 작성, pip보다 10~100배 빠름)
curl -LsSf https://astral.sh/uv/install.sh | sh
uv init myproj && cd myproj
uv python pin 3.12
uv add django                    # pyproject.toml + uv.lock 갱신, .venv 자동 생성
uv add --dev pytest ruff mypy
uv run python -c "import django; print(django.get_version())"
```

**왜 activate가 동작하나?** `activate`는 `PATH` 앞에 `.venv/bin`을 끼워 넣을 뿐입니다. 가상환경의 `python`은 원본 인터프리터를 가리키되, `pyvenv.cfg` 덕분에 `sys.prefix`가 `.venv`로 잡혀 패키지 탐색 경로(`sys.path`)가 바뀝니다.

```python
import sys; print(sys.prefix, sys.path)
```

### 진리값과 비교 — 가장 많이 틀리는 곳
| 값 | JS | Python |
|---|---|---|
| `[]` / `{}` | truthy | **falsy** |
| `"0"` | truthy | truthy |
| `0`, `""`, `null/None` | falsy | falsy |

```python
1 == "1"      # False — 암묵적 형변환 없음 (JS는 true)
1 + "1"       # TypeError (JS는 "11") → Python은 "강한 동적 타입"
a = [1]; b = [1]
a == b        # True  (값 비교, __eq__)
a is b        # False (동일 객체인가 = JS의 === 에 대한 객체 비교)
x is None     # None 비교는 항상 is
0.1 + 0.2 == 0.3   # False — 두 언어 모두 IEEE754
```

### 함수
```javascript
const add = (a, b = 1) => a + b;
function f(...args) {}  f({a, b})
```
```python
def add(a, b=1):
    return a + b
square = lambda x: x * x     # 표현식 하나만 가능

def f(*args, **kwargs): ...  # 가변 위치/키워드 인자
def g(a, /, b, *, c): ...    # a: 위치전용, c: 키워드전용
g(1, 2, c=3)
```
⚠️ **기본값 함정**: 기본 인자는 *정의 시점에 한 번* 평가됩니다.
```python
def append(x, acc=[]):   # 버그! 모든 호출이 같은 리스트 공유
    acc.append(x); return acc
append(1); append(2)     # [1, 2]
def append(x, acc=None):
    acc = [] if acc is None else acc
```
(JS는 호출마다 기본값을 다시 평가하므로 이 버그가 없습니다.)

### 스코프
```python
count = 0
def inc():
    global count      # 없으면 UnboundLocalError
    count += 1
def outer():
    n = 0
    def inner():
        nonlocal n    # 클로저 변수 재할당 시 필요 (JS는 불필요)
        n += 1
        return n
    return inner
```
Python은 **함수 단위 스코프**(LEGB: Local→Enclosing→Global→Builtin)이고 블록 스코프가 없습니다. `for` 루프 변수는 루프 후에도 살아있습니다.

### 예외

### 비동기 — 결정적 차이
Node는 런타임 자체가 이벤트 루프 위에서 돌고 I/O가 기본 논블로킹입니다. Python은 **기본이 동기·블로킹**이고, `asyncio`는 opt-in입니다. Django의 대부분 코드(ORM 포함)는 동기 코드이며 동시성은 **여러 워커 프로세스/스레드**(gunicorn)로 확보합니다. 이것이 Week 2(GIL)와 Week 9(배포)의 핵심 복선입니다.

## 3. CS 미니 섹션: 모든 것은 객체 + 시간복잡도

Python에서 변수는 "상자"가 아니라 **객체에 붙은 이름표(참조)**입니다.
```python
a = [1, 2]; b = a; b.append(3); print(a)   # [1, 2, 3]
id(a) == id(b)                              # True
def f(lst): lst = [9]      # 이름 재바인딩 → 호출자에 영향 없음
def g(lst): lst.append(9)  # 객체 변경 → 영향 있음 ("call by object reference")
```
CPython의 `list`는 **동적 배열**(포인터 배열, 용량 초과 시 약 1.125배 재할당) → `append` 분할상환 O(1), `insert(0, x)`/`pop(0)` O(n). 큐가 필요하면 `collections.deque`.

| 연산 | list | dict / set |
|---|---|---|
| 인덱스 접근 | O(1) | – |
| `x in` | **O(n)** | **O(1) 평균** (해시) |
| 끝 추가/삭제 | O(1)* | O(1) |
| 앞 삽입/삭제 | O(n) | – |

```python
# O(n^2) → O(n): 실무 코드 리뷰에서 자주 지적되는 패턴
seen = []            # x in seen 이 O(n)
seen = set()         # x in seen 이 O(1)
```
dict 키는 **해시 가능(불변)** 해야 합니다: `tuple`은 OK, `list`는 TypeError. 작은 정수(-5~256)와 일부 문자열은 캐싱(interning)되므로 `is`로 비교하면 "우연히" True가 나올 수 있습니다 — 값 비교에 `is`를 쓰지 마세요.

## 5. 면접 질문

<details><summary>Q1. Python에서 <code>==</code>와 <code>is</code>의 차이는? <code>a = 256; b = 256; a is b</code>는 True인데 257이면 False가 나오기도 하는 이유는?</summary>

`==`는 `__eq__`를 통한 **값 동등성**, `is`는 **객체 동일성**(같은 `id`)입니다. CPython은 -5~256 정수를 미리 만들어 캐싱(small int cache)하므로 256은 같은 객체를 공유합니다. 257은 매번 새 객체가 생길 수 있어 `is`가 False일 수 있지만, 같은 코드 블록 내 상수는 컴파일러가 합쳐 True가 될 수도 있습니다 — 즉 **구현 세부사항**이므로 의존하면 안 되고, `is`는 `None`, 싱글턴, 센티넬 비교에만 씁니다.
</details>

<details><summary>Q2. Node.js는 싱글 스레드인데도 높은 동시성을 처리합니다. 전통적인 Django는 어떻게 동시 요청을 처리하나요? 각각의 장단점은?</summary>

Node는 **단일 스레드 이벤트 루프 + 논블로킹 I/O**(libuv)로, I/O 대기 중 다른 요청을 처리합니다. CPU 바운드 작업이 루프를 막으면 전체가 멈추는 것이 약점입니다.
Django(WSGI)는 **요청 하나를 동기적으로 처리**하고, gunicorn 같은 서버가 **여러 워커 프로세스**(+선택적으로 스레드)를 띄워 동시성을 확보합니다. CPython의 GIL 때문에 한 프로세스 안에서 순수 Python 바이트코드는 한 번에 한 스레드만 실행되지만, I/O 대기 중에는 GIL이 해제되므로 스레드도 I/O 바운드에는 유효합니다. 장점: 코드가 단순하고 프로세스 격리로 한 요청의 크래시/CPU 사용이 다른 워커에 덜 영향. 단점: 프로세스당 메모리 비용, 동시 연결 수가 워커 수에 묶임(롱폴링/웹소켓에 불리) → ASGI(uvicorn) + async views/Channels로 보완합니다.
</details>
