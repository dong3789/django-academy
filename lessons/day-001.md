## Part 1. 환경 구축

### 1-1. 가상환경은 왜 필요한가

Node는 `npm install`을 하면 패키지가 프로젝트 안의
`node_modules/`에 들어갑니다. 프로젝트마다 자동으로 격리되죠.

Python은 다릅니다. 기본적으로 패키지가 **인터프리터 전역**
(`site-packages`)에 설치됩니다. 프로젝트 A가 Django 4를,
B가 Django 5를 쓰면 서로 덮어써서 깨집니다.

그래서 프로젝트마다 **격리된 인터프리터 환경(가상환경, venv)**
을 만듭니다. 사실상 "프로젝트 전용 node_modules"입니다.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install django
# 확인: .venv/bin/python 이어야 함
which python
```

**JS에서는:** 격리가 기본값이라 이 단계가 없습니다.
Python에서는 activate를 잊으면 전역에 설치되는 사고가 납니다.

> 💡 핵심: venv = 프로젝트 전용 node_modules. 직접 만들어야 한다.

### 1-2. activate는 실제로 무엇을 하나

면접에서 "가상환경이 어떻게 동작하나요?"가 나오면
"마법"이 아니라 메커니즘으로 답해야 합니다.

`activate`는 셸의 `PATH` 맨 앞에 `.venv/bin`을 끼워 넣을 뿐입니다.
그래서 `python`을 치면 `.venv/bin/python`이 먼저 잡힙니다.
이 python은 같은 폴더의 `pyvenv.cfg`를 보고 `sys.prefix`를
`.venv`로 잡아, 패키지 탐색 경로(`sys.path`)가 바뀝니다.

```python
import sys
print(sys.prefix)
# 출력: /home/me/proj/.venv
```

**JS에서는:** Node는 `require`가 현재 폴더부터 위로
`node_modules`를 찾아 올라가는 규칙으로 격리를 해결합니다.

> 💡 핵심: activate = PATH 조작, 격리 = sys.prefix/sys.path.

### 1-3. uv — 현대적인 도구

`pip + venv`는 동작하지만 느리고, lock 파일이 없습니다.
`uv`(Rust로 작성)는 npm처럼 **선언 파일 + lock 파일 + 실행기**를
한 번에 제공하고, pip보다 10~100배 빠릅니다.

```bash
uv init myproj && cd myproj
uv python pin 3.12
uv add django
uv add --dev pytest ruff
uv run python manage.py check
```

**JS와 대응:**

| Node | Python(uv) |
|---|---|
| `package.json` | `pyproject.toml` |
| `package-lock.json` | `uv.lock` |
| `npm install x` | `uv add x` |
| `npx x` | `uvx x` |
| `nvm` | `uv python install` |

`uv add`는 `.venv`를 자동으로 만들고, `uv run`은 activate 없이
그 환경으로 실행합니다.

> 💡 핵심: uv = npm + nvm. 새 프로젝트는 uv로 시작한다.

## Part 2. 핵심 문법의 "차이점"

### 2-1. null은 하나, undefined는 없다

JS에는 "값이 없음"이 `null`과 `undefined` 두 개입니다.
Python은 `None` 하나뿐이고, **선언 안 한 변수를 읽으면
`undefined`가 아니라 즉시 에러**(`NameError`)가 납니다.

```python
n = None
print(n)
# 출력: None
print(m)
# NameError: name 'm' is not defined
```

**JS에서는:** `let u; console.log(u)`는 `undefined`.
선언 안 한 변수는 `ReferenceError`.

> 💡 핵심: Python은 `None` 하나. "없는 값"보다 "에러"를 선호한다.

### 2-2. int는 크기 제한이 없다

JS의 `number`는 전부 64비트 실수(IEEE754)라
2⁵³ 이상의 정수는 정확도가 깨지고, 큰 정수엔 `BigInt`가 필요합니다.
Python의 `int`는 **임의 정밀도**라 메모리가 허락하는 한 정확합니다.
대신 `int`와 `float`가 **다른 타입**입니다.

```python
print(2 ** 100)
# 1267650600228229401496703205376
print(type(1), type(1.5))
# <class 'int'> <class 'float'>
```

**JS에서는:** `2 ** 100`은 근사값 `1.2676506002282294e+30`.
`typeof 1 === typeof 1.5` (둘 다 `"number"`).

다만 실수 오차는 두 언어 모두 같습니다:
`0.1 + 0.2 == 0.3`은 둘 다 False입니다. (돈 계산은 `Decimal`)

> 💡 핵심: int는 무한 정밀도, float는 JS number와 같은 IEEE754.

### 2-3. 빈 리스트·빈 dict는 falsy

`if items:`는 Python에서 "비어 있지 않으면"이라는 관용구입니다.
그런데 JS에서 `[]`와 `{}`는 **truthy**라서,
JS 습관으로 읽으면 정반대로 해석합니다. 실제로 자주 틀립니다.

```python
items = []
if not items:
    print("비어 있음")
# 출력: 비어 있음
```

**JS에서는:** `if (![])`는 실행되지 않습니다.
빈 배열 체크는 `arr.length === 0`으로 해야 합니다.

| 값 | JS | Python |
|---|---|---|
| `[]`, `{}` | truthy | **falsy** |
| `0`, `""` | falsy | falsy |
| `"0"` | truthy | truthy |

> 💡 핵심: Python에서 빈 컨테이너는 False. `if items:`가 관용구.

### 2-4. 암묵적 형변환이 없다 (강한 타입)

JS는 `1 + "1"`을 `"11"`로 만들어 버립니다. 이런 조용한 변환이
버그의 원천이라 `===`를 쓰라고 배웠죠.
Python은 **동적 타입이지만 강한 타입**입니다.
타입이 안 맞으면 변환하지 않고 에러를 냅니다.

```python
print(1 == "1")
# 출력: False
1 + "1"
# TypeError: unsupported operand
```

**JS에서는:** `1 == "1"`은 true, `1 + "1"`은 `"11"`.
그래서 Python에는 `===`가 따로 없습니다. `==`가 이미 엄격합니다.

> 💡 핵심: 동적(타입은 런타임에 결정) ≠ 약한(알아서 변환). Python은 동적+강한.

### 2-5. `==` vs `is`

Python의 `==`는 **값이 같은가**(`__eq__` 호출),
`is`는 **같은 객체인가**(메모리상 동일)입니다.
JS `===`가 객체에 대해 하는 일이 `is`에 해당합니다.

```python
a = [1]
b = [1]
print(a == b)
# True: 내용이 같다
print(a is b)
# False: 서로 다른 객체
```

`is`는 `None` 같은 **싱글턴** 비교에만 씁니다: `if x is None:`.
숫자·문자열에 `is`를 쓰면 CPython의 캐싱 때문에
"우연히" True가 나올 수 있어 위험합니다(면접 Q1 참고).

**JS에서는:** `[1] === [1]`은 false(참조 비교).
값 비교는 직접 구현하거나 라이브러리를 씁니다.

> 💡 핵심: 값은 `==`, 정체성은 `is`. `is`는 None 비교 전용으로.

### 2-6. f-string과 문자열 불변성

f-string은 템플릿 리터럴과 같은 역할에 **포맷 지정**까지 됩니다.
`{x=}`는 디버깅용으로 변수명까지 찍어 줘서 매우 편합니다.

```python
name, price = "dh", 12345.6
print(f"hi {name}")
# hi dh
print(f"{price:,.1f}")
# 12,345.6
print(f"{price=}")
# price=12345.6
```

문자열은 불변입니다. 루프에서 `s += x`를 반복하면 매번
새 문자열이 생겨 O(n²)이 될 수 있습니다. 모아서 한 번에 합칩니다.

```python
parts = []
for w in ["a", "b", "c"]:
    parts.append(w)
s = "".join(parts)
```

**JS에서는:** `` `hi ${name}` ``. 포맷은 `toLocaleString` 등
별도 API. 배열 모아 `join`하는 패턴은 같습니다.

> 💡 핵심: f-string + `{x=}` 디버깅. 반복 연결은 `"".join`.

### 2-7. 슬라이싱과 `in`

Python 시퀀스는 `[start:stop:step]` 슬라이스 문법을 공유합니다.
음수 인덱스는 뒤에서부터 셉니다. 리스트·문자열·튜플 모두 같습니다.

```python
s = "django"
print(s[-3:])
# ngo
print(s[::-1])
# ognajd
print("ang" in s)
# True
```

**JS에서는:** `s.slice(-3)`, `[...s].reverse().join("")`,
`s.includes("ang")`. 메서드가 타입마다 다릅니다.

> 💡 핵심: 슬라이스·`in`은 모든 시퀀스에 공통인 문법이다.

## Part 3. 제어 흐름

### 3-1. 들여쓰기가 문법이다

중괄호 대신 **들여쓰기(공백 4칸)** 가 블록을 정합니다.
논리 연산자도 `&& || !` 대신 영어 단어 `and or not`입니다.
삼항은 `값 if 조건 else 값` 순서로, 자연어처럼 읽힙니다.

```python
a, b = 1, False
if a > 0 and not b:
    label = "pos"
elif a == 0:
    label = "zero"
label = "pos" if a > 0 else "neg"
```

**JS에서는:** `cond ? a : b`. Python은 "a if cond else b"로
**참값이 맨 앞**에 옵니다. 순서를 헷갈리기 쉽습니다.

> 💡 핵심: 블록은 들여쓰기, 삼항은 `A if cond else B`.

### 3-2. for는 항상 for-of

Python의 `for`는 C식 `for (i=0; ...)`이 없고 항상 **이터러블 순회**입니다.
인덱스가 필요하면 `enumerate`, dict는 `.items()`로 키·값을 같이 받습니다.

```python
items = ["a", "b"]
for i, v in enumerate(items):
    print(i, v)
user = {"name": "dh"}
for k, v in user.items():
    print(k, v)
```

**JS에서는:** `for (const [i, v] of items.entries())`,
`for (const [k, v] of Object.entries(user))`.

> 💡 핵심: 인덱스는 `enumerate`, dict는 `.items()`.

### 3-3. for-else (JS에 없음)

"리스트에서 찾다가 못 찾으면 X를 해라"를 JS에선 보통
`found` 플래그로 짭니다. Python은 루프에 `else`를 붙일 수 있고,
**break 없이 끝났을 때만** 실행됩니다.

```python
target = 9
for x in [1, 2, 3]:
    if x == target:
        break
else:
    print("not found")
```

**JS에서는:** `let found = false;` 후 루프 뒤 `if (!found)`.
또는 `arr.includes`/`find`.

> 💡 핵심: 루프의 `else` = "break 안 당했으면". 이름이 헷갈리니 주석을 달자.

### 3-4. match — 구조 분해까지 하는 switch

3.10+의 `match`는 값 비교만 하는 `switch`가 아니라
**모양(구조)을 매칭하면서 변수에 꺼내 담습니다**.
JSON 같은 중첩 데이터 분기에 유용합니다.

```python
cmd = {"type": "move", "x": 1, "y": 2}
match cmd:
    case {"type": "move", "x": x, "y": y}:
        print("move", x, y)
    case _:
        print("unknown")
```

**JS에서는:** `switch(cmd.type)` 후 각 case에서
`const {x, y} = cmd`로 따로 구조 분해합니다.

> 💡 핵심: `match`는 switch + 구조 분해. `case _`가 default.

## Part 4. 함수와 데이터

### 4-1. 기본 인자 함정 (면접 단골)

Python의 기본 인자는 **함수가 정의될 때 딱 한 번** 평가됩니다.
그래서 기본값으로 리스트를 주면, 모든 호출이 **같은 리스트**를
공유합니다. 실무에서 "데이터가 요청 간에 섞이는" 버그의 원인입니다.

```python
def append(x, acc=[]):
    acc.append(x)
    return acc

print(append(1))
# [1]
print(append(2))
# [1, 2]  ← 이전 호출 값이 남음
```

해결: 기본값은 `None`, 함수 안에서 새로 만듭니다.

```python
def append(x, acc=None):
    if acc is None:
        acc = []
    acc.append(x)
    return acc
```

**JS에서는:** `function f(x, acc = [])`는 **호출마다**
기본값을 다시 평가하므로 이 버그가 없습니다.

> 💡 핵심: 가변 기본값 금지. `None`으로 받고 안에서 생성.

### 4-2. 스코프: 블록 스코프가 없다

Python은 **함수 단위 스코프**입니다. `if`/`for` 블록은
새 스코프를 만들지 않아서, 루프 변수가 루프 뒤에도 살아 있습니다.
(자세한 LEGB 규칙은 Day 3)

```python
for i in range(3):
    pass
print(i)
# 2
```

**JS에서는:** `for (let i...)`의 `i`는 루프 밖에서
`ReferenceError`. Python은 `var`에 가깝게 동작합니다.

> 💡 핵심: 블록이 아니라 함수가 스코프 경계다.

### 4-3. 구조 분해와 스프레드

JS의 `[a, ...rest]`, `{...obj}`에 해당하는 문법이 있습니다.
기호만 다릅니다: 리스트는 `*`, dict는 `**`.

```python
nums = [1, 2, 3]
first, *rest = nums
user = {"name": "dh", "age": 3}
merged = {**user, "age": 4}
email = user.get("email", "none")
```

**JS에서는:**

```javascript
const [first, ...rest] = nums;
const merged = {...user, age: 4};
const email = user.email ?? "none";
```

없는 키를 `user["email"]`로 읽으면 `undefined`가 아니라
`KeyError`입니다. 없을 수 있으면 `.get(키, 기본값)`.

> 💡 핵심: `*`=배열 rest/spread, `**`=객체 spread, `.get`=`??`.

### 4-4. 예외: EAFP 문화

JS/C는 "미리 검사하고 실행"(LBYL)하는 경향이 있습니다.
Python은 **"일단 하고, 실패하면 예외 처리"**(EAFP)가 관용적입니다.
검사와 실행 사이에 상태가 바뀌는 경쟁 조건도 피할 수 있습니다.

```python
try:
    v = int("abc")
except ValueError as e:
    print("bad", e)
else:
    print("성공 시에만", v)
finally:
    print("항상")
```

`else`는 예외가 **없을 때만** 실행됩니다. try 블록을
최소한으로 유지하려고 씁니다.

**JS에서는:** `try/catch/finally`. catch는 하나뿐이라
타입별 분기는 `if (e instanceof ...)`로 합니다.

> 💡 핵심: 타입별 `except`, 성공 경로는 `else`, EAFP가 기본.

### 4-5. 비동기 — 가장 큰 차이

Node는 런타임 전체가 **이벤트 루프** 위에서 돌고,
I/O가 기본적으로 논블로킹입니다.
Python은 **기본이 동기·블로킹**입니다. `asyncio`는 선택 사항이고,
Django 코드(ORM 포함)의 대부분은 동기 코드입니다.

```python
import time
# 이 줄에서 프로세스가 1초 멈춘다
time.sleep(1)
print("done")
```

그럼 동시 요청은 어떻게 처리할까요? 서버(gunicorn)가
**워커 프로세스/스레드를 여러 개** 띄웁니다.
이것이 Week 2(GIL)와 Week 9(배포)의 핵심 복선입니다.

**JS에서는:** `await sleep(1000)` 동안 다른 요청을 처리합니다.
`fs.readFileSync`처럼 동기 API를 쓰면 서버 전체가 멈추죠.

> 💡 핵심: Node = 이벤트 루프로 동시성, Django = 프로세스 여러 개로 동시성.

## Part 5. CS: 모든 것은 객체 + 복잡도

### 5-1. 변수는 상자가 아니라 이름표

Python 변수는 값을 담는 상자가 아니라 **객체에 붙인 이름표(참조)** 입니다.
`b = a`는 복사가 아니라 같은 객체에 이름표를 하나 더 붙이는 것입니다.

```python
a = [1, 2]
b = a
b.append(3)
print(a)
# [1, 2, 3]
print(a is b)
# True
```

함수 인자도 마찬가지입니다("call by object reference").
객체를 **변경**하면 호출자에게 보이고,
이름을 **재할당**하면 함수 안에서만 바뀝니다.

```python
def change(lst):
    lst.append(9)

def rebind(lst):
    lst = [9]
```

**JS에서는:** 객체/배열에 대해 정확히 같은 모델입니다.
차이는 Python에선 int·str도 "객체"라는 점뿐(불변이라 티가 안 남).

> 💡 핵심: 대입은 복사가 아니다. 변경(mutate)과 재할당(rebind)을 구분하라.

### 5-2. list는 동적 배열

CPython `list`는 **객체 포인터의 연속 배열**입니다.
꽉 차면 여유 있게(약 1.125배) 재할당하므로
끝에 추가(`append`)는 **분할상환 O(1)** 입니다.
하지만 앞에 넣거나 빼면 전부 한 칸씩 밀어야 해서 **O(n)** 입니다.

```python
from collections import deque
q = deque([1, 2, 3])
# 앞에서 꺼내기 O(1)
q.popleft()
```

| 연산 | list | set/dict |
|---|---|---|
| 끝 추가 | O(1)* | O(1) |
| 앞 삽입/삭제 | O(n) | – |
| `x in` | **O(n)** | **O(1)** 평균 |

**JS에서는:** `Array`도 비슷합니다. `shift/unshift`가 O(n).

> 💡 핵심: 큐가 필요하면 list 말고 `deque`.

### 5-3. 멤버십 검사는 set으로

"이미 본 값인가?"를 리스트로 검사하면 매번 O(n)이라
루프 전체가 **O(n²)** 이 됩니다. 코드 리뷰 단골 지적입니다.
set은 해시 테이블이라 평균 O(1)입니다.

```python
seen = set()
for x in [3, 1, 3]:
    if x in seen:
        print("dup", x)
    seen.add(x)
```

set 원소·dict 키는 **해시 가능(불변)** 해야 합니다.
`tuple`은 되고 `list`는 `TypeError`입니다.

**JS에서는:** `arr.includes(x)` 대신 `new Set()`의 `has`.
같은 원리입니다.

> 💡 핵심: `in`을 반복한다면 set. O(n²) → O(n).

### 문제 2. JS → Python 번역

다음 JS를 관용적인 Python으로 옮기세요.
(컴프리헨션, dict 스프레드, `.get` 활용)

```javascript
const r = users
  .filter(u => u.active)
  .map(u => ({
    ...u,
    name: u.name.toUpperCase(),
  }));
const emails = r.map(
  u => u.email ?? "none"
);
```

<details>
<summary>정답 보기</summary>

```python
r = [
    {**u, "name": u["name"].upper()}
    for u in users
    if u.get("active")
]
emails = [
    u.get("email", "none")
    for u in r
]
```

**설명**

- `filter + map`은 컴프리헨션 하나로:
  `[변환 for 원소 in 목록 if 조건]`.
- `{...u}` → `{**u}`. 뒤에 쓴 키가 덮어씁니다(JS와 동일).
- dict는 `u.name`처럼 점으로 접근할 수 없고 `u["name"]`.
- `??` → `.get(key, default)`. 주의: `??`는 값이 `null`일 때도
  기본값을 쓰지만, `.get`은 **키가 없을 때만** 기본값을 씁니다.
  키는 있는데 값이 `None`이면 `u.get("email") or "none"`이
  더 정확한 번역입니다.

</details>

### 문제 3. 첫 번째 중복 원소

리스트에서 **처음으로 두 번째 등장하는** 원소를 O(n)으로 반환하세요.
없으면 `None`. 왜 `list`가 아니라 `set`을 써야 하는지 설명하세요.

<details>
<summary>정답 보기</summary>

```python
def first_dup(xs):
    seen = set()
    for x in xs:
        if x in seen:
            return x
        seen.add(x)
    return None

print(first_dup([3, 1, 4, 1, 3]))
# 1
```

**설명**

- 순회 1회 × `in`/`add` O(1) = 전체 **O(n)**, 추가 공간 O(n).
- `seen`이 list라면 `x in seen`이 O(n)이라 전체 **O(n²)**.
- 정답이 3이 아니라 1인 점에 주의:
  "두 번째 등장이 가장 먼저 일어나는" 원소입니다.
- 원소가 해시 불가(예: list)라면 set에 넣을 수 없으니
  `tuple`로 변환해야 합니다.

</details>

### 문제 4. 람다 출력 예측

출력을 예측하고, 이유를 설명한 뒤 고치세요.

```python
fns = [lambda: i for i in range(3)]
print([f() for f in fns])
```

<details>
<summary>정답 보기</summary>

**출력:** `[2, 2, 2]`

**이유:** 클로저는 값이 아니라 **변수 `i` 자체**를 기억합니다
(late binding). 람다가 *호출되는* 시점에 `i`를 찾는데,
그때는 루프가 끝나 `i == 2`입니다.

**수정 1: 기본 인자로 값 고정** (정의 시점 평가를 역이용)

```python
fns = [lambda i=i: i for i in range(3)]
print([f() for f in fns])
# [0, 1, 2]
```

**수정 2: 팩토리 함수** (호출마다 새 스코프)

```python
def make(i):
    return lambda: i

fns = [make(i) for i in range(3)]
```

**JS 비교:** `for (let i...)`는 반복마다 새 바인딩을 만들어
`[0,1,2]`가 나오지만, `var`면 똑같이 `[3,3,3]` 류의 문제가 납니다.

</details>

### 문제 5. (심화) 2차원 리스트 함정

결과를 예측하고 참조 모델로 설명하세요.
올바른 2차원 리스트 생성법은?

```python
a = [[0] * 3] * 3
a[0][0] = 1
print(a)
```

<details>
<summary>정답 보기</summary>

**출력:** `[[1, 0, 0], [1, 0, 0], [1, 0, 0]]`

**이유:** `[[0]*3] * 3`은 안쪽 리스트를 **복사하지 않고**
같은 리스트 객체에 대한 참조를 3번 담습니다.
세 행이 모두 같은 객체라 한 곳을 바꾸면 전부 바뀝니다.

```python
print(a[0] is a[1])
# True
```

**올바른 방법:** 컴프리헨션으로 행마다 새 리스트 생성.

```python
a = [[0] * 3 for _ in range(3)]
a[0][0] = 1
print(a)
# [[1, 0, 0], [0, 0, 0], [0, 0, 0]]
```

바깥 `* 3` 대신 안쪽 `[0] * 3`은 괜찮습니다.
`0`은 불변 int라 공유해도 문제가 없기 때문입니다.

</details>

## 면접 질문

<details>
<summary>Q1. ==와 is의 차이는? 256은 is가 True인데 257은 False일 때가 있는 이유는?</summary>

**정의:** `==`는 `__eq__`를 통한 **값 동등성**,
`is`는 **객체 동일성**(같은 `id`)입니다.

**원리:** CPython은 자주 쓰는 -5~256 정수를 미리 만들어
캐싱(small int cache)합니다. 256은 항상 같은 객체라 `is`가 True.
257은 새 객체가 생길 수 있어 False가 될 수 있습니다.
다만 같은 코드 블록의 상수는 컴파일러가 합쳐서 True가 되기도 합니다.

**실무 함의:** 이건 **구현 세부사항**이라 의존하면 안 됩니다.
`is`는 `None`, `True/False`, 센티넬 객체 비교에만 씁니다.

</details>

<details>
<summary>Q2. Node는 싱글 스레드로 높은 동시성을 냅니다. 전통적인 Django는 동시 요청을 어떻게 처리하나요?</summary>

**Node:** 단일 스레드 **이벤트 루프 + 논블로킹 I/O**(libuv).
I/O를 기다리는 동안 다른 요청을 처리합니다.
약점: CPU를 오래 쓰는 작업이 루프를 막으면 전체가 멈춥니다.

**Django(WSGI):** 요청 하나를 **동기적으로** 처리합니다.
gunicorn 같은 서버가 **워커 프로세스 여러 개**(+선택적으로 스레드)를
띄워 동시성을 확보합니다.

**GIL:** CPython은 한 프로세스에서 Python 바이트코드를
한 번에 한 스레드만 실행합니다. 하지만 I/O 대기 중엔 GIL을
놓으므로, I/O 위주 작업엔 스레드도 효과가 있습니다.

**트레이드오프:**

- 장점: 코드가 단순하고, 프로세스 격리로 한 요청의 크래시나
  CPU 사용이 다른 워커에 영향을 덜 줍니다.
- 단점: 프로세스당 메모리 비용, 동시 연결 수가 워커 수에 묶임
  (롱폴링·웹소켓에 불리) → ASGI(uvicorn) + async view,
  Channels로 보완합니다.

</details>
