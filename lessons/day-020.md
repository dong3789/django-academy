## 1. 미들웨어: 양파 껍질

모든 뷰에 "로그인 확인", "요청 시간 재기", "보안 헤더 붙이기"를 하나하나 넣으면 빠뜨리기 쉽습니다. 이렇게 **모든 요청에 공통으로** 할 일은 뷰 바깥에서 한 번만 처리하고 싶습니다.

**미들웨어**(middleware, 요청과 뷰 사이에 끼는 함수 층)가 그 자리입니다. Express를 써 봤다면 `app.use()`와 거의 같습니다.

**비유:** 양파입니다. 요청은 바깥 껍질부터 안으로 들어가 뷰(심)에 닿고, 응답은 **반대 순서로** 껍질을 거쳐 나옵니다.

![미들웨어 양파 흐름](assets/gif/day20-onion.gif)

순서는 `settings.py`의 `MIDDLEWARE` 리스트가 정합니다. **위에 있을수록 바깥 껍질**입니다.

```python
MIDDLEWARE = [
    "django.middleware.security."
    "SecurityMiddleware",
    "django.contrib.sessions.middleware."
    "SessionMiddleware",
    "django.contrib.auth.middleware."
    "AuthenticationMiddleware",
]
```

(실제 파일에는 문자열 하나를 한 줄에 씁니다. 휴대폰 화면 때문에 나눴습니다. 파이썬은 붙어 있는 문자열을 자동으로 이어 붙입니다.)

**결과를 맞혀 보세요:** `AuthenticationMiddleware`를 `SessionMiddleware`보다 **위로** 옮기면?

<details>
<summary>정답</summary>

**요청이 오자마자 `ImproperlyConfigured` 에러가 납니다.** Auth는 `request.session`을 읽어 사용자를 찾는데, 세션이 아직 붙지 않았기 때문입니다 (Admin을 쓰면 시작 시 시스템 체크도 경고합니다). 미들웨어 순서는 "누가 누구 결과를 쓰는가"로 정해집니다.

</details>

**JS (Node)** · Express는 `next()`를 부르면 안쪽으로 들어갑니다.

```javascript
app.use((req, res, next) => {
  console.log("들어감");
  res.on("finish", () =>
    console.log("나옴"));
  next();
});
```

> 💡 미들웨어는 모든 요청을 감싸는 양파 껍질. 위에 있을수록 바깥이고, 응답은 거꾸로 나온다.

## 2. 커스텀 미들웨어: 요청 시간 재기

Django 미들웨어는 **"다음 단계를 받아서, 요청을 받는 함수"**입니다. 클래스로 쓰면 `__init__`에서 다음 단계(`get_response`)를 받고, `__call__`에서 요청마다 실행합니다.

Goals 대시보드가 느려졌을 때 "어느 페이지가 느린지" 알고 싶습니다. 응답 헤더에 걸린 시간을 붙여 봅시다.

```python
# goals/middleware.py
import time

class TimingMiddleware:
    def __init__(self, get_response):
        # 서버 시작 시 딱 한 번
        self.get_response = get_response
```

```python
    def __call__(self, request):
        t = time.perf_counter()
        # 여기까지가 "들어가는 길"
        res = self.get_response(request)
        # 여기부터가 "나오는 길"
        ms = (time.perf_counter() - t) * 1000
        res["X-Elapsed-ms"] = f"{ms:.1f}"
        return res
```

`settings.py`의 `MIDDLEWARE` **맨 위**에 `"goals.middleware.TimingMiddleware"`를 넣으면 다른 미들웨어 시간까지 포함해서 잽니다. 로컬에서 확인해 보세요.

```bash
python manage.py runserver
curl -I http://127.0.0.1:8000/goals/
# X-Elapsed-ms: 12.4
```

**결과를 맞혀 보세요:** 아래는 Django 미들웨어 구조를 순수 Python으로 흉내 낸 코드입니다. 출력 순서는?

```python-run
def view(req):
    print("뷰")
    return "응답"
def mw(name, nxt):
    def call(req):
        print(name, "들어감")
        res = nxt(req)
        print(name, "나옴")
        return res
    return call
app = mw("A", mw("B", view))
app("GET /")
```

<details>
<summary>정답</summary>

```text
A 들어감
B 들어감
뷰
B 나옴
A 나옴
```

`mw("A", mw("B", view))`처럼 **함수가 함수를 감싸는 구조**라서 들어갈 땐 A→B, 나올 땐 B→A입니다. Django는 `MIDDLEWARE` 리스트를 거꾸로 돌면서 정확히 이렇게 감싸 둡니다.

</details>

**미들웨어가 요청을 막을 수도 있습니다.** `get_response`를 부르지 않고 바로 응답을 돌려주면 안쪽 껍질과 뷰는 실행되지 않습니다. 점검 모드가 좋은 예입니다.

```python
from django.conf import settings
from django.http import HttpResponse

class MaintenanceMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        if settings.MAINTENANCE:
            return HttpResponse(
                "점검 중", status=503)
        return self.get_response(request)
```

> 💡 `get_response` 앞은 요청 처리, 뒤는 응답 처리. 안 부르면 거기서 끝(차단).

<details>
<summary>🔍 더 깊이 (면접용)</summary>

**훅 메서드 세 개.** `__call__` 외에도 미들웨어 클래스는 다음을 가질 수 있습니다.

- `process_view(request, view_func, args, kwargs)`: URL 매칭 후, 뷰 실행 직전. 뷰가 무엇인지 알 수 있습니다 (예: CSRF 검사가 여기서 `@csrf_exempt` 여부를 봅니다).
- `process_exception(request, exception)`: 뷰가 예외를 던졌을 때. 응답을 반환하면 그걸로 대체합니다.
- `process_template_response`: `TemplateResponse`가 렌더되기 직전.

**미들웨어 vs 데코레이터.** 모든 요청이면 미들웨어, 일부 뷰만이면 데코레이터(`@login_required`)나 믹스인이 맞습니다. 미들웨어는 **모든 정적 파일·헬스체크 요청에도** 실행되니 무거운 DB 쿼리를 넣으면 전체가 느려집니다.

**비동기.** ASGI(비동기 서버 규격)에서는 미들웨어도 `async def __call__`을 지원합니다. 동기 미들웨어가 하나라도 끼면 Django가 스레드로 바꿔 실행하므로 성능 이득이 줄어듭니다 (`sync_capable`/`async_capable` 플래그).

**`request.user`는 게으르다.** `AuthenticationMiddleware`는 `SimpleLazyObject`를 붙여 둘 뿐이고, 실제로 `request.user`를 읽을 때 DB를 조회합니다. 그래서 사용자를 안 쓰는 요청은 쿼리가 안 나갑니다.

</details>

## 3. 시그널: 편하지만 숨는다

**시그널**(signal, "이 일이 일어나면 알려 줘" 구독 장치)은 모델 저장·삭제 같은 순간에 다른 코드를 자동 실행합니다. Node의 `EventEmitter`와 같은 발행·구독(pub/sub) 패턴입니다.

목표를 달성(체크인 합계 ≥ target)하면 축하 기록 `Achievement`를 남기고 싶다고 합시다. 시그널로 쓰면 이렇습니다.

```python
# goals/signals.py
from django.db.models.signals import (
    post_save)
from django.dispatch import receiver
from .models import CheckIn, Achievement
```

```python
@receiver(post_save, sender=CheckIn)
def check_goal(sender, instance,
               created, **kwargs):
    goal = instance.goal
    if created and goal.is_done():
        Achievement.objects.get_or_create(
            goal=goal)
```

```python
# goals/apps.py (빼먹으면 안 돎)
class GoalsConfig(AppConfig):
    name = "goals"
    def ready(self):
        from . import signals
```

**JS (Node)** · 같은 패턴입니다.

```javascript
const bus = new EventEmitter();
bus.on("checkin:saved", (c) => {
  if (c.goal.isDone()) award(c.goal);
});
bus.emit("checkin:saved", checkin);
```

편해 보이지만 문제가 있습니다. 체크인 저장 코드만 읽는 사람은 **축하 기록이 생긴다는 걸 전혀 알 수 없습니다.** 코드가 멀리 떨어진 파일에 숨어 있기 때문입니다.

**결과를 맞혀 보세요:** Admin 액션에서 `CheckIn.objects.bulk_create([...])`로 체크인 5개를 한 번에 넣었습니다. 목표가 달성됐다면 `Achievement`가 생길까요?

<details>
<summary>정답</summary>

**안 생깁니다.** `bulk_create`와 `update()`는 `save()`를 부르지 않으므로 `post_save` 시그널도 안 보냅니다 (복습 1번). 시그널에 기대는 로직은 이런 "다른 저장 경로"에서 **조용히 빠집니다.** 에러도 안 나서 더 위험합니다.

</details>

순수 Python으로 시그널의 본질(콜백 목록)을 만들어 보면 왜 "숨는지" 보입니다.

```python-run
handlers = []
def connect(fn):
    handlers.append(fn)
    return fn
def save(obj):
    print("저장:", obj)
    for h in handlers:
        h(obj)
@connect
def award(obj):
    print("  축하 기록!", obj)
save("체크인#1")
```

<details>
<summary>출력 확인</summary>

```text
저장: 체크인#1
  축하 기록! 체크인#1
```

`save()` 본문 어디에도 "축하"라는 말이 없습니다. 실제 프로젝트에서는 `award`가 다른 파일에 있으니, `save`만 읽어서는 무슨 일이 일어나는지 모릅니다. 이것이 시그널의 "숨은 제어 흐름"입니다.

</details>

**그래서 같은 앱 안의 로직은 명시적 함수로 씁니다.** 체크인을 만드는 "서비스 함수"(service function, 비즈니스 동작 하나를 담는 함수)에 직접 적습니다.

```python
# goals/services.py
from django.db import transaction

@transaction.atomic
def add_checkin(goal, amount, day):
    c = CheckIn.objects.create(
        goal=goal, amount=amount, day=day)
    if goal.is_done():
        Achievement.objects.get_or_create(
            goal=goal)
    return c
```

뷰와 Admin은 이제 `add_checkin(...)`만 부릅니다. 읽는 사람이 **한 화면에서** 모든 부작용을 봅니다. `@transaction.atomic` 덕분에 축하 기록 저장이 실패하면 체크인도 함께 취소됩니다.

**시그널이 맞는 경우**도 있습니다.

| 상황 | 선택 |
|---|---|
| 내 앱 안의 로직 | 서비스 함수 |
| 남의 앱(User 등)에 반응 | 시그널 |
| 앱끼리 결합을 끊기 | 시그널 |

예: 회원가입(`User` 생성, 내가 못 고치는 `auth` 앱)마다 `Profile`을 만드는 것은 시그널이 자연스럽습니다.

> 💡 시그널은 "남의 코드에 반응"할 때만. 내 앱의 부작용은 서비스 함수에 눈에 보이게 쓴다.

<details>
<summary>🔍 더 깊이 (면접용)</summary>

**시그널은 동기·같은 트랜잭션.** `post_save` 수신자는 `save()`를 부른 **그 스레드, 그 트랜잭션 안에서** 바로 실행됩니다. 비동기가 아닙니다. 수신자가 느리면 요청이 느려지고, 수신자가 예외를 던지면 `save()`를 부른 쪽까지 예외가 올라옵니다.

**`transaction.on_commit`.** 시그널이나 서비스에서 이메일 발송·Celery 작업을 바로 실행하면, 나중에 트랜잭션이 롤백돼도 메일은 이미 나갔습니다. 커밋이 확정된 뒤 실행하도록 감쌉니다.

```python
transaction.on_commit(
    lambda: send_mail_task.delay(goal.id))
```

**중복 연결.** `ready()` 밖(예: `models.py` 아래)에서 import하면 모듈이 두 번 로드될 때 수신자가 두 번 연결될 수 있습니다. `@receiver(..., dispatch_uid="unique")`로 막습니다.

**시그널을 피해야 하는 이유 정리 (면접 답변용).**

1. 숨은 제어 흐름: 디버깅·코드 리뷰가 어렵다.
2. 우회 경로: `update()`, `bulk_create()`, raw SQL, 마이그레이션 데이터 작업에서 안 불린다.
3. 순서 보장이 약하다: 수신자 여러 개의 실행 순서에 기대면 안 된다.
4. 테스트가 어렵다: 모델 하나 만들 때마다 부작용이 따라온다.

</details>

## 연습문제

**1.** `TimingMiddleware`를 고쳐서, 500ms보다 오래 걸린 요청만 경고 로그로 남기세요. 로그에는 메서드, 경로, 걸린 시간이 보여야 합니다.

<details>
<summary>정답</summary>

```python
import logging, time
log = logging.getLogger("goals.slow")

class TimingMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response
```

```python
    def __call__(self, request):
        t = time.perf_counter()
        res = self.get_response(request)
        ms = (time.perf_counter() - t) * 1000
        if ms > 500:
            log.warning("%s %s %.0fms",
                request.method,
                request.path, ms)
        return res
```

`log.warning("%s ...", 값들)`처럼 **인자를 따로 넘기면** 로그 레벨이 꺼져 있을 때 문자열 포맷 비용도 아낍니다 (f-string은 항상 먼저 만들어집니다). 기준값 500은 실제로는 `settings`로 빼면 좋습니다.

</details>

**2.** 1절의 흉내 코드에 "차단" 미들웨어를 추가하세요. 경로가 `/admin`으로 시작하면 뷰를 부르지 않고 `"403"`을 돌려줘야 합니다. `app("/admin/x")`와 `app("/goals")`의 출력을 맞혀 보세요.

```python-run
def view(req):
    print("뷰")
    return "200"
def block(nxt):
    def call(path):
        # 여기를 완성하세요
        return nxt(path)
    return call
app = block(view)
```

<details>
<summary>정답</summary>

```python-run
def view(req):
    print("뷰")
    return "200"
def block(nxt):
    def call(path):
        if path.startswith("/admin"):
            return "403"
        return nxt(path)
    return call
app = block(view)
print(app("/admin/x"))
print(app("/goals"))
# 출력: 403 / 뷰 / 200
```

`/admin/x`는 `nxt`를 부르지 않았으므로 "뷰"가 찍히지 않습니다. Django의 점검 모드·IP 차단 미들웨어가 정확히 이 구조입니다.

</details>

**3.** 회원가입할 때마다 `Profile`(사용자당 하나, `OneToOneField`)을 자동으로 만들고 싶습니다. 서비스 함수와 시그널 중 무엇이 맞을까요? 코드도 써 보세요.

<details>
<summary>정답</summary>

**시그널이 맞습니다.** 사용자는 회원가입 뷰, `createsuperuser` 명령, Admin, 소셜 로그인 등 **여러 경로에서** 생기고, 그 경로 대부분은 내 코드가 아닙니다.

```python
@receiver(post_save,
          sender=settings.AUTH_USER_MODEL)
def make_profile(sender, instance,
                 created, **kwargs):
    if created:
        Profile.objects.get_or_create(
            user=instance)
```

`created`를 확인하지 않으면 사용자 정보를 고칠 때마다 실행됩니다. `get_or_create`를 쓰면 혹시 두 번 실행돼도 안전합니다. `sender`에 `User`를 직접 import하지 않고 `settings.AUTH_USER_MODEL`을 쓰는 이유는 Day 18의 커스텀 User 때문입니다.

</details>

## 면접 질문

<details>
<summary>Q1. Django 미들웨어의 실행 순서를 설명하고, 순서가 중요한 예를 들어 주세요.</summary>

- `MIDDLEWARE` 리스트의 **위에서 아래로** 요청이 들어가고, 응답은 **아래에서 위로** 나옵니다. 각 미들웨어는 다음 단계를 감싸는 함수이기 때문입니다.
- 중간 미들웨어가 응답을 바로 반환하면 그 안쪽 미들웨어와 뷰는 실행되지 않고, 바깥쪽 미들웨어의 "나오는 길"만 실행됩니다.
- 예 1: `SessionMiddleware`는 `AuthenticationMiddleware`보다 앞에 있어야 합니다. Auth가 세션을 읽기 때문입니다.
- 예 2: `GZipMiddleware`는 응답 본문을 압축하므로, 본문을 고치는 다른 미들웨어보다 바깥(위)에 둡니다.
- 예 3: `SecurityMiddleware`는 HTTPS 리다이렉트를 하므로 거의 맨 위에 둡니다.

</details>

<details>
<summary>Q2. 시그널은 언제 쓰고 언제 피해야 하나요?</summary>

- **쓸 때:** 내가 수정할 수 없는 앱(예: `auth.User`, 서드파티)의 이벤트에 반응해야 하거나, 재사용 앱끼리 서로 import하지 않게 결합을 끊고 싶을 때.
- **피할 때:** 같은 앱 안의 비즈니스 로직. 제어 흐름이 숨어 리뷰·디버깅이 어렵고, `update()`/`bulk_create()`에서는 실행되지 않아 조용히 누락됩니다.
- 대안은 서비스 함수에 부작용을 명시적으로 쓰고 `transaction.atomic`으로 묶는 것입니다.
- 외부 부작용(메일, 큐 작업)은 `transaction.on_commit`으로 커밋 뒤에 실행해야 롤백 시 잘못된 발송이 없습니다.
- 시그널은 동기로, 같은 트랜잭션 안에서 실행된다는 점도 함께 말하면 좋습니다.

</details>

## 오늘 정리

1. 미들웨어는 모든 요청을 감싸는 양파. `MIDDLEWARE` 위쪽이 바깥이고, 응답은 거꾸로 나온다.
2. 커스텀 미들웨어는 `get_response` 앞뒤에 코드를 넣고, 안 부르면 차단이다.
3. 시그널은 남의 앱 이벤트에만. 내 앱의 부작용은 서비스 함수 + `transaction.atomic`으로 보이게 쓴다.
