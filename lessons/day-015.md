## 1. URL 설계: 주소에 이름을 붙이기

지금 템플릿 어딘가에 `href="/new/"`처럼 주소를 직접 적었다면 위험합니다. 나중에 앱을 `/goals/` 아래로 옮기면 그 링크가 모두 깨지기 때문입니다. Django는 주소 대신 **이름**으로 가리키게 합니다.

앱이 늘면 `"list"` 같은 이름이 겹칩니다. 그래서 `app_name`으로 **앞에 성(namespace, 이름 공간)**을 붙입니다. 그러면 `goals:list`처럼 부릅니다.

**결과를 맞혀 보세요:** 아래 설정에서 `reverse("goals:edit", args=[7])`는 무엇을 돌려줄까요?

```python
# config/urls.py
path("goals/", include("goals.urls")),
# goals/urls.py
app_name = "goals"
path("<int:pk>/edit/", ..., name="edit"),
```

<details>
<summary>정답</summary>

**`"/goals/7/edit/"`** 문자열입니다. `reverse`는 이름과 인자로 주소를 **거꾸로 조립**합니다. 앞 `goals/`는 `include`한 쪽에서, 뒤는 앱 URL에서 옵니다.

</details>

**JS (Node, Express)**

```javascript
// 주소를 문자열로 직접 씀
router.get("/:id/edit", edit);
// 링크도 손으로 조립
`/goals/${id}/edit`;
```

**Python (Django)**

```python
from django.urls import reverse
url = reverse("goals:edit",
              args=[goal.pk])
# 템플릿에서는
# {% url 'goals:edit' goal.pk %}
```

`<int:pk>`는 **경로 변환기**(path converter)입니다. 숫자만 받고, 뷰에는 이미 `int`로 바꿔서 넘깁니다. Express의 `:id`는 늘 문자열이라 `Number()`가 필요했던 것과 다릅니다. `abc`가 오면 뷰까지 가지 않고 404입니다.

**비유:** 주소는 집 번지, 이름은 "엄마 집"입니다. 엄마가 이사 가도 "엄마 집"이라고 부르면 내비가 새 번지를 찾아 줍니다.

`reverse`를 순수 Python으로 흉내 내 보세요.

```python-run
routes = {"goals:edit": "/goals/{}/edit/"}
def reverse(name, args):
    return routes[name].format(*args)
print(reverse("goals:edit", [7]))
routes["goals:edit"] = "/g/{}/e/"
print(reverse("goals:edit", [7]))
```

주소 표만 바꿨는데 호출하는 쪽 코드는 그대로입니다.

> 💡 주소는 이름으로 부른다. `app_name:name` + `reverse` / `{% url %}`.

<details>
<summary>🔍 더 깊이 (면접용): reverse_lazy와 슬래시</summary>

- 클래스 속성(`success_url = ...`)은 **모듈을 불러올 때** 계산됩니다. 그때 URL 설정이 아직 다 안 불렸을 수 있어 `reverse`가 실패합니다. 그래서 `reverse_lazy`(값이 필요할 때 계산)를 씁니다.
- `APPEND_SLASH=True`(기본)면 `/goals/7/edit`로 오면 `CommonMiddleware`가 슬래시 붙은 주소로 **301 리다이렉트**합니다. POST는 리다이렉트하면 본문이 사라지므로 DEBUG에서 에러로 알려 줍니다.
- 기본 변환기는 `str`, `int`, `slug`, `uuid`, `path`입니다. `register_converter`로 직접 만들 수도 있습니다.

</details>

## 2. FBV vs CBV: 클래스 뷰의 정체

지금까지 뷰는 **함수**(FBV, Function-Based View)였습니다. 안에서 `if request.method == "POST":`로 갈랐죠. 뷰가 늘면 "로그인 확인 → 내 것만 조회 → 폼 검증 → 저장 → 리다이렉트"가 매번 반복됩니다.

**CBV**(Class-Based View, 클래스 기반 뷰)는 이 반복을 **부모 클래스**에 넣고, 다른 부분만 **오버라이드**(물려받은 메서드를 덮어쓰기)하게 합니다. 하지만 URL은 함수만 받습니다. 그래서 `as_view()`가 클래스를 **함수로 바꿔** 줍니다.

**결과를 맞혀 보세요:** 아래 뷰에 `PUT` 요청이 오면 어떻게 될까요?

```python
from django.views import View
class Ping(View):
    def get(self, request):
        return HttpResponse("pong")
```

<details>
<summary>정답</summary>

**405 Method Not Allowed**입니다. `dispatch()`가 `put` 메서드를 찾는데 없으니 `http_method_not_allowed`를 부릅니다. 함수 뷰라면 `if`를 안 썼을 때 PUT도 그냥 GET처럼 처리됐을 겁니다.

</details>

**JS (Node, Express)**

```javascript
// 메서드별로 라우터가 갈라 줌
router.route("/ping")
  .get((req, res) =>
    res.send("pong"));
// PUT은 404 (라우트 없음)
```

**Python (Django)**

```python
# urls.py: 클래스 → 함수
path("ping/", Ping.as_view()),
# as_view()가 만든 함수가
# 요청마다 Ping() 새로 생성
# → dispatch() → get()
```

Express는 **라우터**가 메서드로 가르고, Django CBV는 **뷰 안의 `dispatch()`**가 가릅니다. 핵심은 이 `dispatch`가 그냥 `getattr`라는 점입니다. 직접 만들어 보세요.

```python-run
class View:
    def dispatch(self, method):
        h = getattr(self, method.lower(),
                    None)
        return h() if h else "405"
class Ping(View):
    def get(self): return "pong"
print(Ping().dispatch("GET"))
print(Ping().dispatch("PUT"))
```

**비유:** CBV는 프랜차이즈 매뉴얼입니다. 본사(부모 클래스)가 순서를 다 정해 두고, 가맹점(내 클래스)은 메뉴판 한 장만 바꿉니다.

| | FBV | CBV |
|---|---|---|
| 읽기 | 위→아래 그대로 | 부모를 알아야 |
| 재사용 | 데코레이터 | 상속·Mixin |
| 맞는 곳 | 특이한 흐름 | CRUD 반복 |

> 💡 CBV = `as_view()`가 함수로 바꾸고, `dispatch()`가 HTTP 메서드 이름의 메서드로 보내는 클래스.

<details>
<summary>🔍 더 깊이 (면접용): 요청마다 새 인스턴스인 이유</summary>

`as_view()`는 클래스를 한 번 함수로 감싸고, **요청이 올 때마다 `cls(**initkwargs)`로 새 인스턴스**를 만듭니다. 그래서 `self.object`, `self.request`에 값을 넣어도 다른 사용자 요청과 섞이지 않습니다(스레드 안전).

반대로 **클래스 속성에 가변 객체**(`items = []`)를 두고 `append`하면, 모든 요청이 그 리스트 하나를 공유합니다. Day 1의 "이름표" 문제 그대로입니다. 그래서 `as_view(foo=...)`로 넘길 수 있는 건 **이미 클래스에 있는 속성**만 허용됩니다.

`setup()` → `dispatch()` → `get()/post()` 순서이며, 공통 전처리는 `dispatch`나 `setup`을 오버라이드하고 `super()`를 부릅니다.

</details>

## 3. 제네릭 뷰로 Goals 화면 정리

**제네릭 뷰**(generic view)는 "목록 보여 주기", "폼으로 만들기" 같은 흔한 일을 미리 짜 둔 CBV입니다. 우리는 **어디를 고칠지**만 알면 됩니다.

![CBV 요청 흐름](assets/gif/day15-cbv-flow.gif)

**결과를 맞혀 보세요:** 아래 `ListView`만 두면, 로그인한 사용자 A는 목록에서 무엇을 보게 될까요?

```python
class GoalList(LoginRequiredMixin,
               ListView):
    model = Goal
```

<details>
<summary>정답</summary>

**모든 사용자의 Goal**이 보입니다. `model = Goal`은 `Goal.objects.all()`입니다. Day 9에서 막은 "남의 데이터 보기"가 되살아나요. 그래서 `get_queryset()`을 꼭 오버라이드합니다.

</details>

목록·만들기·수정을 바꾸면 이렇습니다. 템플릿 이름 기본값은 `goals/goal_list.html`, `goals/goal_form.html`이라 기존 파일을 그대로 쓸 수 있습니다.

```python
class GoalList(LoginRequiredMixin,
               ListView):
    def get_queryset(self):
        return Goal.objects.filter(
            owner=self.request.user)
```

```python
class GoalCreate(LoginRequiredMixin,
                 CreateView):
    form_class = GoalForm
    success_url = reverse_lazy(
        "goals:list")
    def form_valid(self, form):
        form.instance.owner = \
            self.request.user
        return super().form_valid(form)
```

`form_valid`는 "검증 통과 후 저장 직전"입니다. Day 9의 `commit=False` + `owner` 채우기가 여기로 옵니다. `super()`가 저장하고 `success_url`로 리다이렉트(PRG)까지 해 줍니다.

```python
class GoalEdit(LoginRequiredMixin,
               UpdateView):
    form_class = GoalForm
    success_url = reverse_lazy(
        "goals:list")
    def get_queryset(self):
        return Goal.objects.filter(
            owner=self.request.user)
```

`UpdateView`는 URL의 `pk`로 `get_queryset()` 안에서 찾습니다. 남의 Goal 번호를 넣으면 **404**가 납니다. Day 9의 `get_object_or_404(Goal, pk=pk, owner=...)`와 같은 효과입니다.

```python
# goals/urls.py
app_name = "goals"
urlpatterns = [
  path("", GoalList.as_view(),
       name="list"),
  path("new/", GoalCreate.as_view(),
       name="create"),
  path("<int:pk>/edit/",
       GoalEdit.as_view(), name="edit"),
]
```

로컬에서 `python manage.py runserver`로 목록·추가·수정이 그대로 되는지 확인하세요. 템플릿의 `{% url 'goal_list' %}`는 `{% url 'goals:list' %}`로 바꿔야 합니다.

**JS (Node) 비교**

```javascript
// 비슷한 개념: 공통 CRUD 컨트롤러
class GoalCtrl extends CrudCtrl {
  query(req) {
    return { owner: req.user.id };
  }
}
```

**비유:** 제네릭 뷰는 밀키트입니다. 손질·순서는 다 돼 있고, 나는 "간 맞추기"(`get_queryset`, `form_valid`)만 합니다.

> 💡 제네릭 뷰에선 "어디에 끼어들지"가 실력. 내 것만은 `get_queryset`, 저장 전 손질은 `form_valid`.

<details>
<summary>🔍 더 깊이 (면접용): Mixin 순서와 MRO</summary>

`class GoalList(LoginRequiredMixin, ListView)`에서 Mixin이 **왼쪽**이어야 합니다. Day 4의 MRO(메서드 찾는 순서)는 왼쪽부터라서, `LoginRequiredMixin.dispatch()`가 먼저 돌아 손님을 걸러냅니다. 오른쪽에 두면 `View.dispatch()`가 먼저 잡혀 로그인 확인이 **건너뛰어집니다.**

- 확인: `GoalList.__mro__`를 출력해 보세요.
- `get_queryset` 대신 `get_object`에서 `if obj.owner != user: raise PermissionDenied`도 가능하지만, 403은 "그 번호가 존재한다"는 정보를 흘립니다. 404가 더 안전합니다.
- 어떤 메서드가 어디서 오는지 헷갈리면 [ccbv.co.uk](https://ccbv.co.uk)에서 클래스별 메서드·속성을 한 페이지로 볼 수 있습니다.

</details>

`/goals/7/` 주소로 내 Goal 하나를 보여 주는 `GoalDetail`과 URL을 만드세요. 남의 Goal이면 404.

class GoalDetail(LoginRequiredMixin,

path("<int:pk>/", GoalDetail.as_view(),

### 문제 2. 목록에 통계 붙이기

`GoalList`에 Day 14의 `done`(체크인 합)을 붙이고, 템플릿에 `total_done`(전체 합)도 넘기세요.

<details>
<summary>정답 보기</summary>

```python
def get_queryset(self):
    return Goal.objects.filter(
        owner=self.request.user
    ).annotate(done=Coalesce(
        Sum("checkins__amount"), 0))
```

```python
def get_context_data(self, **kw):
    ctx = super().get_context_data(**kw)
    ctx["total_done"] = sum(
        g.done for g in ctx["object_list"])
    return ctx
```

행마다 값은 `get_queryset`에서 `annotate`로, 화면용 추가 변수는 `get_context_data`에서 넣습니다. `super()`를 먼저 불러야 `object_list` 등 기본 변수가 유지됩니다. `object_list`는 이미 평가될 QuerySet이라 `sum`은 쿼리를 더 내지 않습니다(캐시 사용).

</details>

### 문제 3. dispatch 확장하기

아래 `View`에 `DELETE`를 처리하는 `Goal` 클래스를 만들고, `PATCH`는 405가 나오는지 확인하세요.

```python-run
class View:
    def dispatch(self, method):
        h = getattr(self, method.lower(),
                    None)
        return h() if h else "405"
# 여기에 작성
```

<details>
<summary>정답 보기</summary>

```python-run
class View:
    def dispatch(self, method):
        h = getattr(self, method.lower(),
                    None)
        return h() if h else "405"
class Goal(View):
    def delete(self): return "삭제됨"
print(Goal().dispatch("DELETE"))
print(Goal().dispatch("PATCH"))
# 출력: 삭제됨 / 405
```

메서드 이름을 소문자로 바꿔 같은 이름의 메서드를 찾는 것이 `dispatch`의 전부입니다. 없으면 405. Django 진짜 `dispatch`는 여기에 "허용된 메서드 목록(`http_method_names`)에 있는지" 검사가 하나 더 있습니다.

</details>

## 면접 질문

<details>
<summary>Q1. FBV와 CBV의 차이, 언제 무엇을 쓰나요?</summary>

- FBV는 요청을 받는 함수. 흐름이 위에서 아래로 보여 읽기 쉽고, 특이한 로직에 맞습니다.
- CBV는 `as_view()`로 함수가 되고, `dispatch()`가 HTTP 메서드별 메서드로 보냅니다. 상속·Mixin으로 CRUD 반복을 줄입니다.
- 단점: 동작이 부모 클래스 여러 곳에 흩어져 처음 보는 사람이 추적하기 어렵습니다.
- 기준: 표준 CRUD는 제네릭 뷰, 흐름이 독특하면 FBV. 팀 컨벤션을 따르는 게 가장 중요합니다.

</details>

<details>
<summary>Q2. 제네릭 뷰에서 "내 데이터만" 보이게 하는 올바른 방법은?</summary>

- `LoginRequiredMixin`을 **가장 왼쪽**에 두어 인증합니다(MRO상 `dispatch`가 먼저 실행).
- `get_queryset()`을 오버라이드해 `owner=self.request.user`로 거릅니다. List·Detail·Update·Delete 모두 이 QuerySet에서 찾으므로, 남의 `pk`는 자동으로 404가 됩니다(IDOR 방지).
- 생성 시 주인은 `form_valid`에서 `form.instance.owner = self.request.user`로 서버가 넣습니다. 폼 `fields`에 `owner`를 넣지 않습니다.

</details>

## 오늘 정리

1. 주소는 이름으로 부른다: `app_name:name`, `reverse`, 클래스 속성엔 `reverse_lazy`.
2. CBV는 `as_view()`로 함수가 되고 `dispatch()`가 `get`/`post`로 보낸다. 없는 메서드는 405.
3. 제네릭 뷰는 끼어들 곳이 핵심: 내 것만 `get_queryset`, 저장 전 `form_valid`, 화면 변수 `get_context_data`.
