## 1. 권한: 누구까지 "해도 돼?"

어제 인증으로 `request.user`를 채웠습니다. 이제 그 사람이 **이 동작을 해도 되는지** 판단합니다. 이것이 권한(Permission)입니다.

DRF 권한 클래스에는 질문이 두 단계 있습니다.

- `has_permission`: **뷰 전체**에 들어와도 돼? (모든 요청)
- `has_object_permission`: **이 객체 하나**를 건드려도 돼? (`get_object()` 때만)

**JS (Node)** · Express에선 미들웨어로 막습니다.

```javascript
function isOwner(req, res, next) {
  if (req.goal.ownerId !== req.user.id)
    return res.sendStatus(403);
  next();
}
```

**Python (DRF)** · 클래스로 만듭니다.

```python
# goals/permissions.py
from rest_framework import permissions

SAFE = permissions.SAFE_METHODS

class IsOwnerOrReadOnly(
        permissions.BasePermission):
    def has_object_permission(
            self, request, view, obj):
        if request.method in SAFE:
            return True
        return obj.owner == request.user
```

`SAFE_METHODS`는 `GET`·`HEAD`·`OPTIONS`, 즉 읽기 전용 메서드입니다. 읽기는 허용하고, 수정·삭제는 주인만 하게 합니다.

```python
# goals/views.py
class GoalViewSet(viewsets.ModelViewSet):
    permission_classes = [
        permissions.IsAuthenticated,
        IsOwnerOrReadOnly,
    ]
```

여러 개를 나열하면 **모두 통과(AND)**해야 합니다.

**결과를 맞혀 보세요:** `get_queryset()`을 `Goal.objects.all()`로 바꾸고 `IsOwnerOrReadOnly`만 믿었습니다. `GET /api/goals/`(목록)를 부르면 남의 목표가 보일까요?

<details>
<summary>정답</summary>

**보입니다.** `has_object_permission`은 `get_object()`가 불릴 때, 즉 **상세·수정·삭제**에서만 실행됩니다. 목록(`list`)은 객체 하나씩 검사하지 않습니다.

그래서 목록 보안은 **`get_queryset()`의 필터**가 책임지고, 객체 권한은 그 위의 **두 번째 잠금**입니다. 둘 다 둡니다.

</details>

**비유:** `has_permission`은 **건물 출입증**, `has_object_permission`은 **각 사무실 열쇠**입니다. 로비 목록판(목록 API)은 열쇠 검사를 하지 않으니, 목록판 자체에 내 사무실만 적어야 합니다.

> 💡 권한은 "해도 돼?". 객체 권한은 상세·수정에서만 돌기 때문에, 목록은 `get_queryset()`으로 막는다.

<details>
<summary>🔍 더 깊이 (면접용)</summary>

**401 vs 403**: 인증 정보가 없거나 틀리면 401(누군지 모름), 누군지는 알지만 금지면 403입니다. 권한 검사에서 실패했는데 사용자가 익명이면 DRF는 `NotAuthenticated`(401 또는 403)를, 로그인 상태면 `PermissionDenied`(403)를 냅니다.

**`get_object()`를 우회하면** 객체 권한이 안 돕니다. `@action`에서 직접 `Goal.objects.get()`을 쓰면 안 되는 이유가 이것입니다. 직접 꺼내야 한다면 `self.check_object_permissions(request, obj)`를 호출합니다.

**OR 조합**: DRF 3.9부터 `IsAdminUser | IsOwner`처럼 `|`, `&`, `~`로 조합할 수 있습니다.

**액션별 권한**: `get_permissions()`를 오버라이드해서 `self.action == "destroy"`일 때만 더 강한 권한을 줄 수 있습니다.

</details>

## 2. Throttling: "너무 자주 오시네요"

누군가 스크립트로 1초에 1,000번 요청하면 서버와 DB가 버티지 못합니다. **Throttling**(속도 제한)은 정해진 시간당 요청 수를 넘으면 **429 Too Many Requests**로 거절합니다.

```python
# config/settings.py
REST_FRAMEWORK = {
  "DEFAULT_THROTTLE_CLASSES": [
    "rest_framework.throttling"
    ".UserRateThrottle",
  ],
  "DEFAULT_THROTTLE_RATES": {
    "user": "100/min"},
}
```

로그인 사용자는 `user.id`로, 익명은 `AnonRateThrottle`이 **IP 주소**로 셉니다. 세는 기록은 Django **캐시**에 저장됩니다.

**JS (Node)** · `express-rate-limit`과 같은 역할입니다.

```javascript
app.use("/api", rateLimit({
  windowMs: 60_000, max: 100 }));
```

원리는 단순합니다. 사용자별로 최근 요청 시각을 기록하고, 창(window) 안의 개수를 셉니다. 직접 돌려 보세요.

```python-run
import time
log = {}
def allow(uid, limit=3, win=60):
    now = time.time()
    ts = [t for t in log.get(uid, [])
          if now - t < win]
    ok = len(ts) < limit
    log[uid] = ts + [now] if ok else ts
    return ok
print([allow(7) for _ in range(5)])
```

**결과를 맞혀 보세요:** 위 코드는 무엇을 출력할까요?

<details>
<summary>정답</summary>

`[True, True, True, False, False]`입니다. 60초 창 안에서 3번까지만 허용하고, 4번째부터 거절합니다. DRF의 `SimpleRateThrottle`도 이렇게 **시각 목록**을 캐시에 두고, 창을 벗어난 기록을 버린 뒤 개수를 셉니다.

거절할 때 DRF는 `Retry-After` 헤더로 "몇 초 뒤 다시 오세요"를 알려 줍니다.

</details>

특정 동작만 더 엄하게 막고 싶으면 **scope**(범위)를 씁니다.

```python
class CheckInView(APIView):
    throttle_scope = "checkin"

# settings: "DEFAULT_THROTTLE_CLASSES"
# 에 ScopedRateThrottle 추가,
# RATES에 "checkin": "10/hour"
```

**비유:** 놀이기구 줄의 **"1인 1시간 3회"** 도장입니다. 도장 칸이 꽉 차면 직원이 "다음 시간에 오세요"라고 합니다.

> 💡 Throttling = 시간당 요청 수 제한, 넘으면 429. 기록은 캐시에 있으니 캐시가 곧 정확도다.

<details>
<summary>🔍 더 깊이 (면접용)</summary>

**서버가 여러 대라면?** 기본 캐시가 `LocMemCache`(프로세스 메모리)면 서버마다 따로 세므로 제한이 사실상 N배가 됩니다. **Redis 같은 공유 캐시**를 써야 합니다.

**경쟁 조건**: DRF 스로틀은 "읽고 → 판단 → 쓰기"가 원자적이지 않아, 동시에 몰린 요청 몇 개가 한도를 넘겨 통과할 수 있습니다. 엄격해야 하면 Redis `INCR` + `EXPIRE` 같은 원자 연산을 씁니다.

**알고리즘 비교**

| 방식 | 특징 |
|---|---|
| 고정 창 | 단순, 경계에서 2배 폭주 |
| 슬라이딩 로그 | 정확, 메모리 많음 (DRF) |
| 토큰 버킷 | 순간 폭주 허용, 평균 제한 |

**보안 한계**: 스로틀은 남용 방지용이지 보안 장치가 아닙니다. IP는 프록시 뒤에서 `X-Forwarded-For` 설정(`NUM_PROXIES`)을 잘못하면 모두 같은 IP로 보이거나 위조됩니다. 로그인 무차별 대입 방어는 계정 잠금 등과 함께 씁니다.

</details>

## 3. Pagination·Filtering: 잘라서, 골라서

목표가 5,000개면 한 번에 다 보내면 느리고 폰 화면도 버벅입니다. **Pagination**(페이지 나누기)은 일정 개수씩 잘라 주고, **Filtering**은 조건에 맞는 것만 줍니다.

```python
# config/settings.py
REST_FRAMEWORK = {
  "DEFAULT_PAGINATION_CLASS":
    "rest_framework.pagination"
    ".PageNumberPagination",
  "PAGE_SIZE": 20,
}
```

이제 목록 응답 모양이 바뀝니다.

```text
{"count": 53,
 "next": ".../goals/?page=2",
 "previous": null,
 "results": [ ...20개... ]}
```

내부에서는 결국 **잘라내기**입니다. ORM이 SQL의 `LIMIT`·`OFFSET`으로 바꿉니다.

```python-run
goals = [f"goal-{i}" for i in range(1, 54)]
def page(n, size=20):
    start = (n - 1) * size
    return goals[start:start + size]
print(len(page(1)), len(page(3)))
print(page(3)[0])
```

**결과를 맞혀 보세요:** 위 코드의 출력은?

<details>
<summary>정답</summary>

```text
20 13
goal-41
```

53개를 20개씩 자르면 1·2페이지는 20개, 3페이지는 남은 13개입니다. 3페이지 시작은 41번째입니다. DRF는 `queryset[40:60]`처럼 자르고, Django가 `LIMIT 20 OFFSET 40` SQL로 바꿉니다.

</details>

**Filtering**은 `django-filter` 패키지와 DRF 기본 필터를 함께 씁니다. 로컬에서 설치하세요.

```bash
pip install django-filter
```

```python
# goals/views.py
from django_filters.rest_framework \
    import DjangoFilterBackend
from rest_framework import filters

class GoalViewSet(viewsets.ModelViewSet):
    filter_backends = [
        DjangoFilterBackend,
        filters.SearchFilter,
        filters.OrderingFilter]
```

```python
    filterset_fields = ["category"]
    search_fields = ["title"]
    ordering_fields = ["created", "target"]
```

그러면 이런 URL이 바로 됩니다.

```bash
GET /api/goals/?category=운동
GET /api/goals/?search=피아노
GET /api/goals/?ordering=-created&page=2
```

**JS (Node)** · Express에선 `req.query`를 직접 파싱해 SQL을 조립합니다. DRF는 이 반복 작업을 선언 몇 줄로 끝냅니다.

```javascript
const { category, page = 1 } = req.query;
const rows = await Goal.findAll({
  where: category ? { category } : {},
  limit: 20, offset: (page - 1) * 20 });
```

**중요:** 필터는 `get_queryset()`의 결과 **위에** 적용됩니다. 그래서 `?search=`를 아무리 바꿔도 남의 목표는 나오지 않습니다.

**비유:** 도서관 검색대입니다. 분류(필터)로 좁히고, 제목(검색)으로 찾고, 한 화면에 20권씩(페이지) 보여 줍니다. 단, 내 대출 목록 안에서만요.

> 💡 Pagination은 LIMIT/OFFSET으로 자르기, Filtering은 쿼리스트링으로 WHERE 만들기. 둘 다 `get_queryset()` 위에서 돈다.

<details>
<summary>🔍 더 깊이 (면접용)</summary>

**OFFSET의 함정**: `OFFSET 100000`이면 DB는 앞의 10만 행을 **읽고 버립니다**. 깊은 페이지일수록 느려집니다. 또 페이지를 넘기는 사이 새 행이 추가되면 항목이 **중복되거나 빠집니다**.

**CursorPagination**: "마지막으로 본 created 값 다음부터"(`WHERE created < 값 LIMIT 20`)로 가져옵니다. 인덱스를 타서 깊어도 빠르고, 중간 삽입에도 흔들리지 않습니다. 대신 "37페이지로 점프"가 안 되고, **고유하고 변하지 않는 정렬 키**가 필요합니다. 무한 스크롤 피드에 맞습니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| PageNumber | 쉬움, 점프 | 깊으면 느림 |
| LimitOffset | 유연 | 깊으면 느림 |
| Cursor | 빠름, 안정 | 점프 불가 |

**`count` 비용**: `PageNumberPagination`은 매번 `SELECT COUNT(*)`를 합니다. 큰 테이블에선 이것도 비쌉니다.

**정렬 없는 페이지**: `order_by` 없이 자르면 DB가 순서를 보장하지 않아 페이지마다 결과가 섞일 수 있습니다. DRF는 경고(`UnorderedObjectListWarning`)를 냅니다.

**`ordering_fields` 화이트리스트**: 지정하지 않으면 민감한 필드로 정렬해 값을 추측하는 공격이 가능합니다. 허용할 필드만 적습니다.

</details>

## 연습문제

**1.** 관리자(`is_staff`)는 누구의 목표든 수정할 수 있고, 일반 사용자는 자기 것만 수정하게 `IsOwnerOrStaff`를 만드세요. 읽기는 모두 허용입니다.

<details>
<summary>정답</summary>

```python
class IsOwnerOrStaff(
        permissions.BasePermission):
    def has_object_permission(
            self, request, view, obj):
        if request.method in SAFE:
            return True
        u = request.user
        return u.is_staff or obj.owner == u
```

해설: 관리자 검사를 먼저 해도 되고 OR로 묶어도 됩니다. 다만 일반 사용자는 `get_queryset()`에서 이미 자기 것만 보이므로, 관리자에게는 `get_queryset()`도 넓혀 줘야(예: `if user.is_staff: return Goal.objects.all()`) 남의 목표에 접근할 수 있습니다. 권한과 쿼리셋은 **짝으로** 바꿉니다.

</details>

**2.** 체크인 생성 API(`POST /api/goals/{id}/checkin/`)만 하루 30번으로 제한하려면 어떻게 하나요?

<details>
<summary>정답</summary>

```python
# settings.py
"DEFAULT_THROTTLE_RATES": {
    "user": "100/min",
    "checkin": "30/day"},
```

```python
# views.py
@action(detail=True, methods=["post"],
        throttle_classes=[
            ScopedRateThrottle],
        throttle_scope="checkin")
def checkin(self, request, pk=None):
    ...
```

`@action`에 넘긴 추가 인자는 그 동작에서만 뷰 속성을 덮어씁니다. 그래서 체크인에만 `ScopedRateThrottle`과 `"checkin"` 범위가 걸립니다. 핵심은 **scope 이름과 RATES의 키를 맞추는 것**입니다. ViewSet 전체에 `throttle_scope`를 두면 목록·상세에도 같은 제한이 걸리니 주의합니다.

</details>

**3.** 순수 Python으로 커서 방식 페이지를 만드세요. `after`(마지막으로 본 id)보다 큰 id를 최대 `size`개, 그리고 다음 커서를 돌려줍니다.

```python-run
ids = list(range(1, 54))
def cursor_page(after=0, size=20):
    ...
```

<details>
<summary>정답</summary>

```python-run
ids = list(range(1, 54))
def cursor_page(after=0, size=20):
    rows = [i for i in ids if i > after]
    rows = rows[:size]
    nxt = rows[-1] if len(rows) == size \
        else None
    return rows, nxt
r, c = cursor_page()
print(r[0], r[-1], c)
r, c = cursor_page(40)
print(r[0], r[-1], c)
# 출력: 1 20 20
# 출력: 41 53 None
```

해설: OFFSET처럼 "몇 개 건너뛸지"가 아니라 "**어디서부터**"를 기억합니다. DB에선 `WHERE id > 40 ORDER BY id LIMIT 20`이 되어 인덱스로 바로 찾아가므로, 페이지가 깊어도 빠릅니다. 마지막 페이지는 개수가 모자라 다음 커서가 `None`입니다.

</details>

## 면접 질문

**Q1. DRF에서 `has_permission`과 `has_object_permission`의 차이는? 목록 API 보안은 어떻게 하나요?**

<details>
<summary>모범 답안</summary>

`has_permission`은 뷰에 들어오는 모든 요청에서 먼저 실행되어 "이 엔드포인트를 쓸 자격"을 봅니다. `has_object_permission`은 `get_object()`가 객체를 꺼낼 때 실행되어 "이 객체를 다룰 자격"을 봅니다. 그래서 상세·수정·삭제에서만 돌고 목록에서는 돌지 않습니다.

목록은 `get_queryset()`에서 `owner=request.user`처럼 범위를 좁혀 막습니다. 이렇게 하면 필터·검색·페이지도 그 범위 위에서만 동작합니다. 객체 권한은 그 위의 추가 방어선으로 두고, `@action`에서는 반드시 `get_object()`를 써서 우회되지 않게 합니다.

</details>

**Q2. 게시글이 수백만 개인 피드 API에서 페이지네이션을 어떻게 설계하겠어요?**

<details>
<summary>모범 답안</summary>

OFFSET 방식은 깊은 페이지에서 앞 행을 모두 읽고 버려 느려지고, 새 글이 들어오면 중복·누락이 생깁니다. 또 매번 `COUNT(*)`도 비쌉니다.

그래서 **커서 기반 페이지네이션**을 쓰겠습니다. `(created, id)`처럼 고유하고 변하지 않는 정렬 키에 인덱스를 두고, `WHERE (created, id) < (마지막 값) ORDER BY created DESC, id DESC LIMIT 20`으로 가져옵니다. DRF의 `CursorPagination`이 이 방식이고, 커서는 인코딩되어 클라이언트가 조작하기 어렵습니다.

임의 페이지 점프가 꼭 필요한 관리자 화면 같은 곳만 PageNumber를 쓰고, 최대 페이지 수를 제한하겠습니다.

</details>

## 오늘 정리

1. 권한은 "해도 돼?". 객체 권한은 상세에서만 돌므로 목록은 `get_queryset()`이 막는다.
2. Throttling은 캐시에 요청 기록을 두고 한도를 넘으면 429. 여러 서버면 공유 캐시.
3. Pagination은 LIMIT/OFFSET(깊으면 Cursor), Filtering은 쿼리스트링을 WHERE로.
