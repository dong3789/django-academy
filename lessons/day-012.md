## 오늘 만들 것

Goal에 **날짜별 체크인**("오늘 2쪽 읽음")과 **태그**(`#건강`, `#습관`)를 붙입니다. 진행률은 이제 체크인을 더해서 계산합니다.

## 오늘 배울 것

- ForeignKey(FK): 하나에 여러 개가 매달리는 관계 (1:N)
- ManyToManyField(M2M): 서로 여러 개씩 연결되는 관계 (N:M)
- 관계 따라가기: 반대 방향 조회와 `__` 조회

## 1. 체크인: ForeignKey로 1:N

지금 Goal에는 `done` 숫자 하나만 있습니다. 그런데 "언제 얼마나 했는지"는 남지 않죠. 기록이 없으면 "이번 주에 몇 번 했나?" 같은 통계도 못 냅니다.

그래서 기록 한 줄 한 줄을 **별도 테이블**(CheckIn)에 쌓습니다. 목표 하나에 체크인이 여러 개 달리니 **1:N 관계**(일대다)입니다. Day 9의 `owner`(User 1명 : Goal 여러 개)와 같은 모양이에요.

**결과를 맞혀 보세요:** 체크인 3개가 달린 Goal "독서"를 삭제했습니다. `on_delete=models.CASCADE`라면 체크인 3개는?

<details>
<summary>정답</summary>

**같이 삭제됩니다.** CASCADE(폭포)는 "부모가 지워지면 자식도 따라 지운다"는 뜻입니다. 목표가 사라졌는데 그 기록만 남아 봐야 가리킬 곳이 없으니까요.

</details>

**JS (Node, Prisma)**

```javascript
model CheckIn {
  id     Int  @id @default(autoincrement())
  amount Int
  goal   Goal @relation(fields: [goalId],
           references: [id])
  goalId Int
}
```

**Python (Django)** · 로컬 `goals/models.py`

```python
class CheckIn(models.Model):
    goal = models.ForeignKey(
        Goal, on_delete=models.CASCADE,
        related_name="checkins")
    amount = models.PositiveIntegerField()
    day = models.DateField(auto_now_add=True)
```

Prisma는 `goalId` 열을 직접 적지만, Django는 `goal` 필드 하나만 쓰면 DB에 **`goal_id` 열**을 알아서 만듭니다. FK는 "자식 쪽"(여러 개인 쪽)에 둡니다.

![FK와 M2M](assets/gif/day12-relations.gif)

**비유:** 일기장(Goal) 한 권에 날짜별 쪽(CheckIn)이 여러 장 붙어 있는 것입니다. 쪽마다 "몇 번 일기장" 도장이 찍혀 있어요. 그 도장이 `goal_id`입니다.

모델을 바꿨으니 Day 7에서 배운 두 단계를 실행합니다.

```bash
python manage.py makemigrations
python manage.py migrate
```

이 관계를 순수 Python으로 흉내 내 보세요.

```python-run
checkins = [
    {"goal_id": 1, "amount": 2},
    {"goal_id": 2, "amount": 5},
    {"goal_id": 1, "amount": 3},
]
mine = [c for c in checkins
        if c["goal_id"] == 1]
print(sum(c["amount"] for c in mine))
```

> 💡 1:N은 **N 쪽에 FK**. 열 이름은 `필드명_id`, 지울 때 규칙은 `on_delete`.

<details>
<summary>🔍 더 깊이 (면접용): on_delete 선택지</summary>

`on_delete`는 필수 인자입니다. 부모가 지워질 때 DB 무결성(참조가 깨지지 않음)을 어떻게 지킬지 **반드시** 정하라는 뜻입니다.

| 옵션 | 동작 |
|---|---|
| `CASCADE` | 자식도 삭제 |
| `PROTECT` | 자식이 있으면 삭제 거부 |
| `SET_NULL` | 자식의 FK를 NULL로 (`null=True` 필요) |

`RESTRICT`, `SET_DEFAULT`, `DO_NOTHING`도 있습니다. 주의할 점: Django의 CASCADE는 **DB 제약이 아니라 Django가** 자식을 먼저 찾아 지우는 방식입니다. 그래서 `delete()` 시그널이 자식마다 발생하고, 자식이 수만 개면 느립니다.

FK 열에는 Django가 **인덱스를 자동으로** 만듭니다. `goal.checkins.all()`은 `WHERE goal_id = 1`이 되므로 인덱스가 없으면 매번 테이블 전체를 훑습니다 (Week 6).

</details>

## 2. 태그: ManyToManyField로 N:M

이번엔 태그입니다. "독서"에는 `#습관`, "걷기"에는 `#건강`과 `#습관`. 태그 하나가 여러 Goal에, Goal 하나가 여러 태그에 붙습니다. 이것이 **N:M 관계**(다대다)입니다.

FK는 열 하나에 값 하나만 담습니다. Goal 테이블에 `tag_id` 열을 두면 태그를 하나밖에 못 달죠. 그래서 DB는 **중간 테이블**(연결 테이블)에 `(goal_id, tag_id)` 짝을 쌓습니다.

**결과를 맞혀 보세요:** `Tag` 모델을 만들고 `Goal`에 `tags = ManyToManyField(Tag)`를 추가해 migrate했습니다. 새로 생기는 테이블은 몇 개일까요?

<details>
<summary>정답</summary>

**2개**입니다. `goals_tag`(태그 자체)와 `goals_goal_tags`(짝을 담는 중간 테이블). 중간 테이블은 우리가 모델을 쓰지 않아도 Django가 만들어 줍니다.

</details>

**JS (Node, Prisma)**

```javascript
model Goal {
  id   Int   @id @default(autoincrement())
  tags Tag[]
}
model Tag {
  id    Int    @id @default(autoincrement())
  goals Goal[]
}
```

**Python (Django)** · 로컬 `goals/models.py`

```python
class Tag(models.Model):
    name = models.CharField(
        max_length=20, unique=True)

    def __str__(self):
        return self.name
```

```python
class Goal(models.Model):
    # owner, title, target 그대로
    tags = models.ManyToManyField(
        Tag, blank=True,
        related_name="goals")
```

`blank=True`는 "폼에서 태그를 안 골라도 된다"는 뜻입니다. Tag 클래스가 Goal보다 **위에** 있어야 이름으로 참조할 수 있습니다 (아니면 `"Tag"` 문자열로).

M2M은 **집합처럼** 다룹니다. `python manage.py shell`에서 실행해 보세요.

```python
g = Goal.objects.get(title="걷기")
health, _ = Tag.objects.get_or_create(
    name="건강")
g.tags.add(health)
g.tags.all()
# 출력: <QuerySet [<Tag: 건강>]>
```

`add` / `remove` / `set([..])` / `clear()`가 중간 테이블에 행을 넣고 뺍니다. `save()`는 필요 없어요. 바로 DB에 반영됩니다.

**비유:** 학생과 동아리입니다. 학생 명부에 동아리 칸을 하나만 두면 두 곳에 못 들죠. 그래서 "가입 신청서"(중간 테이블) 한 장에 학생·동아리 이름을 적어 쌓습니다.

```python-run
pairs = {(1, "습관"), (2, "건강")}
pairs.add((2, "습관"))
pairs.add((2, "습관"))
print(len(pairs))
print(sorted(t for g, t in pairs if g == 2))
```

같은 짝을 두 번 `add`해도 하나만 남습니다. 중간 테이블에도 `(goal_id, tag_id)` **유니크 제약**이 있어서 똑같이 동작합니다.

> 💡 N:M은 **중간 테이블**. Django가 만들어 주고, `add`/`remove`/`set`으로 집합처럼 다룬다.

<details>
<summary>🔍 더 깊이 (면접용): through 모델</summary>

중간 테이블에 **정보를 더** 담고 싶을 때가 있습니다. "이 태그를 언제 붙였나" 같은 것이요. 그때는 중간 테이블을 직접 모델로 만들고 `through`로 연결합니다.

```python
class GoalTag(models.Model):
    goal = models.ForeignKey(
        Goal, on_delete=models.CASCADE)
    tag = models.ForeignKey(
        Tag, on_delete=models.CASCADE)
    added = models.DateTimeField(
        auto_now_add=True)
```

```python
    class Meta:
        constraints = [
            models.UniqueConstraint(
                fields=["goal", "tag"],
                name="uniq_goal_tag")]
```

그리고 `tags = ManyToManyField(Tag, through="GoalTag")`. 결국 **M2M = FK 두 개를 가진 테이블**이라는 점이 핵심입니다. 면접에서 "M2M은 DB에 어떻게 저장되나요?"의 답이 바로 이것입니다.

나중에 through를 추가하려면 마이그레이션이 까다롭습니다(Day 13). 추가 정보가 필요할 것 같으면 처음부터 through로 시작하는 팀도 많습니다.

</details>

## 3. 관계 따라가기: 반대 방향과 `__`

관계를 만들었으면 꺼내 써야 합니다. 방향은 두 가지입니다. **정방향**(FK를 가진 쪽에서)과 **반대 방향**(가리켜지는 쪽에서)이요.

| 출발 | 코드 | 결과 |
|---|---|---|
| CheckIn | `c.goal` | Goal 1개 |
| Goal | `g.checkins.all()` | 체크인 여러 개 |
| Tag | `tag.goals.all()` | Goal 여러 개 |

반대 방향 이름이 바로 `related_name`입니다. 안 정하면 `checkin_set`처럼 `모델명_set`이 됩니다.

**결과를 맞혀 보세요:** "`#건강` 태그가 붙은 **내** 목표"를 가져오려 합니다. SQL의 JOIN을 직접 써야 할까요?

<details>
<summary>정답</summary>

**아니요.** 필터 안에서 `__`(밑줄 두 개)로 관계를 건너가면 Django가 JOIN을 만들어 줍니다.

```python
Goal.objects.filter(
    owner=request.user,
    tags__name="건강")
```

</details>

**JS (Node, Prisma)**

```javascript
prisma.goal.findMany({
  where: {
    ownerId: user.id,
    tags: { some: { name: "건강" } },
  },
});
```

**Python (Django)**

```python
Goal.objects.filter(
    owner=request.user,
    tags__name="건강")
```

`tags__name`은 "tags를 따라가서 name이 '건강'인 것"으로 읽습니다. `checkins__amount__gte=3`처럼 여러 번 이어 붙일 수도 있습니다.

이제 진행률을 체크인으로 계산합니다. Goal에 프로퍼티를 하나 둡니다.

```python
    # (Goal 클래스 안)
    @property
    def done_total(self):
        return sum(c.amount for c in
                   self.checkins.all())
```

템플릿에서는 `{{ goal.done_total }}`로 씁니다. 체크인 테이블에서 이 Goal의 것만 모아 더하는 것이죠. 지금은 Python에서 더하지만, Day 14에 DB가 더하게(`Sum`) 바꿉니다.

`__` 조회를 순수 Python으로 풀어 보면 이렇습니다.

```python-run
goals = [
    {"t": "독서", "tags": ["습관"]},
    {"t": "걷기",
     "tags": ["건강", "습관"]},
]
hit = [g["t"] for g in goals
       if "건강" in g["tags"]]
print(hit)
```

> 💡 정방향은 `c.goal`, 반대는 `related_name`, 필터 속 관계는 `__`로 건넌다.

<details>
<summary>🔍 더 깊이 (면접용): 중복 행과 N+1 맛보기</summary>

`Goal.objects.filter(tags__name__in=["건강", "습관"])`은 "걷기"를 **두 번** 돌려줄 수 있습니다. JOIN하면 태그 짝마다 행이 하나씩 생기기 때문이에요. `.distinct()`를 붙여 중복을 없앱니다.

또 하나. 목록 화면에서 Goal 20개마다 `goal.done_total`을 부르면 쿼리가 **1 + 20번** 나갑니다. 목록 1번, Goal마다 체크인 1번씩. 이것이 유명한 **N+1 문제**입니다. 해결책은 `prefetch_related("checkins")`(Week 6)나 DB 집계 `annotate(Sum(...))`(Day 14)입니다.

FK 방향 조회(`c.goal`)는 `select_related`(JOIN 한 번), 반대·M2M은 `prefetch_related`(쿼리 2번 + Python에서 짝 맞추기)라고 기억하세요.

</details>

Goal 상세 화면에 **최근 체크인 3개**만 보여 주려 합니다. 뷰에서 쓸 쿼리를 작성하세요.

```python
recent = (goal.checkins
          .order_by("-day", "-id")[:3])
```

`related_name="checkins"`로 반대 방향에서 출발하고, `-day`는 최신순(내림차순)입니다. 같은 날 여러 번이면 `-id`로 나중 것이 먼저 옵니다. `[:3]`은 리스트 자르기가 아니라 SQL `LIMIT 3`으로 바뀌어 DB가 3개만 보냅니다. 템플릿에선 `{% for c in recent %}`로 돌립니다.

### 문제 2. 태그별 Goal 개수

아래 짝 목록에서 태그마다 Goal이 몇 개인지 `{"습관": 2, "건강": 1}` 꼴로 세어 보세요.

```python-run
pairs = [(1, "습관"), (2, "건강"),
         (2, "습관")]
# 여기에 작성
```

<details>
<summary>정답 보기</summary>

```python-run
from collections import Counter
pairs = [(1, "습관"), (2, "건강"),
         (2, "습관")]
cnt = Counter(t for _, t in pairs)
print(dict(cnt))
# 출력: {'습관': 2, '건강': 1}
```

`pairs`는 중간 테이블 그대로입니다. 태그 이름만 뽑아 `Counter`로 세면 됩니다. Django에서는 `Tag.objects.annotate(n=Count("goals"))`로 **DB가 GROUP BY**하게 하는데, Day 14에서 배웁니다.

</details>

### 문제 3. 태그 지우면?

"걷기"에 `#건강`이 붙어 있습니다. `Tag` 객체 `#건강`을 `delete()`하면 "걷기" Goal은 어떻게 될까요?

<details>
<summary>정답 보기</summary>

**Goal은 그대로 남고, 중간 테이블의 짝 `(2, 건강)`만 지워집니다.** 중간 테이블은 Goal과 Tag 양쪽에 FK(CASCADE)를 가진 테이블이라, Tag가 지워지면 그 Tag를 가리키던 **짝 행**만 따라 지워집니다. Goal 테이블은 Tag를 직접 가리키지 않으니 영향이 없습니다. 반대로 Goal을 지워도 Tag는 남습니다.

</details>

## 면접 질문

<details>
<summary>Q1. ForeignKey와 ManyToManyField는 DB에 어떻게 저장되나요?</summary>

- **FK(1:N)**: "N 쪽" 테이블에 `<필드>_id` 열이 생기고, 상대 테이블의 PK를 가리키는 외래 키 제약과 인덱스가 붙습니다. 예: `checkin.goal_id`.
- **M2M(N:M)**: 양쪽 테이블은 건드리지 않고 **중간 테이블**이 생깁니다. `(goal_id, tag_id)` 두 FK와 그 짝의 유니크 제약을 가집니다.
- 중간 테이블에 추가 정보(붙인 시각 등)가 필요하면 `through` 모델로 직접 정의합니다.
- 조회 시 `__` 조회는 JOIN이 되고, M2M·반대 방향 JOIN은 행이 중복될 수 있어 `distinct()`가 필요할 때가 있습니다.

</details>

<details>
<summary>Q2. on_delete는 왜 필수이고, 어떻게 고르나요?</summary>

- 부모가 지워질 때 자식의 참조가 깨지지 않게 **무결성 정책을 명시**하라는 뜻입니다.
- 부모 없이는 의미 없는 데이터(체크인, 댓글) → `CASCADE`.
- 지우면 안 되는 참조(주문이 가리키는 상품) → `PROTECT`. 기록은 남기고 연결만 끊기(탈퇴한 작성자) → `SET_NULL`.
- Django CASCADE는 애플리케이션 레벨에서 수행돼 시그널이 돌고 대량 삭제는 느릴 수 있다는 점, 실무에선 삭제 대신 soft delete(`is_active=False`)를 쓰기도 한다는 점을 덧붙이면 좋습니다.

</details>

## 오늘 정리

1. 1:N은 N 쪽에 `ForeignKey`. DB에는 `goal_id` 열이 생기고, `on_delete`로 삭제 규칙을 정한다.
2. N:M은 `ManyToManyField`. Django가 중간 테이블을 만들고 `add`/`remove`/`set`으로 다룬다.
3. 반대 방향은 `related_name`, 필터 속 관계는 `tags__name`처럼 `__`로 건넌다.
