## 1. APIView: 익숙한 모양에서 시작

Django의 일반 `View`도 JSON을 돌려줄 수는 있습니다. 하지만 매번 `json.loads(request.body)`, 상태 코드, 인증 확인을 손으로 해야 합니다.

DRF의 **APIView**는 Day 15의 CBV 위에 API용 기능을 얹은 것입니다. 요청 본문 파싱, 인증·권한 검사, 예외를 JSON 에러로 바꾸기를 **자동으로** 해 줍니다.

**JS (Node)** · Express라면 이렇게 씁니다.

```javascript
app.get("/api/goals", async (req, res) => {
  const goals = await Goal.findMany({
    where: { ownerId: req.user.id } });
  res.json(goals);
});
```

**Python (DRF)** · 모양이 거의 같습니다.

```python
# goals/api.py
class GoalList(APIView):
    def get(self, request):
        qs = Goal.objects.filter(
            owner=request.user)
        s = GoalListSerializer(qs, many=True)
        return Response(s.data)
```

생성(`POST`)도 같은 클래스에 메서드만 추가합니다.

```python
    def post(self, request):
        s = GoalDetailSerializer(
            data=request.data)
        s.is_valid(raise_exception=True)
        s.save(owner=request.user)
        return Response(s.data, status=201)
```

- `request.data`: JSON·폼 어느 쪽이든 **파싱된 딕셔너리**입니다. Express의 `req.body`와 같습니다.
- `Response`: 딕셔너리를 받아 JSON으로 바꿔 줍니다. 브라우저로 열면 DRF가 보기 좋은 HTML 화면까지 그려 줍니다.

**결과를 맞혀 보세요:** 제목이 빈 JSON을 `POST`하면 `post()`의 마지막 줄까지 갈까요? 클라이언트는 무엇을 받을까요?

<details>
<summary>정답</summary>

**못 갑니다.** `is_valid(raise_exception=True)`가 `ValidationError`를 던지고, APIView의 예외 처리기가 이것을 잡아 **400 응답**과 `{"title": ["제목을 입력하세요."]}` 같은 JSON을 돌려줍니다.

Express에서 에러 미들웨어(`app.use((err, req, res, next) => …)`)가 하던 일을 DRF가 기본으로 해 주는 셈입니다.

</details>

**비유:** 일반 `View`가 빈 주방이라면, APIView는 **기본 도구가 갖춰진 주방**입니다. 칼(파서), 위생 검사(인증·권한), 사고 매뉴얼(예외 처리)이 이미 있습니다.

> 💡 APIView = CBV + 파싱·인증·권한·예외 처리. 모양은 Express 핸들러와 같고, 에러는 던지기만 하면 JSON 응답이 된다.

## 2. ViewSet: 다섯 동작을 한 클래스로

API를 만들다 보면 같은 패턴이 반복됩니다. 목록, 생성, 상세, 수정, 삭제. 흔히 **CRUD**(Create·Read·Update·Delete)라고 부릅니다.

APIView로 하면 클래스 두 개(목록용, 상세용)에 메서드 다섯 개를 손으로 써야 합니다. **ViewSet**은 이것을 **동작 이름**으로 묶습니다.

| 동작(action) | HTTP |
|---|---|
| `list` / `create` | GET·POST `/goals/` |
| `retrieve` | GET `/goals/1/` |
| `update` / `partial_update` | PUT·PATCH `/goals/1/` |
| `destroy` | DELETE `/goals/1/` |

`ModelViewSet`은 이 다섯(여섯)을 **모두 미리 구현**해 둔 클래스입니다. 우리는 "무엇을"만 알려 주면 됩니다.

```python
class GoalViewSet(
        viewsets.ModelViewSet):
    serializer_class = GoalDetailSerializer

    def get_queryset(self):
        return Goal.objects.filter(
            owner=self.request.user)
```

```python
    def perform_create(self, s):
        s.save(owner=self.request.user)

    def get_serializer_class(self):
        if self.action == "list":
            return GoalListSerializer
        return GoalDetailSerializer
```

이게 전부입니다. 각 줄의 역할은 이렇습니다.

- `get_queryset()`: **이 사용자가 볼 수 있는 목표**의 범위. 목록·상세·수정·삭제가 모두 여기서 시작합니다.
- `perform_create()`: 저장 직전 훅(hook, 끼어드는 자리). 소유자를 서버가 채웁니다.
- `get_serializer_class()`: 목록은 가볍게, 상세는 중첩으로 (어제 연습문제 1번).

**결과를 맞혀 보세요:** 아래는 ViewSet이 동작 이름으로 메서드를 고르는 원리를 흉내 낸 코드입니다. 무엇이 출력될까요?

```python-run
class ViewSet:
    def list(s): return "목록"
    def destroy(s): return "삭제"
m = {"get": "list", "delete": "destroy"}
v = ViewSet()
for verb in ["get", "delete", "put"]:
    fn = getattr(v, m.get(verb, ""), None)
    print(verb, fn() if fn else "405")
```

<details>
<summary>정답</summary>

```text
get 목록
delete 삭제
put 405
```

ViewSet은 `{"get": "list", "delete": "destroy"}` 같은 **매핑표**를 받아, HTTP 메서드를 동작 이름으로 바꾼 뒤 `getattr`로 찾아 부릅니다. 매핑에 없는 메서드는 **405 Method Not Allowed**가 됩니다. 이 매핑표를 만들어 주는 것이 다음 절의 Router입니다.

</details>

**JS (Node)** · NestJS의 컨트롤러가 비슷한 발상입니다. 다만 데코레이터를 메서드마다 붙여야 합니다.

```javascript
@Controller("goals")
class GoalsController {
  @Get() list() { /* ... */ }
  @Get(":id") one(@Param("id") id) {}
  @Delete(":id") remove() {}
}
```

**비유:** APIView가 메뉴를 하나씩 주문하는 것이라면, `ModelViewSet`은 **세트 메뉴**입니다. 필요 없는 건 빼면 됩니다 (아래 연습문제 2번).

> 💡 ViewSet은 HTTP 메서드 대신 동작 이름(list·create·retrieve…)으로 생각한다. 우리는 `get_queryset`과 훅만 채운다.

<details>
<summary>🔍 더 깊이 (면접용)</summary>

**`get_queryset()` 하나가 보안의 중심입니다.** `retrieve`·`update`·`destroy`는 내부에서 `get_object()`를 부르고, `get_object()`는 `get_queryset()`에서 `pk`로 찾습니다. 그래서 남의 목표 id(`/goals/99/`)를 넣으면 범위 밖이라 **404**가 납니다. Day 9에서 본 IDOR(남의 id로 남의 데이터 접근)를 이 한 줄이 막습니다.

**404 vs 403.** "있지만 권한 없음(403)"보다 "없음(404)"이 정보를 덜 흘립니다. 다른 사용자의 목표가 **존재한다는 사실**조차 숨기기 때문입니다. 객체 단위 권한(`has_object_permission`)은 내일 권한 수업에서 봅니다.

**클래스 속성 `queryset`의 함정.** `queryset = Goal.objects.all()`처럼 클래스에 두면 모든 사용자에게 같은 범위가 됩니다. 사용자마다 달라야 하면 반드시 `get_queryset()`을 오버라이드합니다. 참고로 DRF는 클래스 속성 QuerySet을 요청마다 `.all()`로 **복제**해 써서, 결과 캐시가 요청 사이에 섞이지는 않습니다.

**믹스인 조합.** `ModelViewSet`은 `GenericViewSet` + `ListModelMixin` + `CreateModelMixin` + `RetrieveModelMixin` + `UpdateModelMixin` + `DestroyModelMixin`입니다. 읽기 전용이면 `ReadOnlyModelViewSet`, 삭제만 빼려면 필요한 믹스인만 골라 상속합니다. 파이썬 MRO(Day 4)가 이 조합을 가능하게 합니다.

</details>

## 3. Router: URL을 자동으로

ViewSet은 그 자체로는 URL에 연결할 수 없습니다. "GET은 list" 같은 매핑표가 필요하기 때문입니다. 직접 쓰면 이렇게 됩니다.

```python
goal_list = GoalViewSet.as_view(
    {"get": "list", "post": "create"})
goal_detail = GoalViewSet.as_view(
    {"get": "retrieve",
     "patch": "partial_update",
     "delete": "destroy"})
```

**Router**는 이 반복을 대신 해 줍니다.

```python
# goals/urls.py
router = DefaultRouter()
router.register("goals", GoalViewSet,
                basename="goal")
urlpatterns = [
    path("api/", include(router.urls)),
]
```

`register` 한 줄이 URL 두 개와 이름을 만듭니다.

```text
/api/goals/       goal-list
/api/goals/{pk}/  goal-detail
```

![Router가 URL을 동작으로 연결하는 흐름](assets/gif/day22-router.gif)

`basename`은 URL 이름의 앞부분입니다. `get_queryset()`만 쓰고 `queryset` 속성이 없으면 Router가 이름을 추측할 수 없어 **반드시** 적어야 합니다.

**JS (Node)** · Express에는 이런 자동 생성이 없어서 보통 직접 나열합니다.

```javascript
const r = express.Router();
r.get("/", list).post("/", create);
r.get("/:id", one).patch("/:id", edit)
 .delete("/:id", remove);
app.use("/api/goals", r);
```

### `@action`: CRUD 밖의 동작

Goals 앱에는 "오늘 체크인하기" 같은 동작도 필요합니다. CRUD 어디에도 맞지 않죠. 이럴 때 `@action`을 씁니다.

```python
@action(detail=True, methods=["post"])
def checkin(self, request, pk=None):
    goal = self.get_object()
    c = goal.checkins.create(
        amount=request.data.get("amount", 1))
    return Response(
        {"id": c.id}, status=201)
```

이 메서드는 `GoalViewSet` 안에 넣습니다. Router가 `POST /api/goals/{pk}/checkin/`을 **자동으로** 추가합니다.

**결과를 맞혀 보세요:** `detail=False`로 바꾸면 URL은 어떻게 될까요?

<details>
<summary>정답</summary>

`/api/goals/checkin/`이 됩니다. `pk`가 빠집니다.

- `detail=True`: 목표 **하나**에 대한 동작 (`/goals/1/checkin/`)
- `detail=False`: **목록 전체**에 대한 동작 (예: `/goals/summary/` 통계)

`detail=True`일 때는 꼭 `self.get_object()`로 객체를 가져오세요. 직접 `Goal.objects.get(pk=pk)`를 쓰면 `get_queryset()`의 소유자 필터와 권한 검사를 **건너뛰게** 됩니다.

</details>

**비유:** Router는 건물 **안내판 자동 생성기**입니다. 사무실(ViewSet)을 등록하면 층별 안내(URL)를 알아서 붙입니다. `@action`은 기본 안내판에 없는 "옥상 정원" 표지를 하나 더 붙이는 것입니다.

> 💡 Router는 ViewSet의 동작을 URL에 자동으로 연결한다. CRUD 밖의 동작은 `@action`, 객체는 항상 `get_object()`로.

<details>
<summary>🔍 더 깊이 (면접용)</summary>

**`SimpleRouter` vs `DefaultRouter`.** `DefaultRouter`는 `/api/`에 등록된 모든 엔드포인트 목록을 보여 주는 **API 루트 뷰**와 `.json` 같은 형식 접미사를 추가로 만듭니다. 공개 API에서 목록 노출이 싫으면 `SimpleRouter`를 씁니다.

**`@action` 안의 Serializer.** `@action(..., serializer_class=CheckInSerializer)`를 주면 그 동작에서 `self.get_serializer()`가 해당 클래스를 씁니다. 검증까지 맡기려면 `request.data.get()` 대신 Serializer로 받으세요. 위 예시는 짧게 보이려고 검증을 생략했습니다 (연습문제 3번에서 고칩니다).

**ViewSet을 언제 피할까?** 동작이 CRUD와 거리가 멀거나(결제 승인, 파일 변환), 엔드포인트마다 권한·Serializer가 전부 다르면 ViewSet의 `if self.action == ...` 분기가 늘어납니다. 그때는 `APIView`나 `generics.CreateAPIView` 같은 단일 목적 뷰가 더 읽기 쉽습니다. "편해서"가 아니라 "리소스 중심인가"로 고르세요.

</details>

## 면접 질문

**Q1.** APIView, GenericAPIView, ViewSet의 차이와 각각 언제 쓰는지 설명해 주세요.

<details>
<summary>모범 답안</summary>

**APIView**는 Django CBV에 파싱·인증·권한·예외 처리를 더한 기본 클래스로, HTTP 메서드(`get`, `post`)를 직접 구현합니다. 로직이 특이한 엔드포인트에 적합합니다.

**GenericAPIView**는 여기에 `get_queryset`, `get_object`, `get_serializer`, 페이지네이션·필터 같은 공통 도구를 더하고, 믹스인과 조합해 `ListCreateAPIView` 같은 단일 목적 뷰를 만듭니다.

**ViewSet**은 HTTP 메서드 대신 `list`, `retrieve` 같은 **동작**으로 생각하게 하고, Router가 URL을 자동 생성합니다. 하나의 리소스에 대한 표준 CRUD일 때 가장 생산적이고, CRUD에서 벗어나는 동작은 `@action`으로 붙입니다. 동작마다 규칙이 크게 다르면 분기가 늘어나니 단일 목적 뷰가 낫습니다.

</details>

**Q2.** `ModelViewSet`에서 다른 사용자의 데이터에 접근하지 못하게 하려면 어떻게 하나요?

<details>
<summary>모범 답안</summary>

`get_queryset()`을 오버라이드해 `owner=self.request.user`로 범위를 좁힙니다. 상세·수정·삭제는 `get_object()`를 거치고, `get_object()`는 이 QuerySet에서 찾기 때문에 남의 id는 **404**가 됩니다. 존재 여부도 숨길 수 있습니다.

생성 시에는 `owner`를 읽기 전용으로 두고 `perform_create()`에서 `save(owner=request.user)`로 채웁니다. 커스텀 `@action`에서도 직접 조회하지 말고 반드시 `get_object()`를 써야 이 보호를 우회하지 않습니다. 더 세밀한 규칙은 `permission_classes`와 `has_object_permission`으로 추가합니다.

</details>

## 오늘 정리

1. APIView는 CBV + 파싱·인증·권한·예외 처리. 에러는 던지면 JSON 응답이 된다.
2. ViewSet은 동작 이름으로 CRUD를 묶고, 보안의 중심은 `get_queryset()`이다.
3. Router가 URL을 자동으로 만들고, CRUD 밖의 동작은 `@action` + `get_object()`.
