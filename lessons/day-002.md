## Part 1. list — 동적 배열

### 1-1. list의 정체

CPython `list`는 **객체 포인터의 연속 배열**입니다.
원소 자체가 아니라 "원소 객체를 가리키는 주소"가 나란히 놓여 있어서,
`a[i]`는 주소 계산 한 번으로 끝나는 **O(1)** 입니다.

```python
a = [10, 20, 30]
print(a[2])
# 30
print(len(a))
# 3
```

**JS에서는:** `Array`와 겉모습이 같지만, JS는 `arr[100] = 1`로
구멍 난 희소 배열을 만들 수 있습니다. Python은
범위 밖 대입이 `IndexError`입니다. 길이 = 원소 수가 항상 성립합니다.

> 💡 핵심: list = 포인터 배열. 인덱스 접근 O(1).

### 1-2. append가 O(1)인 이유: 오버얼로케이션

배열은 크기가 고정인데 어떻게 계속 늘어날까요?
용량이 부족하면 **여유분을 더해(약 1.125배) 새로 할당하고 복사**합니다.
복사는 가끔만 일어나므로, 평균을 내면 append 한 번은 O(1)입니다.
이걸 **분할상환(amortized) O(1)** 이라고 합니다.

```python
import sys
a = []
for i in range(5):
    a.append(i)
    print(len(a), sys.getsizeof(a))
```

출력을 보면 크기(바이트)가 매번이 아니라 **계단식으로** 늘어납니다.
계단을 오르는 순간이 재할당입니다.

**JS에서는:** V8 배열도 같은 전략(용량 여유분)을 씁니다.

> 💡 핵심: 가끔 비싸지만 평균 O(1) = 분할상환.

### 1-3. 앞쪽 삽입/삭제는 O(n)

`insert(0, x)`나 `pop(0)`은 뒤의 모든 원소를 한 칸씩 밀어야 합니다.
리스트를 큐로 쓰면 원소 수에 비례해 느려집니다.

```python
from collections import deque
q = deque()
q.append(1)
q.append(2)
print(q.popleft())
# 1  (O(1))
```

| 연산 | list | deque |
|---|---|---|
| 끝 추가/삭제 | O(1)* | O(1) |
| 앞 추가/삭제 | **O(n)** | **O(1)** |
| 인덱스 `[i]` | O(1) | O(n) |

**JS에서는:** `shift()`/`unshift()`도 O(n). 대량 큐는 라이브러리로.

> 💡 핵심: FIFO 큐는 `deque`. list.pop(0)은 리뷰에서 지적받는다.

### 1-4. 슬라이스는 얕은 복사

`a[:]`는 **새 리스트**를 만들지만 원소 객체는 공유합니다.
중첩 리스트를 복사했다고 생각하고 안쪽을 바꾸면 원본도 바뀝니다.

```python
a = [[1], [2]]
b = a[:]
b[0].append(9)
print(a)
# [[1, 9], [2]]
```

깊은 복사가 필요하면 `copy.deepcopy(a)`.

**JS에서는:** `[...a]`, `a.slice()`도 똑같이 얕은 복사.
깊은 복사는 `structuredClone`.

> 💡 핵심: `[:]`/spread는 겉껍데기만 복사한다.

## Part 2. tuple — 불변 시퀀스

### 2-1. 왜 불변 리스트가 따로 있나

tuple은 만든 뒤 바꿀 수 없습니다. 이 제약 덕분에
**해시 가능**해져서 dict 키나 set 원소로 쓸 수 있습니다.
"좌표", "복합 키"처럼 값 자체가 정체성인 데이터에 씁니다.

```python
coord = (37.5, 127.0)
cities = {coord: "Seoul"}
print(cities[(37.5, 127.0)])
# Seoul
```

list를 키로 쓰면 `TypeError: unhashable type: 'list'`.

**JS에서는:** 대응 타입이 없습니다. 배열을 Map 키로 쓰면
**참조**로 비교되므로 `m.get([1,2])`는 항상 실패합니다.
그래서 보통 `"37.5,127.0"` 같은 문자열 키를 만듭니다.

> 💡 핵심: 복합 키가 필요하면 tuple.

### 2-2. 한 원소 tuple은 쉼표가 필수

괄호가 아니라 **쉼표**가 튜플을 만듭니다.
`(1)`은 그냥 괄호로 감싼 int입니다.

```python
print(type((1)))
# <class 'int'>
print(type((1,)))
# <class 'tuple'>
```

Django 설정에서 `("app",)` 대신 `("app")`을 쓰면
문자열이 되어 글자 단위로 순회되는 버그가 납니다.

> 💡 핵심: tuple을 만드는 건 쉼표다.

### 2-3. "얕은" 불변

튜플 자체는 못 바꾸지만, 안에 든 list는 바뀔 수 있습니다.
그런 튜플은 해시도 불가능합니다.

```python
t = ([1], 2)
t[0].append(9)
print(t)
# ([1, 9], 2)
hash(t)
# TypeError: unhashable type: 'list'
```

**JS에서는:** `Object.freeze`도 얕습니다. 같은 개념입니다.

> 💡 핵심: 불변은 "참조 슬롯"이 고정이라는 뜻이지 내용물까지는 아니다.

## Part 3. dict — 해시 테이블

### 3-1. 삽입 순서 보장 (3.7+)

dict는 키→값 매핑이고 **넣은 순서대로 순회**됩니다(3.7부터 언어 스펙).
JSON 응답 필드 순서가 유지되는 것도 이 덕분입니다.

```python
d = {"b": 2, "a": 1}
d["c"] = 3
print(list(d))
# ['b', 'a', 'c']
```

**JS에서는:** 일반 객체는 `{"2":0, "1":0}`처럼 정수 키를
**정렬해 버리는** 특수 규칙이 있습니다. 순서가 중요하면 `Map`.
Python dict는 `Map`에 더 가깝습니다(키 타입 자유, 프로토타입 없음).

> 💡 핵심: dict ≈ JS Map. 순서 보장, 아무 해시 가능 타입이 키.

### 3-2. 내부 구조: 왜 O(1)인가

키를 `hash(key)`로 숫자로 바꾸고, 그 숫자로 배열 위치(버킷)를 정합니다.
위치를 바로 계산하니 탐색이 평균 **O(1)** 입니다.

1. `hash(key)` → 인덱스 계산
2. 자리가 차 있으면(충돌) 다음 후보 자리를 탐색
   (**오픈 어드레싱**, 프로빙)
3. 채운 비율(**로드 팩터**)이 약 2/3을 넘으면
   테이블을 키우고 전부 다시 배치(재해시)

```python
print(hash("django") == hash("django"))
# True
print(hash((1, 2)))
# 매 실행 같은 프로세스에서 고정된 정수
```

CPython dict는 추가로 **작은 인덱스 배열 + 삽입 순서대로 쌓는
엔트리 배열** 두 개로 나뉘어 있습니다. 순서 보장과 메모리 절약이
이 구조 덕분입니다.

> 💡 핵심: 해시 → 위치 계산 → 평균 O(1). 충돌이 몰리면 최악 O(n).

### 3-3. 키가 해시 가능해야 하는 이유

키의 해시값이 저장 후 바뀌면, 그 키는 엉뚱한 버킷에 있게 되어
**다시는 찾을 수 없습니다**. 그래서 가변 객체(list, dict, set)는
아예 해시를 금지합니다.

```python
d = {}
d[[1, 2]] = "x"
# TypeError: unhashable type: 'list'
d[(1, 2)] = "x"
# OK
```

규칙: `a == b`이면 `hash(a) == hash(b)`여야 하고,
해시값은 객체 수명 동안 변하면 안 됩니다. (Day 4에서 직접 구현)

> 💡 핵심: 해시 가능 ≈ 불변. 키가 변하면 테이블이 깨진다.

### 3-4. 실무에서 자주 쓰는 dict 연산

없는 키를 `d[k]`로 읽으면 `KeyError`입니다.
"없으면 기본값"이 필요한 상황이 많아 전용 메서드가 있습니다.

```python
user = {"name": "dh"}
print(user.get("email", "none"))
# none
user.setdefault("tags", []).append("py")
user |= {"age": 3}
```

- `get`: 읽기 전용 기본값 (`??`와 비슷)
- `setdefault`: 없으면 **넣고** 그 값을 반환
- `|=`: 병합 (3.9+, `Object.assign`)

> 💡 핵심: `get`은 읽기, `setdefault`는 넣으며 읽기.

### 3-5. 순회 중 크기 변경 금지

dict를 순회하면서 키를 지우면 `RuntimeError`가 납니다.
내부 테이블이 바뀌면 순회 위치를 신뢰할 수 없기 때문입니다.

```python
d = {"a": 1, "b": 0}
for k in list(d):
    if d[k] == 0:
        del d[k]
```

`list(d)`로 키를 **먼저 복사**한 뒤 순회하면 안전합니다.
또는 컴프리헨션으로 새 dict를 만듭니다.

**JS에서는:** `Map`은 순회 중 삭제를 허용합니다. 습관 주의.

> 💡 핵심: 순회하며 지우려면 키 목록을 복사해서 돌린다.

## Part 4. set — 값 없는 해시 테이블

### 4-1. 멤버십과 집합 연산

set은 dict에서 값을 뺀 해시 테이블입니다.
`x in s`가 평균 O(1)이고, 수학의 집합 연산이 **연산자**로 있습니다.

```python
a = {1, 2, 3}
b = {2, 3, 4}
print(a & b)
# {2, 3}  교집합
print(a - b)
# {1}  차집합
```

`|`는 합집합, `^`는 대칭차입니다.
"두 목록의 공통 ID", "새로 추가된 항목" 계산이 한 줄로 끝납니다.

**JS에서는:** `Set`이 있지만 집합 연산은 최근에야 추가됐고
보통 `[...a].filter(x => b.has(x))`로 씁니다.

> 💡 핵심: 공통/차이 계산은 set 연산자로.

### 4-2. discard vs remove

`remove`는 없는 원소면 `KeyError`, `discard`는 조용히 넘어갑니다.
"있으면 지워라"는 `discard`가 맞습니다.

```python
s = {1, 2}
s.discard(9)
s.remove(9)
# KeyError: 9
```

빈 set은 `set()`입니다. `{}`는 빈 **dict**입니다.

> 💡 핵심: 빈 set은 `set()`, 안전 삭제는 `discard`.

## Part 5. 컴프리헨션

### 5-1. map/filter를 한 문장으로

컴프리헨션은 "어떤 목록에서, 조건에 맞는 것만, 이렇게 바꿔서"를
선언적으로 씁니다. 읽는 순서는 **결과 → 출처 → 조건**입니다.

```python
nums = [1, 2, 3, 4]
evens_sq = [
    n * n
    for n in nums
    if n % 2 == 0
]
print(evens_sq)
# [4, 16]
```

**JS에서는:**

```javascript
nums.filter(n => n % 2 === 0)
    .map(n => n * n);
```

> 💡 핵심: `[변환 for x in 목록 if 조건]`.

### 5-2. dict·set 컴프리헨션

중괄호를 쓰면 dict나 set이 나옵니다. `키: 값` 형태면 dict.
리스트를 ID→객체 맵으로 바꾸는 "인덱싱"에 자주 씁니다.

```python
users = [{"id": 1, "n": "a"},
         {"id": 2, "n": "b"}]
by_id = {u["id"]: u for u in users}
print(by_id[2]["n"])
# b
```

**JS에서는:** `Object.fromEntries(users.map(u => [u.id, u]))`.

> 💡 핵심: 리스트 → 조회용 dict 변환은 dict 컴프리헨션 한 줄.

### 5-3. 중첩 컴프리헨션의 순서

`for`를 두 개 쓰면 **왼쪽이 바깥 루프**입니다.
일반 중첩 for문을 위에서 아래로 쓴 순서 그대로입니다.

```python
matrix = [[1, 2], [3, 4]]
flat = [x for row in matrix for x in row]
print(flat)
# [1, 2, 3, 4]
```

**JS에서는:** `matrix.flat()` 또는 `flatMap`.

> 💡 핵심: for 순서 = 일반 중첩 루프 순서. 3단 이상이면 for문으로.

### 5-4. 컴프리헨션을 쓰면 안 될 때

컴프리헨션은 **값을 만드는** 도구입니다.
출력·저장 같은 부수 효과만 원하면 일반 `for`를 쓰세요.
쓰지도 않을 리스트를 만들어 버리는 낭비이고 의도가 흐려집니다.

```python
items = ["a", "b"]
# 나쁨: 결과 리스트를 버린다
[print(x) for x in items]
# 좋음
for x in items:
    print(x)
```

결과를 한 번만 순회한다면 `(n*n for n in nums)`처럼 괄호를 써서
**제너레이터**로 만들면 메모리를 아낍니다(Day 6).

> 💡 핵심: 값을 만들 땐 컴프리헨션, 일을 시킬 땐 for.

## Part 6. collections — 실무 단골 4종

### 6-1. Counter — 빈도 세기

"가장 많이 나온 K개"는 면접·실무 모두 단골입니다.
`Counter`는 해시 테이블로 빈도를 O(n)에 세고 `most_common`을 제공합니다.

```python
from collections import Counter
c = Counter("banana")
print(c.most_common(2))
# [('a', 3), ('n', 2)]
```

**JS에서는:** `reduce`로 객체에 카운트를 누적하고
`Object.entries(...).sort(...)`로 직접 정렬합니다.

> 💡 핵심: 빈도·Top-K는 `Counter`.

### 6-2. defaultdict — groupBy

키가 없을 때마다 "빈 리스트로 초기화"하는 코드를 없애 줍니다.
없는 키에 접근하면 **팩토리 함수**(여기선 `list`)를 호출해 채웁니다.

```python
from collections import defaultdict
groups = defaultdict(list)
for name, role in [("a", "dev"),
                   ("b", "pm")]:
    groups[role].append(name)
print(dict(groups))
# {'dev': ['a'], 'pm': ['b']}
```

**JS에서는:** `Object.groupBy`(최신) 또는
`(acc[k] ??= []).push(x)` 패턴.

> 💡 핵심: groupBy = `defaultdict(list)`.

### 6-3. namedtuple — 이름 붙은 tuple

튜플에 필드 이름을 붙여 `p[0]` 대신 `p.x`로 읽게 해 줍니다.
불변이고 가벼워서 함수가 여러 값을 반환할 때 좋습니다.

```python
from collections import namedtuple
Point = namedtuple("Point", "x y")
p = Point(1, 2)
print(p.x, p[1])
# 1 2
```

더 풍부한 기능(기본값, 메서드, 타입 힌트)이 필요하면
`@dataclass`를 씁니다(Day 4).

> 💡 핵심: 가벼운 불변 레코드는 namedtuple, 그 이상은 dataclass.

## Part 7. CS 심화: 배열 vs 해시 테이블

### 7-1. 무엇을 언제 쓰나

면접에서 "왜 `x in list`는 느리고 dict는 빠른가"를
**메모리 구조로** 설명할 수 있어야 합니다.

**동적 배열(list)**

- 연속 메모리라 CPU 캐시 효율이 좋고 순회가 빠릅니다.
- 위치로 찾기는 O(1), **값으로 찾기는 O(n)** (전부 훑음).

**해시 테이블(dict/set)**

- 값으로 찾기가 평균 O(1).
- 대가: 빈 슬롯을 남겨야 하므로 메모리를 더 씁니다.
- 순서 기반 질의(범위, 정렬)는 못 합니다 → DB에선 B-Tree 인덱스.

| 상황 | 선택 |
|---|---|
| 순서·인덱스 | `list` |
| 멤버십이 핫패스 | `set` |
| 키→값 | `dict` |
| 양끝 출입 | `deque` |
| 복합 키 | `tuple` |

> 💡 핵심: "값으로 찾는다"면 해시, "순서로 다룬다"면 배열.

### 7-2. 충돌 해결: 체이닝 vs 오픈 어드레싱

두 키가 같은 버킷으로 가면(충돌) 해결 방법이 둘 있습니다.

- **체이닝:** 버킷마다 연결 리스트를 두고 이어 붙임 (Java HashMap)
- **오픈 어드레싱:** 다른 빈 슬롯을 탐색해 넣음 (CPython dict)

오픈 어드레싱은 메모리가 연속이라 캐시에 유리하지만,
테이블이 차면 탐색이 길어지므로 로드 팩터를 낮게(~2/3) 유지합니다.

```python
# 최악의 해시: 모든 키가 같은 버킷
class K:
    def __hash__(self):
        return 1
```

이런 키를 n개 넣으면 탐색이 O(n)으로 무너집니다.
(실제 공격 기법: Hash DoS → Python은 문자열 해시를 랜덤 시드화)

> 💡 핵심: 평균 O(1)은 "해시가 고르게 퍼진다"는 가정 위에 있다.

## 연습문제

### 문제 1. 순서 유지 중복 제거

중복을 제거하되 **처음 등장 순서는 유지**하는 함수를 O(n)으로 작성하세요.

<details>
<summary>정답 보기</summary>

**방법 1: dict의 삽입 순서 이용 (한 줄)**

```python
def dedup(xs):
    return list(dict.fromkeys(xs))

print(dedup([3, 1, 3, 2, 1]))
# [3, 1, 2]
```

**방법 2: set + 결과 리스트 (명시적)**

```python
def dedup(xs):
    seen, out = set(), []
    for x in xs:
        if x not in seen:
            seen.add(x)
            out.append(x)
    return out
```

**설명**

- `dict.fromkeys`는 각 원소를 키로 넣고, 중복 키는 무시합니다.
  3.7+ dict는 삽입 순서를 보장하므로 첫 등장 순서가 남습니다.
- 둘 다 시간 O(n), 공간 O(n).
- `list(set(xs))`는 **순서가 보장되지 않아** 오답입니다.

</details>

### 문제 2. 애너그램 판별

두 문자열이 애너그램인지 판별하세요.
`Counter` 방식과 `sorted` 방식의 시간·공간 복잡도를 비교하세요.

<details>
<summary>정답 보기</summary>

```python
from collections import Counter

def is_anagram(a, b):
    return Counter(a) == Counter(b)

def is_anagram2(a, b):
    return sorted(a) == sorted(b)
```

**비교**

| 방식 | 시간 | 공간 |
|---|---|---|
| Counter | O(n) | O(k) |
| sorted | O(n log n) | O(n) |

(k = 서로 다른 문자 수)

- Counter는 한 번 훑으며 해시 테이블에 셉니다.
- sorted는 정렬 비용 O(n log n)에 새 리스트 O(n)이 듭니다.
- 실무 보강: 대소문자·공백 정규화
  (`a.lower().replace(" ", "")`)는 문제 조건에 따라 추가.
- 길이가 다르면 바로 False를 반환하는 조기 종료도 좋습니다.

</details>

### 문제 3. dict 컴프리헨션

1~20 중 3의 배수만 골라 `{원래수: 제곱}` dict를
컴프리헨션 한 줄로 만드세요.

<details>
<summary>정답 보기</summary>

```python
sq = {
    n: n * n
    for n in range(1, 21)
    if n % 3 == 0
}
print(sq)
# {3: 9, 6: 36, 9: 81, ...}
```

**설명**

- `range(1, 21)`은 1~20 (끝은 포함 안 함).
- `키: 값` 형태라 dict 컴프리헨션이 됩니다.
- 한 줄로 써도 되지만, 모바일·리뷰 가독성을 위해
  위처럼 결과/출처/조건을 줄 나눔하는 스타일도 흔합니다.

</details>

### 문제 4. 버그 찾기

다음 코드의 문제점을 지적하고 고치세요.

```python
def group_by_len(words, acc={}):
    for w in words:
        key = len(w)
        acc.setdefault(key, []).append(w)
    return acc
```

<details>
<summary>정답 보기</summary>

**문제:** 기본 인자 `{}`는 함수 정의 시 **한 번만** 만들어집니다.
두 번째 호출에 첫 호출 결과가 섞여 나옵니다.

```python
print(group_by_len(["a"]))
# {1: ['a']}
print(group_by_len(["b"]))
# {1: ['a', 'b']}  ← 버그
```

**수정:**

```python
from collections import defaultdict

def group_by_len(words):
    acc = defaultdict(list)
    for w in words:
        acc[len(w)].append(w)
    return dict(acc)
```

**설명:** 호출마다 새 컨테이너를 만들면 됩니다.
외부에서 누적 dict를 받아야 한다면 `acc=None` 후
`if acc is None: acc = {}` 패턴(Day 1)을 씁니다.
`defaultdict(list)`는 `setdefault` 반복도 없애 줍니다.

</details>

### 문제 5. (심화) list 큐 vs deque

`list`로 큐를 만들면 왜 느린지, `deque` 내부 구조가
대략 어떻게 생겼는지 설명하세요.

<details>
<summary>정답 보기</summary>

**list가 느린 이유:** `pop(0)`은 0번을 꺼낸 뒤 나머지 n-1개
포인터를 한 칸씩 앞으로 옮깁니다(memmove). 꺼낼 때마다 O(n)이라
n개를 처리하면 O(n²)입니다.

```python
import timeit
setup = "from collections import deque"
t1 = timeit.timeit(
    "a=list(range(10**5))\n"
    "while a: a.pop(0)", number=1)
```

(`deque` 버전과 비교해 보면 수백 배 차이가 납니다.)

**deque 구조:** 고정 크기(64칸) **블록들의 이중 연결 리스트**입니다.
양쪽 끝 블록과 그 안의 위치(인덱스)만 기억합니다.

- 앞/뒤 추가·삭제: 끝 블록의 포인터만 움직임 → O(1)
- 블록이 차면 새 블록을 연결, 비면 해제
- 대가: 중간 인덱스 접근 `d[i]`는 블록을 따라가야 해서 O(n)

</details>

## 면접 질문

<details>
<summary>Q1. dict는 어떻게 O(1)에 가깝게 동작하고, list를 키로 넣으면 왜 TypeError인가요?</summary>

**원리:** 키의 `hash()`로 테이블 위치를 계산하고,
충돌 시 오픈 어드레싱으로 빈 슬롯을 탐색합니다.
로드 팩터(~2/3)를 넘으면 테이블을 키워 탐색 길이를 짧게 유지하므로
평균 O(1)입니다. 최악(충돌 집중)은 O(n)입니다.

**list가 안 되는 이유:** list는 가변이라, 내용이 바뀌면 해시값도
바뀌어야 합니다. 그러면 저장된 위치와 새 해시 위치가 달라져
다시 찾을 수 없습니다. 그래서 `list.__hash__`가 `None`이고
`unhashable type` 에러가 납니다.

**대안:** `tuple`이나 `frozenset` 같은 불변 스냅샷을 키로 씁니다.

</details>

<details>
<summary>Q2. append가 "분할상환 O(1)"이라는 말을 설명해 보세요. 언제 O(n)이 보이나요?</summary>

**직관:** 용량이 찼을 때만 더 크게(약 1.125배) 재할당·복사합니다.
n번 append하는 동안 복사된 원소 총량은 등비급수로
O(n)에 수렴하므로, 한 번당 평균은 O(1)입니다.

**O(n)이 보이는 순간:** 재할당이 일어나는 바로 그 append 한 번은
전체를 복사하므로 O(n)입니다. 총합이 O(n)일 뿐 매번이 O(1)은 아닙니다.

**실무 함의:** 지연 시간이 매우 민감하면(실시간 시스템)
크기를 미리 확보하거나 다른 구조를 고려합니다.
일반 웹 서버에선 무시해도 됩니다.

</details>

<details>
<summary>Q3. JS의 객체/Map과 Python dict의 차이는? (순서, 키 타입, 프로토타입)</summary>

- **순서:** Python dict는 3.7+ 삽입 순서 보장.
  JS 객체는 정수형 키를 먼저 오름차순 정렬하는 특수 규칙이 있고,
  Map은 삽입 순서 보장.
- **키 타입:** dict는 해시 가능하면 무엇이든(int, str, tuple 혼합).
  JS 객체는 문자열/심볼만(숫자는 문자열로 변환).
  Map은 아무 값이나, 객체는 **참조**로 비교.
- **프로토타입:** JS 객체는 `__proto__`, `toString` 같은 상속 키가 있어
  임의 맵으로 쓰면 위험합니다. dict는 그런 게 없습니다.

**결론:** Python dict는 JS `Map`에 가장 가깝고,
차이는 "객체 키를 참조가 아니라 `__eq__`/`__hash__`로 비교"한다는 점입니다.

</details>
