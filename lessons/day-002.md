# Day 2 · 컬렉션 심화: list/dict/set/tuple · 컴프리헨션 · collections

> 목표: 네 가지 내장 컬렉션의 **내부 구현과 복잡도 트레이드오프**를 면접에서 설명할 수 있고, 컴프리헨션·`collections`로 Node 감각의 데이터 가공을 관용적 Python으로 옮길 수 있다.

## 1. list — 동적 배열 (ArrayList)

CPython `list`는 **객체 포인터의 연속 배열**입니다. JS `Array`와 겉모습은 비슷하지만, JS처럼 "구멍 난 희소 배열"은 없고 길이 = 원소 수입니다.

```python
a = [10, 20, 30]
# 논리:  [PyObject*, PyObject*, PyObject*]  ← 연속 메모리
# 물리:  allocated >= len  (over-allocation)
```

**오버얼로케이션**: `append`로 용량이 부족하면 약 **1.125배**(작은 리스트는 더 공격적)로 재할당합니다. 덕분에 `append`/`pop()`은 **분할상환(amortized) O(1)**입니다. 반면 `insert(0, x)` / `pop(0)`은 모든 원소를 한 칸씩 밀어야 해서 **O(n)**.

| 연산 | 복잡도 | 비고 |
|---|---|---|
| `a[i]` | O(1) | 인덱스 = 포인터 산술 |
| `a.append(x)` / `a.pop()` | O(1)* | *분할상환 |
| `a.insert(0,x)` / `a.pop(0)` | O(n) | 앞쪽 밀기 |
| `x in a` | **O(n)** | 선형 스캔 |
| `a + b` / `a * k` | O(n) | 새 리스트 할당 |

```javascript
// JS — splice(0,0,x)도 O(n), unshift/shift도 O(n). 큐면 둘 다 피하라.
arr.push(x); arr.pop();          // O(1) amortized
arr.includes(x);                 // O(n)
```
```python
from collections import deque
q = deque()
q.appendleft(1); q.popleft()     # 양쪽 O(1) — 큐/스택에 list 쓰지 말 것
```

슬라이스는 **얕은 복사**입니다: `b = a[:]`는 새 리스트지만 원소 객체는 공유합니다. `a[i:j] = [...]`는 길이가 달라도 됩니다(삽입/삭제 겸용).

## 2. tuple — 불변 시퀀스

```python
t = (1, 2, 3)
t[0] = 9          # TypeError
(1,)              # 한 원소 튜플 — 쉼표가 필수! (1)은 그냥 int
```

불변이라 **해시 가능**(원소가 모두 해시 가능할 때) → dict 키·set 원소로 쓸 수 있습니다. CPython은 작은 튜플을 freelist로 재사용하고, 길이가 고정이라 list보다 약간 가볍습니다.

```python
coord = (37.5, 127.0)
locations = {coord: "Seoul"}     # OK
# locations[[37.5, 127.0]] = ... # TypeError: unhashable type: 'list'
```

**함정**: 튜플이 "완전 불변"은 아닙니다. 원소가 가변 객체면 그 내용은 바뀝니다.
```python
t = ([1], 2)
t[0].append(9)    # t == ([1, 9], 2) — 튜플 자체는 안 바뀌었고 안의 리스트가 변함
hash(t)           # TypeError (원소에 list가 있으면 해시 불가)
```

JS에는 대응 타입이 없습니다. `Object.freeze`는 얕고, 배열 키로 쓰지도 못합니다.

## 3. dict — 오픈 어드레싱 해시 테이블 (3.7+ 삽입 순서)

Python 3.7부터 dict는 **삽입 순서를 보장**합니다(3.6 CPython은 구현 세부, 3.7+ 언어 스펙). JS의 일반 객체는 정수 키 정렬 등 특수 규칙이 있고, **순서 보장 Map**에 더 가깝습니다.

```javascript
const m = new Map([["b", 2], ["a", 1]]);
m.set("c", 3); [...m.keys()];   // ["b","a","c"] — 삽입 순서
```
```python
d = {"b": 2, "a": 1}
d["c"] = 3
list(d)                          # ['b', 'a', 'c'] — 삽입 순서 (3.7+)
```

### 내부 구조 (고수준)

CPython dict는 **오픈 어드레싱 + 별도 인덱스 배열**입니다.

1. 키의 `hash(key)` → 버킷 인덱스
2. 충돌 시 프로브(다음 슬롯 탐색)
3. **로드 팩터**가 임계치(~2/3)를 넘으면 테이블 확장·재해시

키는 **해시 가능**해야 합니다: `__hash__`와 `__eq__`가 정의되고, 수명 동안 해시값이 변하지 않아야 합니다(불변이 사실상 필수).

| 연산 | 평균 | 최악 |
|---|---|---|
| get / set / `in` / del | **O(1)** | O(n) (극단적 충돌) |
| 전체 순회 | O(n) | |

```python
user = {"name": "dh", "role": "dev"}
user.get("email", "none")        # KeyError 대신 기본값 — JS의 ?? 패턴
user.setdefault("tags", [])      # 없으면 넣고 반환 (mutable 기본값 주의는 D1)
user |= {"age": 3}               # 3.9+ 병합 (JS Object.assign / spread)
{**user, "age": 4}               # 새 dict
```

⚠️ **순회 중 크기 변경은 RuntimeError**:
```python
for k in d:
    del d[k]          # RuntimeError: dictionary changed size during iteration
# 해결: for k in list(d): ...  또는 모아서 따로 삭제
```

## 4. set — dict에서 값만 뺀 해시 집합

내부는 dict와 같은 계열의 해시 테이블입니다. `x in set` → **평균 O(1)**. 합집합·교집합·차집합이 언어 연산자로 되어 있습니다.

```python
a, b = {1, 2, 3}, {2, 3, 4}
a | b; a & b; a - b; a ^ b       # union, intersection, difference, symmetric diff
a.add(5); a.discard(9)           # discard는 없어도 에러 없음 (remove는 KeyError)
```

```javascript
const s = new Set([1, 2, 3]);
s.has(2); s.add(4);
// 합집합 등: new Set([...a, ...b]) — Python만큼 풍부하지 않음
```

원소는 dict 키와 동일하게 **해시 가능**해야 합니다. `list`/`dict`/`set` 자체는 불가 → `frozenset` 또는 `tuple`로 감싸세요.

## 5. JS ↔ Python 빠른 대응

| 목적 | JavaScript | Python |
|---|---|---|
| 순서 있는 리스트 | `Array` | `list` |
| 키-값 (순서) | `Map` | `dict` (3.7+) |
| 문자열 키 객체 | `{}` | `dict` (속성 접근은 없음 → `d["k"]`) |
| 고유 집합 | `Set` | `set` / `frozenset` |
| 불변 시퀀스 | (없음 / `Object.freeze`) | `tuple` |
| 양끝 큐 | 직접 구현 / 라이브러리 | `collections.deque` |

## 6. 컴프리헨션 — map/filter를 선언적으로

```python
nums = [1, 2, 3, 4, 5]
squares = [n * n for n in nums]                    # map
evens   = [n for n in nums if n % 2 == 0]          # filter
pairs   = [(i, n) for i, n in enumerate(nums)]
# dict / set
freq = {n: nums.count(n) for n in set(nums)}       # 주의: count는 O(n) → 아래 Counter
unique_lens = {len(w) for w in ["hi", "hey", "yo"]}
```

### 중첩 · 행렬 평탄화
```python
matrix = [[1, 2], [3, 4], [5, 6]]
flat = [x for row in matrix for x in row]          # [1,2,3,4,5,6]
# for가 왼쪽→오른쪽 = 바깥 루프 → 안쪽 루프 순서
grid = [[0] * 3 for _ in range(3)]                 # 올바른 2D (D1 복습)
```

### 월러스(:=) — 3.8+, 계산 재사용
```python
# 정규식·파싱에서 중복 호출 줄일 때
import re
results = [m.group(1) for s in lines if (m := re.search(r"id=(\d+)", s))]
```

### 언제 쓰지 말아야 하나
- **부수 효과**(I/O, 전역 변경)가 목적일 때 → 일반 `for`
- 조건·변환이 3단 이상 중첩되어 읽기 힘들 때
- 제너레이터로 충분할 때: `(n*n for n in nums)` — 괄호, **lazy** (Day 6)

```python
# 나쁜 예: 컴프리헨션으로 로깅
[print(x) for x in items]        # 리스트를 만들고 버림 — for문으로
```

## 7. `collections` 모듈 — 실무 단골

```python
from collections import deque, Counter, defaultdict, namedtuple
# typing.TypedDict, dataclasses.dataclass 는 타입/구조용 (Week 2·Day 4)
```

| 타입 | 용도 | 한 줄 예 |
|---|---|---|
| `deque` | 양끝 O(1) 큐/스택, `maxlen` 링버퍼 | `d.appendleft(x)` |
| `Counter` | 빈도 집계, `most_common(k)` | `Counter("abracadabra")` |
| `defaultdict` | 키 없을 때 팩토리 호출 | `defaultdict(list)` |
| `namedtuple` | 가벼운 불변 레코드 | `Point = namedtuple("Point", "x y")` |

```python
# Counter — 애너그램·Top-K 면접 단골
from collections import Counter
Counter("banana").most_common(2)     # [('a', 3), ('n', 2)]
Counter([1,1,2]) + Counter([2,3])    # Counter({1:2, 2:2, 3:1})

# defaultdict — groupBy
groups = defaultdict(list)
for u in users:
    groups[u["role"]].append(u)
# dict.setdefault("role", []) 반복보다 깔끔. 팩토리는 list/set/int/lambda: []

# namedtuple vs TypedDict
from typing import TypedDict
class User(TypedDict):
    name: str
    age: int
# namedtuple: 런타임 불변 객체 + 인덱스/속성 접근
# TypedDict: dict 형태 유지 + 정적 타입 체크(mypy). Django JSONField·API 응답에 자주
```

## 9. CS 심화: 배열 vs 해시 테이블

면접에서 "왜 `x in list`는 느린가 / dict는 빠른가"를 **구조로** 말할 수 있어야 합니다.

### 동적 배열 (list)
- **장점**: 지역성(cache-friendly), 인덱스 O(1), 순회 빠름, 메모리 오버헤드 상대적으로 작음
- **단점**: 임의 원소 탐색·삭제 O(n), 중간 삽입 O(n), 재할당 시 순간 비용
- `append` 분할상환 O(1): n번 append의 재할당 비용을 합산하면 ≈ O(n) → 한 번당 평균 O(1)

### 해시 테이블 (dict / set)
- **장점**: 평균 O(1) 탐색·삽입·삭제
- **단점**: 해시·테이블 오버헤드(메모리), 최악 O(n) 충돌, 순서/범위 쿼리에 불리(정렬된 키 순회는 tree/BTree)
- **로드 팩터**: `n / capacity`. 너무 높으면 충돌↑ → 탐색 길어짐 → 리사이즈. 너무 낮으면 메모리 낭비
- **충돌 해결**: 체이닝(버킷 연결리스트) vs **오픈 어드레싱**(빈 슬롯 프로브). CPython dict는 후자 + 삽입 순서용 인덱스 배열

### 언제 무엇을
| 상황 | 선택 | 이유 |
|---|---|---|
| 순서·인덱스·슬라이스 | `list` | 배열 |
| 멤버십 테스트가 핫패스 | `set` | O(1) vs O(n) |
| 키→값 매핑 | `dict` | 해시 |
| 양끝 출입 | `deque` | 링 버퍼 |
| dict 키 / 좌표 | `tuple` / `frozenset` | 해시 가능 |
| 빈도·Top-K | `Counter` | 해시 + 헬퍼 |

```python
# 실무 리뷰에서 자주 고치는 한 줄
# before: if id not in seen_list: ...     # O(n) per check → 전체 O(n²)
# after:  if id not in seen_set: ...      # O(1) → 전체 O(n)
```

## 10. 연습문제

1. 길이 n 리스트에서 **중복을 제거하되 최초 등장 순서는 유지**하는 함수를 O(n)으로 작성하라. (`dict.fromkeys` 또는 삽입 순서 dict 활용)
2. 문자열 두 개가 애너그램인지 O(n)으로 판별하라. `Counter`와 정렬(`sorted`) 두 방식의 복잡도·메모리 차이를 비교하라.
3. 다음을 컴프리헨션 **한 줄**로: 1~20 중 3의 배수만 제곱한 뒤, `{원래수: 제곱}` dict를 만들어라.
4. 아래 코드의 문제점을 지적하고 고쳐라.
   ```python
   def group_by_len(words, acc={}):
       for w in words:
           acc.setdefault(len(w), []).append(w)
       return acc
   ```
5. (심화) `list`로 큐를 만들면 왜 느린지, `deque` 내부가 대략 어떻게 생겼는지(블록 연결 / 링)를 5줄 이내로 설명하라.

<details><summary>힌트 / 해설</summary>

- 1: `list(dict.fromkeys(xs))` — 3.7+ dict 삽입 순서. 또는 `seen=set(); out=[]; for x in xs: ...`
- 2: `Counter(a)==Counter(b)` → 시간 O(n), 공간 O(k). `sorted(a)==sorted(b)` → 시간 O(n log n), 공간 O(n). 유니코드·대소문자 정규화는 별도.
- 3: `{n: n*n for n in range(1, 21) if n % 3 == 0}`
- 4: 기본 인자 `{}`가 호출 간에 공유됨(D1). `acc=None` 후 `acc = {} if acc is None else acc`. 또는 `defaultdict(list)`로 새 객체를 매 호출 생성.
- 5: `list.pop(0)`은 전 원소 이동 O(n). `deque`는 고정 크기 블록을 더블 링크(또는 링)로 이어 양쪽 끝 포인터만 움직이므로 append/popleft가 O(1).
</details>

## 11. 면접 질문

<details><summary>Q1. Python dict는 어떻게 O(1)에 가깝게 동작하고, 키에 list를 넣으면 왜 TypeError인가?</summary>

키의 `hash()`로 버킷을 정한 뒤 오픈 어드레싱으로 슬롯을 찾습니다. 평균 프로브 길이가 짧도록 로드 팩터를 관리·리사이즈하므로 평균 O(1)입니다. `list`는 가변이라 내용이 바뀌면 해시값도 바뀌어 테이블 불변식이 깨집니다 — 그래서 `__hash__ = None`이고 `unhashable type` TypeError가 납니다. 키로 쓰려면 `tuple`/`frozenset`처럼 불변 스냅샷이 필요합니다.
</details>

<details><summary>Q2. <code>append</code>가 분할상환 O(1)이라는 말을 수식으로/직관적으로 설명해 보세요. 언제 O(n)이 보이나요?</summary>

용량이 가득 찰 때만 약 α배(α≈1.125)로 재할당합니다. 길이 1→n까지 append할 때 복사 비용은 roughly `1 + α + α² + ... ≤ O(n)`이라 **한 번당 평균 O(1)**입니다. 단일 `append` 호출이 재할당을 만나면 그 한 번은 O(n)이 보이지만, 연속 작업의 총합은 O(n)입니다. 실시간 지연이 민감하면 미리 `list` 크기를 확보하거나 다른 구조를 검토합니다.
</details>

<details><summary>Q3. JS <code>Map</code> / 객체와 Python <code>dict</code>의 차이는? 삽입 순서·키 타입·프로토타입 측면에서.</summary>

Python `dict`는 3.7+ **삽입 순서 보장**, 키는 해시 가능이면 어떤 타입도 가능(혼합 타입 OK), 프로토타입 체인이 없습니다. JS 일반 객체는 문자열/심볼 키, 정수 키 정렬 등 특수 규칙·프로토타입 상속이 있어 임의 맵으로 쓰기 위험하고, **삽입 순서 맵**이 필요하면 `Map`을 씁니다. `Map`은 객체 참조도 키로 쓸 수 있습니다(동일성 = 참조). Python에서 객체 식별로 쓰려면 보통 `id`를 키로 두거나 weakref 계열을 검토합니다.
</details>
