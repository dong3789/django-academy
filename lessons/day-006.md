# Day 6 · 이터레이터·제너레이터·yield from

> 목표: `for`·컴프리헨션·언패킹이 내부에서 쓰는
> **이터레이션 프로토콜**(`__iter__`/`__next__`)을 설명하고,
> 제너레이터로 **지연 평가**(lazy evaluation)를 설계하며,
> `yield from`으로 제너레이터를 위임·합성하는 법을 익힌다.
> CS로는 "전부 메모리에 올리지 않는 **풀(pull) 기반 파이프라인**"을 본다.

Django의 `QuerySet`은 리스트가 아닙니다.
`for row in User.objects.filter(active=True):`를 쓰는 순간
DB에서 **한 줄씩** 가져오는 이터레이터 관약이 동작합니다.
오늘 프로토콜을 모르면 ORM이 "마법으로 느려지거나 빨라지는"
블랙박스로 남습니다. (ORM 세부 최적화는 나중에 다룹니다.)

## Part 1. 이터레이션 프로토콜

### 1-1. for가 실제로 하는 일

`for x in items:`는 문법 설탕입니다.
내부에서는 ① `iter(items)`로 **이터레이터**를 얻고,
② `next(it)`를 반복하다 ③ `StopIteration`이 나면 끝냅니다.
리스트·문자열·파일·range·dict 키가 모두 같은 관약을 따릅니다.
이 관약 덕분에 `for` 한 줄로 어떤 컨테이너든 순회할 수 있습니다.

```python
items = [10, 20, 30]
it = iter(items)
print(next(it))
# 출력: 10
print(next(it))
# 출력: 20
```

```python
print(next(it))
# 출력: 30
print(next(it))
# StopIteration
```

**JS에서는:** `for...of`가 `[Symbol.iterator]()`를 호출합니다.
Python의 `iter()` ↔ JS의 `obj[Symbol.iterator]()`,
`next()` ↔ `iterator.next()`(값+`done` 플래그)입니다.
Python은 끝이 예외(`StopIteration`)로 표현됩니다.

> 💡 핵심: for = iter → 반복 next → StopIteration으로 종료.

### 1-2. 이터러블 vs 이터레이터

**이터러블**(iterable)은 `iter()`를 받을 수 있는 객체입니다.
`__iter__`를 구현하거나(시퀀스는 `__getitem__`으로도 가능)하면 됩니다.
**이터레이터**(iterator)는 `__next__`로 값을 하나씩 꺼내는 객체입니다.
이터레이터는 보통 `__iter__`가 `self`를 반환해, 자기 자신도 이터러블입니다.

```python
nums = [1, 2, 3]
it = iter(nums)
print(it is iter(it))
# 출력: True
```

리스트는 이터러블이지만 이터레이터가 아닙니다.
`iter(리스트)`를 할 때마다 **새** 이터레이터가 생깁니다.
그래서 같은 리스트를 `for`로 두 번 돌릴 수 있습니다.

```python
xs = [1, 2]
print(list(iter(xs)))
# 출력: [1, 2]
print(list(iter(xs)))
# 출력: [1, 2]
```

**JS에서는:** 배열은 iterable이고, `arr[Symbol.iterator]()`가
iterator를 줍니다. 한 번 소진된 iterator는 다시 쓸 수 없습니다.
Python도 이터레이터는 **일회용**입니다.

> 💡 핵심: 이터러블=순회 가능, 이터레이터=다음 값을 꺼내는 커서.

### 1-3. StopIteration은 에러가 아니다

`StopIteration`은 "더 이상 값 없음"을 알리는 **제어 신호**입니다.
`for`·`list()`·언패킹이 이 예외를 내부에서 잡습니다.
직접 `next(it)`를 쓸 때만 바깥으로 새어 나옵니다.
기본값을 주면 예외 대신 그 값을 받을 수 있습니다.

```python
it = iter([1])
print(next(it, None))
# 출력: 1
print(next(it, None))
# 출력: None
```

**주의:** 제너레이터 안에서 `return 값`을 하면
그 값이 `StopIteration.value`에 실립니다.
일반 `for`는 이 값을 무시합니다. `yield from`이 받을 때 의미가 있습니다(Part 4).

> 💡 핵심: StopIteration = 종료 신호. for가 삼킨다.

### 1-4. 컴프리헨션·언패킹도 같은 프로토콜

리스트/셋/dict 컴프리헨션, `a, b = pair`, `[*xs, 99]` 전부가
이터레이션 프로토콜을 씁니다.
그래서 **커스텀 이터러블**만 만들면 `for`뿐 아니라
언패킹·컴프리헨션·`list()`·`sum()`에도 바로 들어갑니다.
"한 관약으로 언어 전체가 연결된다"가 Python의 설계 철학입니다.

```python
class Countdown:
    def __init__(self, n):
        self.n = n

    def __iter__(self):
        return self
```

```python
    def __next__(self):
        if self.n <= 0:
            raise StopIteration
        self.n -= 1
        return self.n + 1
```

```python
print(list(Countdown(3)))
# 출력: [3, 2, 1]
a, b, c = Countdown(3)
print(a, b, c)
# 출력: 3 2 1
```

**JS에서는:** 스프레드 `...arr`, 구조 분해도 iterable 프로토콜을 씁니다.
관약 이름은 달라도 "언어가 한 인터페이스에 기대는" 구조는 같습니다.

> 💡 핵심: 커스텀 이터러블 하나면 for·언패킹·sum이 모두 동작한다.

## Part 2. 이터레이터 클래스 vs 제너레이터

### 2-1. 클래스로 이터레이터 만들기

상태를 `__init__`에 두고, `__next__`에서 갱신·반환합니다.
끝나야 할 때 `raise StopIteration`을 합니다.
동작은 명확하지만, 간단한 순회에도 클래스가 길어집니다.
"다음에 무엇을 줄지"를 상태 머신으로 직접 관리하는 셈입니다.

```python
class RangeLike:
    def __init__(self, start, stop):
        self.cur = start
        self.stop = stop

    def __iter__(self):
        return self
```

```python
    def __next__(self):
        if self.cur >= self.stop:
            raise StopIteration
        v = self.cur
        self.cur += 1
        return v
```

```python
print(list(RangeLike(1, 4)))
# 출력: [1, 2, 3]
```

**Django 연결:** 예전 코드·라이브러리에서 이런 클래스를 자주 봅니다.
직접 짤 일은 줄었지만, **읽는** 능력은 필요합니다.

> 💡 핵심: 이터레이터 클래스 = 상태 + __next__ + StopIteration.

### 2-2. 제너레이터 함수: yield가 상태를 저장한다

함수 안에 `yield`가 하나라도 있으면 그 함수는
호출 즉시 **제너레이터 객체**를 반환합니다.
본문은 아직 실행되지 않습니다.
`next()`를 호출할 때마다 `yield`까지 실행하고 값을 넘긴 뒤 **멈춥니다**.
지역 변수·실행 위치가 그대로 보존됩니다.

```python
def count_up(n):
    i = 1
    while i <= n:
        yield i
        i += 1
```

```python
g = count_up(3)
print(next(g), next(g), next(g))
# 출력: 1 2 3
```

클래스 `RangeLike`와 같은 일을 **훨씬 짧게** 합니다.
상태를 필드로 꺼낼 필요 없이, 평범한 지역 변수가 상태입니다.

**JS에서는:** `function*`와 `yield`가 대응합니다.
`const g = countUp(3); g.next().value` 패턴과 같습니다.

> 💡 핵심: yield 있는 함수 = 제너레이터 팩토리. 호출 ≠ 실행.

### 2-3. 제너레이터는 이터레이터다

제너레이터 객체는 `__iter__`와 `__next__`를 이미 갖습니다.
`for`·`list()`에 바로 넣을 수 있습니다.
한 번 소진하면 다시 쓸 수 없습니다.
다시 순회하려면 함수를 **다시 호출**해 새 제너레이터를 만듭니다.

```python
g = count_up(2)
print(list(g))
# 출력: [1, 2]
print(list(g))
# 출력: []
print(list(count_up(2)))
# 출력: [1, 2]
```

**면접 함정:** "제너레이터를 변수에 담아 두 번 `for` 돌렸다" →
두 번째는 빈 결과. 버그가 아니라 **일회용** 특성입니다.

> 💡 핵심: 제너레이터 = 자동 구현된 일회용 이터레이터.

### 2-4. 언제 클래스, 언제 제너레이터?

대부분 **제너레이터 함수**로 충분합니다.
클래스가 나은 경우는 드뭅니다.

- 순회 외에 메서드가 더 필요할 때
  (`send`/`throw`를 감춘 API, 재시작, 통계 조회)
- pickle·복사 등 객체 수명이 길 때
- C 확장·성능 임계 경로(드묾)

실무 기본값: **yield로 쓰고, 막히면 클래스로 올린다.**

> 💡 핵심: 기본은 제너레이터. 상태가 API로 노출될 때만 클래스.

## Part 3. 지연 평가와 메모리

### 3-1. yield는 값을 "지금" 만들지 않는다

리스트 컴프리헨션은 **즉시** 모든 원소를 메모리에 만듭니다.
제너레이터는 `next()`가 올 때까지 다음 값을 계산하지 않습니다.
로그 수백만 줄·API 페이지·대용량 CSV에서
"전부 리스트로 만들기"는 OOM(메모리 부족)의 지름길입니다.

```python
def squares(n):
    for i in range(n):
        yield i * i
```

```python
g = squares(1_000_000)
print(next(g))
# 출력: 0
print(next(g))
# 출력: 1
```

백만 칸 리스트를 만들지 않았습니다.
필요한 만큼만 계산합니다.

**JS에서는:** 보통 배열을 한 번에 만들고,
스트림/`for await`로 지연합니다.
Python은 동기 코드에서도 제너레이터로 같은 패턴이 자연스럽습니다.

> 💡 핵심: 제너레이터 = 필요할 때 한 칸씩 계산 (lazy).

### 3-2. 메모리 비교: list vs generator

같은 수열을 리스트로 만들면 원소 수에 비례해 메모리가 큽니다.
제너레이터 객체 자체는 거의 고정 크기입니다
(프레임·지역 변수만 보관).

```python
import sys

n = 100_000
lst = [i * i for i in range(n)]
gen = (i * i for i in range(n))
```

```python
print(sys.getsizeof(lst))
# 출력: (대략 수백 KB~수 MB)
print(sys.getsizeof(gen))
# 출력: (대략 100~200 바이트)
```

`getsizeof`는 컨테이너 **본체**만 봅니다.
리스트 안의 int 객체까지 합치면 차이는 더 큽니다.
요지는 "크기가 n에 비례하느냐, 상수에 가깝냐"입니다.

> 💡 핵심: 큰 데이터는 list 금지, 제너레이터/이터레이터로.

### 3-3. 제너레이터 표현식

`(식 for x in xs if ...)`는 리스트 컴프리헨션의 **지연** 버전입니다.
대괄호 `[]` 대신 소괄호 `()`를 씁니다.
함수 인자로 넘길 때는 괄호를 생략할 수 있습니다.

```python
evens = (x for x in range(10) if x % 2 == 0)
print(next(evens))
# 출력: 0
print(sum(x * x for x in range(5)))
# 출력: 30
```

리스트가 필요 없는 집계(`sum`·`any`·`max`)에는
제너레이터 표현식이 기본값이어야 합니다.
불필요하게 `sum([x*x for x in ...])`처럼 대괄호를 넣지 마세요.

**JS에서는:** 비슷한 한 줄 문법이 없습니다.
`Array.from`/`map`/`filter`는 보통 중간 배열을 만듭니다.

> 💡 핵심: () 컴프리헨션 = 제너레이터. sum/any에 바로 쓴다.

### 3-4. 파일을 한 줄씩 읽기

텍스트 파일 객체는 **줄 단위 이터러블**입니다.
`for line in f:`는 파일을 통째로 읽지 않습니다.
수 GB 로그도 메모리 상수에 가깝게 처리할 수 있습니다.

```python
def grep(path, needle):
    with open(path, encoding="utf-8") as f:
        for line in f:
            if needle in line:
                yield line.rstrip("\n")
```

```python
# matches = list(grep("app.log", "ERROR"))
# 필요하면 리스트화, 기본은 for로 소비
```

**Django 연결:** 대용량 업로드·내보내기 뷰에서
`StreamingHttpResponse`와 제너레이터를 짝지어
응답 본문을 **청크 단위**로 흘려 보냅니다.

> 💡 핵심: 파일 for-루프 = 줄 단위 이터레이터. read() 남용 금지.

### 3-5. 파이프라인처럼 이어 붙이기

제너레이터는 입력으로 이터러블을 받고
다시 yield하면 **필터/변환 파이프**가 됩니다.
각 단계는 값을 한 개씩 주고받습니다(풀 기반).
중간 리스트가 없습니다.

```python
def lines(path):
    with open(path, encoding="utf-8") as f:
        for line in f:
            yield line.rstrip("\n")
```

```python
def only_error(rows):
    for row in rows:
        if "ERROR" in row:
            yield row
```

```python
def take(n, rows):
    for i, row in enumerate(rows):
        if i >= n:
            break
        yield row

# for row in take(10, only_error(lines("a.log"))):
#     print(row)
```

**CS:** 이는 **풀(pull)** 모델입니다.
소비자가 `next()`로 당겨야 생산자가 움직입니다.
전부 push로 밀어 넣는 방식(한 번에 리스트 적재)과 대비됩니다.

> 💡 핵심: 제너레이터 체이닝 = 메모리 상수 파이프라인.

## Part 4. yield from

### 4-1. 위임: for yield를 한 줄로

하위 이터러블의 값을 그대로 넘겨줄 때
`for x in sub: yield x` 대신 `yield from sub`를 씁니다.
의도가 "이 구간은 하위에 맡긴다"로 분명해지고,
예외·`send`·`return` 값 전파도 올바르게 됩니다.

```python
def concat(a, b):
    yield from a
    yield from b

print(list(concat([1, 2], (3, 4))))
# 출력: [1, 2, 3, 4]
```

단순 위임만 보면 `for`+`yield`와 결과가 같습니다.
차이는 Part 4-3의 **반환값**과 양방향 통신에서 드러납니다.

**JS에서는:** `yield*`가 같은 역할입니다.
`function* concat(a, b) { yield* a; yield* b; }`

> 💡 핵심: yield from = 하위 이터러블에 순회 위임.

### 4-2. 재귀·트리 순회에 특히 유용

중첩 구조를 펼 때 `yield from`이 빛납니다.
직접 스택을 관리하는 이터레이터 클래스보다
재귀 제너레이터가 읽기 쉽습니다.

```python
def flatten(xs):
    for x in xs:
        if isinstance(x, list):
            yield from flatten(x)
        else:
            yield x
```

```python
print(list(flatten([1, [2, [3], 4], 5])))
# 출력: [1, 2, 3, 4, 5]
```

실무에서는 깊이 제한·순환 참조 가드가 필요하지만,
프로토콜 이해용으로는 이 패턴이면 충분합니다.

> 💡 핵심: 중첩 구조 flatten = 재귀 + yield from.

### 4-3. yield from의 반환값

하위가 **제너레이터**이고 `return 값`으로 끝나면,
그 값이 `StopIteration.value`에 실립니다.
`yield from` 표현식은 그 값을 **받아 반환**합니다.
`for`+`yield`로는 이 값을 얻기 어렵습니다.

```python
def tally(xs):
    total = 0
    for x in xs:
        total += x
        yield x
    return total
```

```python
def run(xs):
    result = yield from tally(xs)
    print("sum=", result)
```

```python
print(list(run([1, 2, 3])))
# 출력: sum= 6
# 출력: [1, 2, 3]
```

`list()`가 소비하는 동안 `run` 안에서
`result`에 6이 들어간 뒤 출력됩니다.
하위 제너레이터의 "요약 결과"를 상위로 올리는 공식 경로입니다.

> 💡 핵심: yield from 표현식 값 = 하위 return 값.

### 4-4. Django QuerySet은 이터러블이다

`QuerySet`은 리스트가 아닙니다.
순회·`list()`·슬라이스 시점에 쿼리가 실행되는
**지연 평가** 객체입니다(대략).
오늘 배운 말로 하면 "이터러블 + 실행 계획"에 가깝습니다.

```python
# Django 셸 예시 (개념)
qs = User.objects.filter(is_active=True)
# 아직 DB 조회 없음

for u in qs.iterator():
    process(u)
```

`qs.iterator()`는 결과를 캐시하지 않고
서버 사이드 커서로 **한 줄씩** 가져옵니다.
대량 내보내기에 리스트 컴프리헨션 대신 이터레이터를 쓰라는
가이드가 바로 이 프로토콜 위에 있습니다.

ORM을 지금 깊게 파지는 않습니다.
다만 **"QuerySet ≠ list, 순회가 곧 실행"** 만 기억하세요.

> 💡 핵심: QuerySet은 지연 이터러블. list(qs)는 전부 적재.

## Part 5. CS: 풀 기반 지연 파이프라인

### 5-1. Eager vs Lazy

**Eager:** 입력을 받자마자 전부 변환해 리스트로 붙잡습니다.
구현이 단순하고 인덱싱·길이가 쉽지만, 메모리는 O(n)입니다.
**Lazy:** 소비자가 값을 요청할 때만 다음 원소를 만듭니다.
메모리는 O(1)에 가깝고, 무한 시퀀도 표현 가능합니다.

```python
# eager: 즉시 100만 개
eager = [i * i for i in range(10**6)]

# lazy: 객체만 생성
lazy = (i * i for i in range(10**6))
```

Python의 `range`·파일·제너레이터·(개념적으로) QuerySet이 lazy 쪽입니다.
Node 스트림의 "backpressure로 당기기"와 같은 문제의식입니다.

> 💡 핵심: lazy = 요청될 때까지 계산·적재를 미룬다.

### 5-2. 무한 시퀀스

제너레이터는 **끝나지 않는** 순회도 표현합니다.
`for`에 그대로 넣으면 무한 루프이므로
`take`·`islice`로 상한을 둡니다.

```python
def naturals():
    n = 0
    while True:
        yield n
        n += 1
```

```python
import itertools
print(list(itertools.islice(naturals(), 5)))
# 출력: [0, 1, 2, 3, 4]
```

"모든 자연수"를 리스트로 만들 수 없다는 사실이
지연 평가의 존재 이유를 보여 줍니다.

**JS에서는:** `function*`로 동일한 무한 생성기를 만듭니다.

> 💡 핵심: 무한 시퀀스 = 제너레이터 + 소비 측 상한.

### 5-3. 면접에서 말하는 법

"대용량을 어떻게 처리하나요?" →
① 한 번에 리스트로 모으지 않는다
② 이터레이터/제너레이터로 스트리밍한다
③ 필요 시 청크·DB cursor·`QuerySet.iterator()`를 쓴다
④ 체이닝으로 단계별 변환을 분리한다

이 네 줄이면 Day 6 + Django 실무 연결이 됩니다.

> 💡 핵심: 스트리밍 = 프로토콜 + 지연 + 상수 메모리.

## 연습문제

### 문제 1. 이터레이터 클래스 직접 구현

`Repeater(value, times)`를 이터레이터 클래스로 작성하세요.
`list(Repeater("x", 3))`이 `["x", "x", "x"]`가 되어야 합니다.
`__iter__`와 `__next__`를 모두 구현하세요.

<details>
<summary>정답 보기</summary>

```python
class Repeater:
    def __init__(self, value, times):
        self.value = value
        self.left = times

    def __iter__(self):
        return self
```

```python
    def __next__(self):
        if self.left <= 0:
            raise StopIteration
        self.left -= 1
        return self.value
```

```python
print(list(Repeater("x", 3)))
# 출력: ['x', 'x', 'x']
```

**해설:** `left`가 남은 횟수입니다.
0 이하이면 `StopIteration`, 아니면 값을 주고 카운트를 줄입니다.
`__iter__`가 `self`를 반환하므로 이 객체는 이터레이터이자 이터러블입니다.
한 번 소진된 뒤 다시 `for`를 돌리면 빈 결과가 나옵니다.

</details>

### 문제 2. 제너레이터로 바꾸기

문제 1과 같은 동작을 **제너레이터 함수** `repeater(value, times)`로
다시 작성하세요. 클래스보다 짧아지는지 비교하세요.

<details>
<summary>정답 보기</summary>

```python
def repeater(value, times):
    for _ in range(times):
        yield value

print(list(repeater("x", 3)))
# 출력: ['x', 'x', 'x']
```

**해설:** 루프와 `yield`만으로 상태가 유지됩니다.
`left` 같은 필드를 직접 관리할 필요가 없습니다.
실무에서는 이 형태가 기본입니다.
클래스는 "순회 + 추가 API"가 필요할 때만 올립니다.

</details>

### 문제 3. 제너레이터 파이프라인

문자열 이터러블을 받아

1. 앞뒤 공백을 제거하고
2. 빈 줄을 버리고
3. `'#'`로 시작하는 주석을 버린 뒤
4. 남은 줄만 yield

하는 `clean_lines(rows)`를 작성하세요.

```python
raw = [
    "  a  ",
    "",
    "# comment",
    "b",
]
print(list(clean_lines(raw)))
# 기대: ['a', 'b']
```

<details>
<summary>정답 보기</summary>

```python
def clean_lines(rows):
    for row in rows:
        line = row.strip()
        if not line:
            continue
        if line.startswith("#"):
            continue
        yield line
```

```python
raw = [
    "  a  ",
    "",
    "# comment",
    "b",
]
print(list(clean_lines(raw)))
# 출력: ['a', 'b']
```

**해설:** 각 조건을 `continue`로 걸러 낸 뒤 한 번만 yield합니다.
중간 리스트가 없으므로 파일 객체·네트워크 스트림에도
그대로 연결할 수 있습니다.
단계를 쪼개고 싶다면 `strip_rows` → `drop_empty` → `drop_comments`
제너레이터를 체인으로 연결하면 됩니다.

</details>

### 문제 4. yield from과 반환값

아래 `pair_sum`은 두 값을 yield한 뒤 합을 `return`합니다.
`show`에서 `yield from`으로 합을 받아 출력하도록 빈칸을 채우세요.

```python
def pair_sum(a, b):
    yield a
    yield b
    return a + b
```

```python
def show(a, b):
    # TODO: yield from 위임
    # 합을 total에 담아 출력
    ...
```

```python
print(list(show(2, 3)))
# 기대 출력:
# total= 5
# [2, 3]
```

<details>
<summary>정답 보기</summary>

```python
def pair_sum(a, b):
    yield a
    yield b
    return a + b

def show(a, b):
    total = yield from pair_sum(a, b)
    print("total=", total)
```

```python
print(list(show(2, 3)))
# 출력: total= 5
# 출력: [2, 3]
```

**해설:** `pair_sum`의 `return a + b`는
`StopIteration.value`로 전달됩니다.
`yield from`이 그 값을 표현식 결과로 돌려 주므로
`total`에 5가 들어갑니다.
`for x in pair_sum(...): yield x`로는 이 합을 받기 어렵습니다.
반환값이 필요하면 `yield from`을 쓰세요.

</details>

## 면접 질문

<details>
<summary>Q1. 이터러블과 이터레이터의 차이는 무엇인가요?</summary>

**정의:** 이터러블은 `iter()`로 이터레이터를 만들 수 있는 객체
(`__iter__` 또는 시퀀스 `__getitem__`)입니다.
이터레이터는 `__next__`로 다음 값을 주고,
끝나면 `StopIteration`을 던지는 객체입니다.

**관계:** 이터레이터의 `__iter__`는 보통 `self`를 반환합니다.
그래서 이터레이터는 이터러블이기도 합니다.
반대로 리스트 같은 이터러블은 호출마다 **새** 이터레이터를 만듭니다.

**실무:** "같은 데이터를 여러 번 순회"하려면 이터러블을 보관하고,
매회 `iter()`/`for`로 새 커서를 열어야 합니다.
제너레이터 한 번 소진 후 재순회가 빈 이유입니다.

</details>

<details>
<summary>Q2. 제너레이터와 일반 함수의 차이는? yield는 무엇을 보존하나요?</summary>

**차이:** `yield`가 있는 함수를 호출하면 본문이 실행되지 않고
**제너레이터 객체**가 반환됩니다.
`next()`마다 `yield` 지점까지 실행 후 일시 정지합니다.

**보존:** 실행 프레임, 지역 변수, 명령 포인터(어디까지 실행했는지)가
객체 안에 남습니다. 그래서 클래스 필드 없이도 상태가 유지됩니다.

**종료:** 함수가 끝나면(또는 `return`) `StopIteration`이 납니다.
`return 값`은 `StopIteration.value`에 실립니다.

**JS 대응:** `function*` / `yield`와 동일한 모델입니다.

</details>

<details>
<summary>Q3. 리스트 컴프리헨션 대신 제너레이터 표현식을 쓰는 이유는?</summary>

**메모리:** `[]`는 즉시 전체 리스트를 만듭니다(O(n) 메모리).
`()`는 제너레이터만 만들어 원소를 요청할 때 계산합니다.

**언제 리스트:** 여러 번 순회, 인덱싱, `len`이 필요할 때.

**언제 제너레이터:** `sum`·`any`·`all`·한 번만 순회하는 필터/변환,
대용량 입력. `sum([x*x for x in xs])`처럼 불필요한 대괄호는 피합니다.

**Django:** `list(큰_QuerySet)`은 위험할 수 있습니다.
순회·`iterator()`·집계를 DB/스트림 쪽에 남겨 두세요.

</details>

<details>
<summary>Q4. yield from은 for-yield와 무엇이 다른가요?</summary>

**공통:** 하위 이터러블 값을 상위 소비자에게 그대로 넘깁니다.

**차이:**

1. `yield from` 표현식은 하위 제너레이터의 **`return` 값**을 받습니다.
2. `send`/`throw`가 하위로 올바르게 전파됩니다(코루틴 용도).
3. 의도가 "위임"으로 분명하고 코드가 짧습니다.

**실무:** 단순 이어 붙이기·재귀 flatten·서브 제너레이터 합성에 씁니다.
반환값이 필요 없고 `send`도 없으면 `for`+`yield`도 동작은 같습니다.
다만 습관적으로 `yield from`을 쓰는 편이 안전합니다.

</details>

<details>
<summary>Q5. Django QuerySet이 리스트가 아닌 이유는? iterator()는 언제 쓰나요?</summary>

**이유:** QuerySet은 "쿼리 설계도 + 지연 실행" 객체입니다.
정의 시점에는 SQL을 보내지 않고,
순회·`list()`·슬라이스 등 **평가** 시점에 조회합니다.
항상 리스트면 필터를 이어 붙일 때마다 DB를 치거나
메모리를 낭비하게 됩니다.

**iterator():** 기본 순회는 결과를 QuerySet 캐시에 남깁니다.
같은 QS를 재순회할 때 유리합니다.
반면 한 번만 흘려보내면 되는 대량 작업
(내보내기·일괄 처리)에서는 `iterator()`로
캐시 없이 커서 스트리밍하는 편이 메모리가 덜 듭니다.

**연결:** Day 6의 이터러블/지연 평가 개념이 곧 ORM 사용 감각입니다.

</details>

<details>
<summary>Q6. 무한 제너레이터를 안전하게 소비하는 방법은?</summary>

**문제:** `while True: yield ...`는 `list(g)`나 그냥 `for`에 넣으면
끝나지 않습니다.

**방법:**

- `itertools.islice(g, n)`으로 상한
- 자체 `take(n, g)` 제너레이터
- 종료 조건이 있는 입력을 기다림(센티널·타임아웃)

**설계:** 생산자는 무한을 허용하고,
**소비 측이 경계를 정한다**는 점이 풀 기반 파이프라인의 핵심입니다.
백프레셔·스트리밍 API와 같은 철학입니다.

</details>
