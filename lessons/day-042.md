## 1. 이미지와 레이어 캐시: 줄 순서가 속도다

왜 Docker를 쓸까요? "제 컴퓨터에선 되는데요" 문제 때문입니다. Python 버전, 시스템 라이브러리(libpq), 환경 설정이 서버마다 다르면 같은 코드도 다르게 동작합니다.

**이미지**(image)는 앱과 실행 환경을 통째로 얼린 **읽기 전용 스냅샷**입니다. **컨테이너**(container)는 그 이미지를 실행한 **프로세스**입니다. 클래스와 인스턴스 관계와 비슷합니다.

**비유:** 이미지는 밀키트, 컨테이너는 그 밀키트로 끓인 한 냄비입니다. 같은 밀키트면 어느 주방에서도 같은 맛이 납니다.

Dockerfile의 각 줄은 **레이어**(layer, 변경분을 쌓은 층)가 됩니다. Docker는 줄의 입력이 그대로면 예전 레이어를 **재사용**합니다. 한 줄이 바뀌면 **그 아래 줄은 전부 다시** 만듭니다.

**결과를 맞혀 보세요:** 아래 Dockerfile에서 \`views.py\` 한 줄만 고치고 다시 빌드하면, \`pip install\`은 다시 돌까요?

\`\`\`dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["gunicorn", "config.wsgi"]
\`\`\`

<details>
<summary>정답</summary>

**네, 매번 다시 돕니다.** \`COPY . .\`가 코드 전체를 복사하니, \`views.py\`가 바뀌면 이 레이어가 바뀝니다. 그 아래 \`pip install\`도 캐시가 깨져 수십 초~수 분을 다시 씁니다.

</details>

해결책은 **잘 안 바뀌는 것을 위로** 올리는 것입니다. 의존성 목록만 먼저 복사해 설치하고, 코드는 마지막에 복사합니다.

\`\`\`dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["gunicorn", "config.wsgi"]
\`\`\`

Node에서 이미 해 본 패턴입니다. \`package.json\`을 먼저 복사하는 바로 그 이유입니다.

**JS (Node)**

\`\`\`javascript
// Dockerfile (Node)
// COPY package*.json ./
// RUN npm ci
// COPY . .
// CMD ["node", "server.js"]
\`\`\`

**Python**

\`\`\`bash
# Dockerfile (Django)
# COPY requirements.txt .
# RUN pip install -r requirements.txt
# COPY . .
\`\`\`

![레이어 캐시](assets/gif/day42-layers.gif)

캐시 규칙을 직접 돌려 봅시다. 바뀐 줄부터 아래가 전부 다시 빌드됩니다.

\`\`\`python-run
steps = ["FROM py", "COPY req", "RUN pip",
         "COPY code", "CMD"]
changed = "COPY code"
hit = True
for s in steps:
    hit = hit and s != changed
    print(s, "캐시" if hit else "다시 빌드")
\`\`\`

\`changed\`를 \`"COPY req"\`로 바꿔 보세요. 의존성을 추가할 때만 \`pip\`이 다시 돕니다.

하나 더: \`.dockerignore\`가 없으면 \`.git\`, \`venv\`, \`db.sqlite3\`까지 이미지로 들어갑니다. 이미지가 커지고, 쓸데없는 파일 변경에도 캐시가 깨집니다.

\`\`\`bash
# .dockerignore
.git
venv/
__pycache__/
*.sqlite3
.env
\`\`\`

> 💡 Dockerfile은 **잘 안 바뀌는 것 → 자주 바뀌는 것** 순서로. 한 줄이 바뀌면 그 아래는 전부 다시 빌드된다.

## 2. 멀티스테이지 빌드: 공구는 두고 가구만 싣는다

\`psycopg\`나 \`Pillow\` 같은 패키지는 설치할 때 **컴파일러**(gcc)와 헤더 파일이 필요할 때가 있습니다. 그런데 실행할 때는 필요 없습니다. 공구까지 이미지에 실으면 수백 MB가 늘고, 공격자가 쓸 도구도 늘어납니다.

**멀티스테이지 빌드**(multi-stage build)는 Dockerfile 안에 \`FROM\`을 여러 번 씁니다. 앞 단계에서 만들고, 마지막 단계에는 **결과물만 복사**합니다.

**비유:** 공방에서 가구를 만든 뒤, 트럭에는 **가구만** 싣습니다. 톱과 대패는 공방에 두고 갑니다.

**결과를 맞혀 보세요:** 아래 두 단계 중 최종 이미지에 \`gcc\`가 들어 있을까요?

\`\`\`dockerfile
FROM python:3.12 AS builder
COPY requirements.txt .
RUN pip wheel -r requirements.txt \
    -w /wheels
\`\`\`

\`\`\`dockerfile
FROM python:3.12-slim
COPY --from=builder /wheels /wheels
RUN pip install --no-cache-dir \
    /wheels/*
RUN useradd -m app
USER app
\`\`\`

<details>
<summary>정답</summary>

**없습니다.** 최종 이미지는 **마지막 \`FROM\`부터** 만들어집니다. builder 단계(gcc가 있는 큰 이미지)는 빌드가 끝나면 버려집니다. \`COPY --from=builder\`로 가져온 \`/wheels\`(미리 빌드한 패키지 파일)만 남습니다.

</details>

\`USER app\`도 중요합니다. 기본값은 **root**로 실행입니다. 앱에 구멍이 뚫리면 컨테이너 안에서 root 권한을 줍니다. 일반 사용자로 내려 피해 범위를 줄입니다.

**JS (Node)**

\`\`\`javascript
// FROM node:20 AS build
// RUN npm ci && npm run build
// FROM node:20-slim
// COPY --from=build /app/dist ./dist
\`\`\`

**Python**

\`\`\`bash
# FROM python:3.12 AS builder
# RUN pip wheel ... -w /wheels
# FROM python:3.12-slim
# COPY --from=builder /wheels /wheels
\`\`\`

Node는 보통 **번들된 dist**를 옮기고, Python은 **빌드된 wheel**(또는 가상환경 폴더)을 옮깁니다. 원리는 같습니다.

\`\`\`mermaid
flowchart LR
  A[builder<br/>python:3.12<br/>gcc 포함] -->|wheels만| B[runtime<br/>python:3.12-slim]
  A -.버려짐.-> X[ ]
  B --> C[최종 이미지]
\`\`\`

> 💡 멀티스테이지 = **만드는 이미지와 실행하는 이미지를 분리**. 작고, 빠르고, 공격 표면이 좁다.

<details>
<summary>🔍 더 깊이 (면접용)</summary>

- **컨테이너 ≠ VM**: VM은 하드웨어를 흉내 내고 **커널을 따로** 띄웁니다. 컨테이너는 호스트 커널을 **공유**하고, 리눅스 **namespace**(보이는 범위 격리: PID·네트워크·파일시스템)와 **cgroups**(CPU·메모리 제한)로 격리한 프로세스일 뿐입니다. 그래서 1초 안에 뜨지만, 격리는 VM보다 약합니다.
- **레이어 = 유니온 파일시스템**: overlayfs가 읽기 전용 레이어들 위에 쓰기 레이어 하나를 얹습니다. 컨테이너를 지우면 쓰기 레이어도 사라지니, **DB 데이터는 반드시 볼륨**에 둡니다.
- **PID 1과 시그널**: \`CMD gunicorn ...\`(shell form)은 \`/bin/sh -c\`가 PID 1이 되어 **SIGTERM을 gunicorn에 전달하지 않을** 수 있습니다. 배포 때 graceful shutdown이 안 되고 10초 뒤 SIGKILL을 맞습니다. **exec form** \`CMD ["gunicorn", ...]\`을 쓰세요.
- **slim vs alpine**: alpine은 glibc 대신 **musl**을 써서 많은 Python wheel을 못 쓰고 소스 컴파일로 빌드가 느려집니다. Python은 보통 \`-slim\`(Debian)이 무난합니다.
- **ENV 두 개**: \`PYTHONUNBUFFERED=1\`(로그가 버퍼에 갇히지 않고 바로 출력), \`PYTHONDONTWRITEBYTECODE=1\`(.pyc 안 씀).

</details>

## 3. docker compose: 서비스 이름이 곧 주소

Goals는 컨테이너 5개가 필요합니다. nginx, web(gunicorn), worker(Celery), db(Postgres), redis. 하나씩 \`docker run\`하면 네트워크·볼륨·순서를 손으로 맞춰야 합니다. **compose**는 이것을 YAML 한 파일에 선언합니다.

**비유:** 밴드 공연 큐시트입니다. 누가 어떤 악기(이미지)를 들고, 어떤 순서로 무대에 오르는지 한 장에 적어 둡니다.

\`\`\`mermaid
flowchart LR
  U[브라우저] --> N[nginx:80]
  N --> W[web<br/>gunicorn]
  W --> D[(db<br/>postgres)]
  W --> R[(redis)]
  K[worker<br/>celery] --> R
  K --> D
\`\`\`

먼저 DB입니다. 데이터는 **이름 있는 볼륨**에 둬야 컨테이너를 지워도 남습니다.

\`\`\`yaml
services:
  db:
    image: postgres:16
    env_file: .env
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD", "pg_isready"]
\`\`\`

web과 worker는 **같은 이미지**를 쓰고 명령만 다릅니다.

\`\`\`yaml
  web:
    build: .
    env_file: .env
    depends_on:
      db:
        condition: service_healthy
  worker:
    build: .
    command: celery -A config worker
\`\`\`

**결과를 맞혀 보세요:** web 컨테이너 안의 Django가 \`HOST="localhost"\`로 Postgres에 접속하면?

<details>
<summary>정답</summary>

**연결 거부**(connection refused)입니다. 컨테이너마다 **자기만의 localhost**가 있습니다. web의 localhost에는 Postgres가 없습니다. compose는 서비스들을 한 네트워크에 묶고 **서비스 이름을 DNS 이름**으로 등록하므로 \`HOST="db"\`라고 써야 합니다.

</details>

\`\`\`python
# settings.py
DATABASES = {"default": {
    "ENGINE": "django.db.backends.postgresql",
    "HOST": os.environ.get("DB_HOST", "db"),
    "NAME": os.environ["POSTGRES_DB"],
}}
\`\`\`

\`depends_on\`만 쓰면 **"db 컨테이너가 시작됨"**까지만 기다립니다. Postgres가 실제로 접속을 받기까지는 몇 초 더 걸립니다. 그래서 \`healthcheck\` + \`condition: service_healthy\`로 **준비 완료**까지 기다리게 합니다.

**JS (Node)**

\`\`\`javascript
// 같은 compose, Node 앱이면
// DATABASE_URL=postgres://u:p@db:5432/goals
// 호스트 이름은 똑같이 'db'
\`\`\`

**Python**

\`\`\`bash
# 로컬에서 실행
docker compose up -d --build
docker compose exec web \
  python manage.py migrate
docker compose logs -f web
\`\`\`

> 💡 compose 안에서 **서비스 이름 = 호스트 이름**. \`depends_on\`은 시작 순서만, 준비 완료는 healthcheck로.

<details>
<summary>🔍 더 깊이 (면접용)</summary>

- **migrate는 어디서?** web 시작 스크립트에 넣으면 web을 3개로 늘렸을 때 **동시에 3번** 돕니다. 운영에선 배포 파이프라인의 **일회성 작업**(release job, \`docker compose run --rm web python manage.py migrate\`)으로 분리하는 편이 안전합니다.
- **volume vs bind mount**: 이름 있는 볼륨(\`pgdata:\`)은 Docker가 관리하는 저장소, bind mount(\`./src:/app\`)는 호스트 폴더를 그대로 꽂은 것입니다. 개발 땐 bind mount로 코드 핫리로드, 운영 땐 이미지에 코드를 굽습니다.
- **비밀값**: \`.env\`는 이미지에 \`COPY\`하지 말고 실행 시 주입합니다(\`env_file\`, 운영은 Secret Manager). \`docker history\`로 이미지 레이어에서 비밀이 그대로 보이기 때문입니다.
- **포트 노출**: db·redis에 \`ports:\`를 열지 마세요. 내부 네트워크로 충분하고, 열면 외부에서 6379(인증 없는 Redis)를 두드릴 수 있습니다. 외부에는 nginx 80/443만.

</details>

## 연습문제

**1.** 아래 Dockerfile은 코드 한 줄만 바꿔도 빌드가 3분 걸립니다. 고쳐 보세요.

\`\`\`dockerfile
FROM python:3.12-slim
COPY . /app
WORKDIR /app
RUN pip install -r requirements.txt
\`\`\`

<details>
<summary>정답</summary>

\`\`\`dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir \
    -r requirements.txt
COPY . .
\`\`\`

**해설:** 의존성 목록만 먼저 복사해 설치 레이어를 만들면, 코드 변경 시 \`pip install\` 레이어는 캐시에서 재사용됩니다. \`--no-cache-dir\`은 pip 다운로드 캐시를 이미지에 남기지 않아 크기를 줄입니다. \`.dockerignore\`로 \`.git\`·\`venv\`도 빼 주세요.

</details>

**2.** Goals에 Celery **beat**(정기 작업 스케줄러, Day 38) 서비스를 추가하세요. 이미지는 새로 만들지 않습니다.

<details>
<summary>정답</summary>

\`\`\`yaml
  beat:
    build: .
    env_file: .env
    command: celery -A config beat
    depends_on:
      - redis
\`\`\`

**해설:** web·worker와 **같은 Dockerfile**을 쓰고 \`command\`만 바꿉니다. 코드가 한 이미지에 있으니 버전이 어긋날 일이 없습니다. beat는 **반드시 1개만** 띄웁니다. 2개면 같은 정기 작업이 두 번 큐에 들어갑니다.

</details>

**3.** \`docker compose up\` 직후 web 로그에 \`could not connect to server: Connection refused (localhost:5432)\`가 뜹니다. 원인 두 가지와 해결책은?

<details>
<summary>정답</summary>

① **HOST가 localhost**: 컨테이너의 localhost엔 Postgres가 없습니다. \`DB_HOST=db\`(서비스 이름)로 바꿉니다.

② **아직 준비 안 됨**: HOST가 맞아도 Postgres가 초기화 중일 수 있습니다. db에 \`healthcheck\`를 두고 web에 \`condition: service_healthy\`를 겁니다.

\`\`\`yaml
    depends_on:
      db:
        condition: service_healthy
\`\`\`

**해설:** 운영에선 DB가 잠깐 끊겨도 앱이 **재시도**해야 하므로, \`restart: unless-stopped\`나 접속 재시도 로직을 함께 둡니다.

</details>

## 면접 질문

<details>
<summary>Q1. 컨테이너와 가상 머신(VM)의 차이는?</summary>

**모범 답안:**

- **VM**은 하이퍼바이저 위에 **게스트 OS 커널**을 통째로 띄웁니다. 격리가 강하지만 무겁고(GB 단위), 부팅이 느립니다.
- **컨테이너**는 호스트 **커널을 공유**하는 격리된 프로세스입니다. namespace로 보이는 것(PID·네트워크·마운트)을 나누고, cgroups로 CPU·메모리를 제한합니다. MB 단위로 가볍고 1초 안에 뜹니다.
- **트레이드오프**: 커널을 공유하니 커널 취약점에 함께 노출됩니다. 그래서 non-root 실행, 읽기 전용 파일시스템, 불필요한 권한(capability) 제거 같은 하드닝을 합니다. 멀티테넌트 강격리가 필요하면 gVisor·Firecracker 같은 경량 VM을 씁니다.

</details>

<details>
<summary>Q2. Django 이미지를 작고 빠르게 빌드하는 방법을 설명해 주세요.</summary>

**모범 답안:**

- **레이어 캐시**: \`requirements.txt\`를 먼저 복사해 설치하고 코드는 마지막에. 코드 변경 시 의존성 레이어를 재사용합니다.
- **멀티스테이지**: gcc·헤더가 있는 builder에서 wheel을 만들고, \`-slim\` 런타임에 결과물만 복사합니다.
- **불필요한 파일 제외**: \`.dockerignore\`(.git, venv, .env), \`pip --no-cache-dir\`, apt 사용 후 \`rm -rf /var/lib/apt/lists/*\`.
- **보안·운영**: \`USER\`로 non-root 실행, exec form \`CMD\`로 SIGTERM을 gunicorn이 직접 받게 해 graceful shutdown, 비밀값은 이미지에 굽지 않고 실행 시 주입.
- 결과적으로 1GB 넘던 이미지가 보통 150~250MB 수준으로 줄고, 코드만 바뀐 빌드는 수 초에 끝납니다.
