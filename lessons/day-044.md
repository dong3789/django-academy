**1.** (Day 43) 이 코드는 무엇을 출력할까요? `os.environ["DEBUG"] = "False"` 다음에 `print(bool(os.environ["DEBUG"]))`.

<details>
<summary>정답</summary>

**True**입니다. 환경변수는 항상 문자열이고, 비어 있지 않은 문자열은 모두 참입니다. 그래서 `== "True"`처럼 **직접 비교**하거나 `env_bool()` 같은 함수로 바꿉니다.

</details>

**2.** (Day 43) `/healthz`가 DB까지 확인해야 할까요? liveness와 readiness의 차이로 답해 보세요.

<details>
<summary>정답</summary>

**liveness**(살아 있나?)는 프로세스만 확인합니다. 실패하면 플랫폼이 컨테이너를 **재시작**합니다. **readiness**(손님 받을 준비 됐나?)는 DB 연결까지 확인합니다. 실패하면 **트래픽만 빼고** 재시작하지 않습니다.

DB가 잠깐 죽었다고 liveness가 실패하면, 멀쩡한 웹 컨테이너가 전부 재시작되는 연쇄 장애가 납니다. 그래서 둘을 나눕니다.

</details>

**3.** (Day 42) `CMD gunicorn ...`(shell form)보다 `CMD ["gunicorn", ...]`(exec form)을 쓰는 이유는?

<details>
<summary>정답</summary>

exec form이면 gunicorn이 **PID 1**이 되어 `docker stop`의 **SIGTERM**을 직접 받습니다. 그래서 처리 중인 요청을 마치고 깔끔하게 내려갑니다(graceful shutdown).

shell form은 `/bin/sh -c`가 PID 1이 됩니다. sh는 신호를 자식에게 넘기지 않아, 10초 뒤 SIGKILL로 강제 종료됩니다. 오늘 배울 **롤링 배포**에서 이 차이가 요청 끊김으로 드러납니다.

</details>

## 1. 어디에 올릴까: 서버를 빌리는 세 가지 방법

지금까지 Goals는 내 컴퓨터의 compose 안에서만 돌았습니다. 인터넷에 올리려면 **24시간 켜진 컴퓨터**, **고정된 주소**, **HTTPS**, **DB**가 필요합니다. 이걸 얼마나 직접 챙길지에 따라 선택지가 갈립니다.

| 방식 | 내가 챙길 것 | 예 |
|---|---|---|
| IaaS (가상 서버) | OS·nginx·TLS·전부 | AWS EC2 |
| 컨테이너 서비스 | 이미지·설정 | ECS Fargate, Cloud Run |
| PaaS | 코드(또는 이미지)만 | Fly.io, Render |

**IaaS**(Infrastructure as a Service)는 빈 컴퓨터를 빌리는 것이고, **PaaS**(Platform as a Service)는 실행 환경까지 빌리는 것입니다. 첫 배포는 PaaS가 좋습니다. Day 42에서 만든 Dockerfile을 그대로 받아 주기 때문입니다.

**비유:** IaaS는 빈 상가 임대(인테리어·전기 공사 직접), PaaS는 푸드코트 입점(자리·전기·결제기는 제공, 나는 요리만)입니다.

**결과를 맞혀 보세요:** 로컬에선 잘 되던 Goals를 배포했습니다. 컨테이너 시작 명령이 `gunicorn goals.wsgi -b 127.0.0.1:8000`입니다. 접속하면?

<details>
<summary>정답</summary>

**연결 실패**(Fly는 "앱이 포트를 듣고 있지 않다"는 경고, 브라우저는 502)입니다. `127.0.0.1`은 **컨테이너 자기 자신**만 받는 주소입니다. 플랫폼의 프록시는 컨테이너 **밖**에서 들어오므로 닿지 않습니다.

`-b 0.0.0.0:8000`으로 "모든 네트워크 카드에서 받기"로 바꿔야 합니다. Node에서 `app.listen(8000, "127.0.0.1")`로 띄웠을 때와 똑같은 함정입니다.

</details>

Fly.io에선 설정 파일 하나가 배포 방법을 정합니다.

```bash
fly launch --no-deploy
KEY=$(openssl rand -base64 48)
fly secrets set SECRET_KEY="$KEY"
fly secrets set ALLOWED_HOSTS=goals.fly.dev
```

`fly launch`는 `fly.toml`을 만들고, `fly secrets set`은 Day 43에서 만든 환경변수를 **암호화 저장소**에 넣습니다. 비밀값은 `fly.toml`(git에 올라감)에 쓰지 않습니다.

```toml
app = "goals"
primary_region = "nrt"

[http_service]
  internal_port = 8000
  force_https = true
```

`internal_port`는 "컨테이너 안에서 gunicorn이 듣는 포트"입니다. 바깥 443은 Fly 프록시가 받아 TLS를 끝내고(Day 41의 nginx 역할), 8000으로 넘깁니다.

DB는 플랫폼의 Postgres를 붙이면 `DATABASE_URL` 비밀값이 주입됩니다. 이 URL 한 줄을 Django 설정으로 풀어 봅시다.

```python-run
from urllib.parse import urlparse
u = urlparse("postgres://"
  "goals:pw@db.internal:5432/goals")
print(u.username, u.hostname, u.port)
print(u.path.lstrip("/"))
# 출력: goals db.internal 5432
# 출력: goals
```

**JS (Node)**

```javascript
// PORT·DATABASE_URL을 env로 받음
const port = process.env.PORT ?? 8000;
app.listen(port, "0.0.0.0");
const db = new Pool({
  connectionString:
    process.env.DATABASE_URL });
```

**Python**

```python
# pip install dj-database-url
import dj_database_url
DATABASES = {"default":
  dj_database_url.config(
    conn_max_age=60)}
```

`dj-database-url`은 위의 `urlparse` 작업을 대신해 주는 작은 라이브러리입니다. `conn_max_age=60`은 DB 연결을 60초 재사용하라는 뜻입니다(아래 접기 참고).

> 💡 첫 배포는 PaaS로. 0.0.0.0에 바인딩하고, 비밀값은 secrets로, DB는 DATABASE_URL 한 줄로.

<details>
<summary>🔍 더 깊이 (면접용)</summary>

**conn_max_age와 연결 수 한계**

기본값 0이면 요청마다 DB 연결을 새로 엽니다. TCP+TLS+인증 왕복이 매번 붙습니다. `CONN_MAX_AGE`로 재사용하면 빨라지지만, **연결 수 = 머신 수 × 워커 수 × 스레드 수**로 늘어납니다. 작은 Postgres는 최대 연결이 수십 개라 금방 찹니다. 그래서 **PgBouncer**(연결 풀러)를 앞에 두거나, Django 5.1+의 psycopg 풀(`OPTIONS: {"pool": True}`)을 씁니다.

`CONN_HEALTH_CHECKS = True`(4.1+)를 켜면 재사용 전에 끊긴 연결인지 확인해, DB 재시작 직후 첫 요청이 500 나는 것을 막습니다.

</details>

## 2. 배포 순서: migrate는 먼저, 그리고 호환되게

새 버전에 모델 변경이 있다고 합시다. 순서는 셋 중 하나입니다.

- 코드 먼저: 새 코드가 **없는 컬럼**을 찾다 500
- migrate 먼저: 옛 코드가 **바뀐 테이블**을 만남

정답은 **migrate 먼저, 단 옛 코드가 버틸 수 있게**입니다. 롤링 배포 중엔 옛 버전과 새 버전이 **몇 분간 함께** 돕니다. 그래서 마이그레이션은 양쪽 모두와 호환돼야 합니다.

Fly에선 `release_command`가 이 "먼저"를 맡습니다. 새 이미지로 **임시 머신**을 띄워 migrate를 돌리고, 성공해야 교체를 시작합니다. 실패하면 배포 전체가 멈추고 옛 버전이 그대로 남습니다.

```toml
[deploy]
release_command = "python manage.py migrate"
```

**비유:** 영업 중인 식당의 메뉴판 교체입니다. 새 메뉴 재료(컬럼)를 먼저 들여놓고, 메뉴판(코드)을 바꾸고, 옛 재료는 다 팔린 다음에 치웁니다.

**결과를 맞혀 보세요:** Goal의 `title` 필드 이름을 `name`으로 바꾸고 한 번에 배포했습니다. migrate가 먼저 돌았고, 아직 교체 안 된 v1 머신이 목록을 읽습니다.

```python-run
row = {"id": 1, "name": "피아노 30분"}
def v1_render(r):
    return r["title"]
try:
    print(v1_render(row))
except KeyError as e:
    print("500 에러:", e)
```

<details>
<summary>정답</summary>

`500 에러: 'title'`이 출력됩니다. migrate가 컬럼 이름을 이미 바꿨는데, v1 코드는 여전히 `title`을 찾습니다. 교체가 끝날 때까지 v1 머신으로 간 요청은 전부 실패합니다.

</details>

해결은 **expand → migrate → contract**(늘리고, 옮기고, 줄이기) 3단계입니다. 배포 한 번에 끝내지 않고 나눠서 냅니다.

| 배포 | DB | 코드 |
|---|---|---|
| 1. expand | `name` 추가(null 허용) | 둘 다 씀, `title` 읽음 |
| 2. migrate | 데이터 복사 | `name` 읽음 |
| 3. contract | `title` 삭제 | `title` 안 씀 |

어느 단계든 **바로 앞 버전 코드와 같은 DB에서 함께 돌 수 있습니다.** 이게 무중단의 조건입니다.

**JS (Node)**

```javascript
// Procfile (Heroku 계열)
// release: npx prisma migrate deploy
// web: node server.js
```

**Python**

```bash
# Procfile 버전
# release: python manage.py migrate
# web: gunicorn goals.wsgi -b 0.0.0.0:$PORT
```

도구만 다를 뿐 개념은 같습니다. "웹 프로세스를 띄우기 전에 한 번만 도는 release 단계"입니다.

> 💡 migrate는 release 단계에서 먼저. 컬럼 삭제·이름 변경은 expand → contract로 배포를 나눈다.

<details>
<summary>🔍 더 깊이 (면접용)</summary>

**왜 migrate를 컨테이너 시작 명령에 넣으면 안 되나?**

`CMD migrate && gunicorn`이면 머신 3대가 **동시에** migrate를 돌립니다. Django는 마이그레이션 테이블에 기록하지만 분산 락은 없어서, 같은 마이그레이션이 경쟁하거나 하나가 실패해 그 머신만 죽습니다. 마이그레이션은 **일회성 작업 하나**로 돌려야 합니다(Day 42 compose의 migrate 서비스와 같은 생각).

**락 주의: 큰 테이블의 마이그레이션**

- Postgres에서 `NOT NULL` + 기본값 추가는 11+부터 빠르지만, 인덱스 생성은 테이블에 쓰기 락을 겁니다. 큰 테이블은 `AddIndexConcurrently`(`atomic = False` 필요)를 씁니다.
- 긴 마이그레이션이 락을 잡는 동안 웹 요청이 줄줄이 대기 → 타임아웃 → 장애. `lock_timeout`을 짧게 걸고 실패하면 재시도하는 편이 안전합니다.
- `RunPython`으로 대량 데이터 복사는 배치로 나누거나, 마이그레이션 밖 관리 명령으로 돌립니다.

**롤백과 마이그레이션:** 코드는 되돌리기 쉽지만 삭제한 컬럼의 데이터는 못 돌립니다. expand-contract는 롤백 안전장치이기도 합니다.

</details>

## 3. 도메인·HTTPS·헬스체크·롤백

`goals.fly.dev`로 열리면 이제 내 도메인을 붙입니다. 흐름은 "DNS가 주소를 알려 주고 → 플랫폼이 인증서를 발급하고 → 헬스체크를 통과한 머신만 손님을 받는다"입니다.

```bash
fly certs add goals.yndl.dev
# DNS에 CNAME 추가:
# goals → goals.fly.dev
fly certs show goals.yndl.dev
```

**DNS**(Domain Name System)는 이름을 주소로 바꾸는 전화번호부입니다. **CNAME**은 "이 이름은 저 이름과 같다"는 별명 기록입니다. DNS가 퍼지면 플랫폼이 **Let's Encrypt**(무료 인증서 발급 기관)로 TLS 인증서를 자동 발급·갱신합니다.

새 도메인을 Day 43 설정에도 넣어야 합니다. 안 넣으면 400(Host)이나 403(CSRF)이 납니다. 여러 개면 쉼표로 잇습니다.

```bash
fly secrets set \
  ALLOWED_HOSTS=goals.yndl.dev \
  CSRF_TRUSTED_ORIGINS=https://goals.yndl.dev
```

이제 **헬스체크**입니다. 플랫폼은 새 머신을 띄운 뒤 `/healthz`가 200을 줄 때까지 트래픽을 보내지 않습니다. 실패하면 교체를 멈춥니다.

```toml
[[http_service.checks]]
  path = "/healthz"
  interval = "10s"
  timeout = "2s"
  grace_period = "15s"
```

`grace_period`는 "켜지는 동안은 봐주는 시간"입니다. Django가 import를 마치기 전에 검사하면 멀쩡한 머신도 실패로 찍힙니다.

![롤링 배포: 검사 통과한 것만 투입](assets/gif/day44-rolling.gif)

**결과를 맞혀 보세요:** 머신 3대를 하나씩 교체합니다. v2가 두 번째 머신에서 헬스체크에 실패하면?

```python-run
def deploy(machines, healthy):
    for i in range(len(machines)):
        if not healthy(i):
            return f"중단: {machines}"
        machines[i] = "v2"
    return f"완료: {machines}"
print(deploy(["v1"] * 3, lambda i: i != 1))
```

<details>
<summary>정답</summary>

`중단: ['v2', 'v1', 'v1']`입니다. 첫 머신은 이미 v2로 바뀌었고, 실패 지점에서 멈춥니다. 나머지는 v1으로 계속 서비스합니다. 장애는 없지만 **버전이 섞인** 상태이므로 원인을 고쳐 다시 배포하거나 롤백합니다. 2장에서 본 "두 버전이 함께 도는" 상황이 바로 이것입니다.

</details>

되돌리기는 **이전 이미지로 다시 배포**하는 것입니다. 이미지가 불변이라 "어제 그 상태"가 정확히 돌아옵니다.

```bash
fly releases --image
fly deploy --image \
  registry.fly.io/goals:deployment-01J...
```

교체될 머신은 SIGTERM을 받습니다. 처리 중인 요청을 마치고 내려가야 롤링 중 끊김이 없습니다.

**JS (Node)** — 직접 짜야 합니다.

```javascript
process.on("SIGTERM", () => {
  server.close(() => process.exit(0));
});
```

**Python** — gunicorn이 대신합니다. exec form으로 띄우기만 하면 됩니다.

```bash
gunicorn goals.wsgi -b 0.0.0.0:8000 \
  --graceful-timeout 20
```

> 💡 도메인은 CNAME + 자동 인증서, 새 도메인은 ALLOWED_HOSTS·CSRF에도. 헬스체크가 나쁜 배포를 막고, 롤백은 이전 이미지로.

<details>
<summary>🔍 더 깊이 (면접용)</summary>

**배포 전략 셋**

- **롤링**: 하나씩 교체. 추가 비용 없음, 대신 두 버전이 섞임.
- **블루/그린**: 새 세트(그린)를 통째로 띄우고 LB를 한 번에 전환. 롤백이 LB 전환 한 번이라 빠름. 리소스 2배.
- **카나리**: 트래픽 1~5%만 새 버전으로, 에러율·지연(Day 43의 RED 지표)을 보고 늘림. 가장 안전, 가장 복잡.

어느 전략이든 **DB는 하나**라서 expand-contract가 필요합니다.

**Cloudflare 앞에 둘 때의 함정**

Cloudflare 프록시(주황 구름)를 켜고 SSL 모드를 **Flexible**로 두면, Cloudflare→서버 구간이 HTTP가 됩니다. 서버의 `force_https`나 `SECURE_SSL_REDIRECT`가 다시 HTTPS로 보내고, 무한 리다이렉트가 납니다. **Full (strict)**로 두어야 합니다.

**LB 헬스체크와 L4/L7**

L4(TCP) 검사는 "포트가 열렸나"만 봐서, 앱이 500만 내도 통과합니다. L7(HTTP)은 경로와 상태 코드를 봅니다. 함정: LB가 Host에 내부 IP를 넣으면 `ALLOWED_HOSTS`에 걸려 검사만 400으로 실패합니다.

</details>

```toml
[[http_service.checks]]
  path = "/healthz"
  interval = "10s"
  timeout = "2s"
  grace_period = "15s"
```

Dockerfile의 시작 명령도 `CMD ["gunicorn", "goals.wsgi", "-b", "0.0.0.0:8000"]`로 맞춥니다.

**해설:** `release_command`는 웹 머신이 아니라 임시 머신에서 **한 번만** 돌아 동시 migrate를 피합니다. 바인딩은 `0.0.0.0`, 시작 명령은 exec form이라 SIGTERM을 직접 받습니다. 비밀값은 이 파일이 아니라 `fly secrets set`으로 넣습니다.

</details>

**2.** Goal 모델의 `title`을 `name`으로 바꾸려 합니다. 무중단으로 하려면 배포를 몇 번, 어떻게 나눠야 할까요? 각 단계의 모델 코드를 쓰세요.

<details>
<summary>정답</summary>

**세 번**으로 나눕니다.

**배포 1 (expand):** 새 컬럼 추가, 쓰기는 둘 다.

```python
class Goal(models.Model):
    title = models.CharField(max_length=100)
    name = models.CharField(
        max_length=100, null=True)
    def save(self, *a, **kw):
        self.name = self.title
        super().save(*a, **kw)
```

**배포 2 (migrate):** 데이터 복사 + 읽기를 `name`으로.

```python
def copy(apps, schema_editor):
    Goal = apps.get_model("goals", "Goal")
    Goal.objects.filter(name__isnull=True
        ).update(name=F("title"))
# operations에 RunPython(copy) 추가
```

`save()`는 반대로 `self.title = self.name`으로 바꿔 **옛 컬럼에도 계속 씁니다.** 배포 1 코드와 함께 돌아도 데이터가 맞습니다.

**배포 3 (contract):** `title` 필드와 `save()` 동기화를 지우고, `name`을 `null=False`로 바꿉니다.

**해설:** 어느 배포든 **바로 앞 버전 코드가 새 DB에서 문제없이 돕니다.** `RenameField` 한 번이면 롤링 중인 v1이 500을 냅니다(2장 예측). 1·2를 합치기도 하지만 3(삭제)은 반드시 따로 냅니다. `F`는 `django.db.models`에서 가져옵니다.

</details>

**3.** 배포 직후 브라우저에서 "리디렉션한 횟수가 너무 많습니다"가 뜹니다. 구성은 Cloudflare(프록시 켬) → Fly → gunicorn이고, Django엔 `SECURE_SSL_REDIRECT = True`입니다. 원인 후보와 확인 방법은?

<details>
<summary>정답</summary>

**원인 후보 ①:** Cloudflare SSL 모드가 **Flexible**. Cloudflare가 서버로 HTTP로 보내니, 서버는 계속 HTTPS로 보냅니다. → **Full (strict)**로 바꿉니다.

**원인 후보 ②:** Django가 HTTPS를 모름. 프록시가 TLS를 끝냈는데 `SECURE_PROXY_SSL_HEADER`가 없어서, Django가 모든 요청을 HTTP로 보고 리다이렉트합니다.

```python
SECURE_PROXY_SSL_HEADER = (
    "HTTP_X_FORWARDED_PROTO", "https")
```

**확인 방법:** 리다이렉트를 따라가지 않고 응답 헤더만 봅니다.

```bash
curl -sI https://goals.yndl.dev | \
  grep -iE "^(HTTP|location|server)"
```

`location`이 자기 자신(https)을 가리키면 ②, `server: cloudflare`만 반복되고 `goals.fly.dev`로 직접 접속하면 정상이면 ①입니다.

**해설:** 프록시가 여러 겹이면 "누가 TLS를 끝냈고 다음 칸에 어떻게 알리나"를 층마다 확인합니다.

</details>

## 면접 질문

<details>
<summary>Q1. 무중단 배포는 어떻게 하나요? DB 마이그레이션이 있을 땐요?</summary>

**모범 답안:**

1. **불변 이미지**를 만들어 레지스트리에 올립니다. 같은 이미지를 스테이징·운영에 씁니다.
2. 배포 전 **release 단계에서 migrate를 한 번** 돌립니다. 실패하면 배포를 멈춥니다.
3. **롤링**(또는 블루/그린·카나리)으로 교체합니다. LB는 **헬스체크(readiness)를 통과한 인스턴스에만** 트래픽을 보내고, 빠지는 인스턴스는 **connection draining** 후 SIGTERM으로 graceful 종료합니다.
4. 교체 중 두 버전이 공존하므로 마이그레이션은 **하위 호환**이어야 합니다. 컬럼 삭제·이름 변경은 **expand → contract**로 여러 배포에 나눕니다.
5. 배포 후 **에러율·지연 지표**를 보고, 나쁘면 **이전 이미지로 롤백**합니다. expand 단계까지는 DB가 옛 코드와 호환되니 롤백도 안전합니다.

</details>

<details>
<summary>Q2. Django 앱을 AWS에 올린다면 어떤 구성으로 하겠어요?</summary>

**모범 답안:**

- **Route 53**(DNS) → **CloudFront**(정적·미디어 캐시) / **ALB**(TLS 종료, ACM 인증서, L7 헬스체크)
- **ECS Fargate**에 gunicorn 컨테이너 2개 이상, 여러 **가용 영역**(AZ)에 분산. Celery 워커는 별도 서비스.
- **RDS Postgres**(Multi-AZ, 자동 백업), **ElastiCache Redis**(캐시·Celery 브로커)
- **S3**에 정적 파일(`collectstatic`)과 업로드(presigned URL)
- 비밀값은 **Secrets Manager**, 이미지는 **ECR**, 로그는 stdout → **CloudWatch Logs**
- 배포는 CI가 이미지 빌드·push → migrate 일회성 태스크 → ECS 롤링 업데이트

초기엔 비싸므로 PaaS로 시작해 옮겨도 된다고 덧붙입니다. 핵심은 웹을 **무상태**(stateless)로 두는 것입니다. 세션·파일·캐시가 밖(DB·S3·Redis)에 있으면 어디로든 옮길 수 있습니다.

</details>

## 오늘 정리

- **어디에**: 첫 배포는 PaaS. `0.0.0.0` 바인딩, 비밀값은 secrets, DB는 `DATABASE_URL`.
- **순서**: release 단계에서 migrate 먼저, 두 버전 공존을 견디게 expand → contract.
- **운영**: CNAME + 자동 인증서, 헬스체크가 나쁜 배포를 막고, 롤백은 이전 이미지로.
