# Day 5 · 모듈/패키지·예외·파일 I/O

> 목표: `import`가 내부에서 **무엇을 하는지**(sys.modules·sys.path),
> 순환 import를 **왜** 만나고 어떻게 푸는지, 예외를 Python답게
> (EAFP·`raise from`) 다루고, `pathlib`로 파일을 안전하게 읽고 쓴다.
> CS로는 dict/set을 떠받치는 **해시 테이블 내부**를 CPython 수준으로 본다.

Django 프로젝트는 처음부터 끝까지 오늘 내용으로 짜여 있습니다.
`settings.py`의 `BASE_DIR = Path(__file__).resolve()...`는 pathlib이고,
앱 하나하나는 `apps.py`(AppConfig)를 가진 **패키지**입니다.
뷰에서 `raise Http404`를 하면 미들웨어가 예외를 404 응답으로 바꿔 주고,
업로드 파일은 `MEDIA_ROOT` 아래에 파일 I/O로 저장됩니다.
그리고 이 모든 것을 빠르게 만드는 게 dict, 즉 해시 테이블입니다.

## Part 1. 모듈과 import

### 1-1. 모듈 = .py 파일 하나

Python에서 **모듈**은 그냥 `.py` 파일 하나입니다.
파일 안의 함수·클래스·변수가 그 모듈의 **네임스페이스**(이름 공간)가 됩니다.
`import`는 "그 파일을 실행하고, 결과 네임스페이스를 이름에 묶는" 동작입니다.
그래서 모듈 맨 위에 쓴 코드는 import 순간 **실제로 실행**됩니다.

```python
# utils.py
PI = 3.14

def area(r):
    return PI * r * r
```

```python
import utils
print(utils.area(2))
# 출력: 12.56
print(type(utils))
# 출력: <class 'module'>
```

**JS에서는:** ES 모듈도 파일 하나가 모듈입니다.
차이는 Python엔 `export` 키워드가 없다는 점입니다.
최상위에 있는 이름은 **전부 공개**되고, `_`로 시작하면
"내부용"이라는 관례만 있습니다.

> 💡 핵심: 모듈 = 파일 = 객체. import = 실행 + 이름 바인딩.

### 1-2. import vs from import: 바인딩이 다르다

`import config`는 **모듈 객체**를 이름에 묶습니다.
`from config import DEBUG`는 그 순간의 **값**을 내 모듈의
새 이름에 복사해 묶습니다. 그래서 나중에 `config.DEBUG`가 바뀌어도
내가 가져온 `DEBUG`는 옛 값 그대로입니다.
테스트에서 설정을 바꿨는데 반영이 안 되는 버그가 여기서 나옵니다.

```python
import config
from config import DEBUG

config.DEBUG = True
print(config.DEBUG, DEBUG)
# 출력: True False
```

**JS에서는:** ESM `import { DEBUG } from './config.js'`는
**라이브 바인딩**이라 원본이 바뀌면 같이 바뀝니다.
Python의 `from import`는 라이브가 아니라 **스냅샷**입니다.

**Django 연결:** 그래서 설정은 항상 이렇게 읽습니다.

```python
from django.conf import settings

if settings.DEBUG:
    print("dev mode")
```

`settings`는 지연 객체라 `override_settings`로 바꿔도
`settings.DEBUG`로 읽는 쪽은 바뀐 값을 봅니다.

> 💡 핵심: 바뀔 수 있는 값은 `모듈.이름`으로 읽는다.

### 1-3. import 캐시: sys.modules

같은 모듈을 열 군데서 import해도 파일은 **한 번만** 실행됩니다.
처음 import한 모듈 객체가 `sys.modules`라는 dict에 저장되고,
다음부터는 그 dict에서 꺼내 주기 때문입니다.
모듈 최상위 코드가 "앱 전체에서 1회 실행"된다는 보장이 여기서 나옵니다.

```python
# counter.py
print("loading counter")
count = 0
```

```python
import sys
import counter
import counter
# 출력: loading counter  (한 번만)
print("counter" in sys.modules)
# 출력: True
```

같은 객체를 공유하므로 모듈은 사실상 **싱글턴**입니다.
다시 실행하려면 `importlib.reload(counter)`를 씁니다.

**JS에서는:** Node의 `require.cache`, ESM의 모듈 맵과 같은 개념입니다.
"모듈은 한 번 평가되고 캐시된다"는 점이 똑같습니다.

> 💡 핵심: import 비용은 첫 1회. 이후엔 sys.modules 조회(dict, O(1)).

### 1-4. 모듈을 어디서 찾나: sys.path

`import x`를 만나면 Python은 `sys.modules`를 먼저 보고,
없으면 `sys.path` 목록의 디렉터리를 **앞에서부터** 뒤집니다.
첫 칸은 보통 실행한 스크립트의 폴더라서,
내 파일 이름이 표준 라이브러리와 겹치면 그쪽이 먼저 잡힙니다.
`json.py`, `random.py`를 만들었다가 이상한 에러를 보는 이유입니다.

```python
import sys

for p in sys.path[:3]:
    print(p)
# 출력: 스크립트 폴더, ..., site-packages
```

```text
my_project/
├── json.py      ← 표준 json을 가려 버림
└── main.py      ← import json 하면 위 파일이 로드
```

Python 3.13은 이런 경우 에러 메시지에
`consider renaming '.../json.py'` 힌트를 붙여 줍니다.

**JS에서는:** `import 'json'` 같은 맨 이름은 `node_modules`에서 찾고,
내 파일은 `./`로 명시해야 합니다. Python은 둘을 **같은 경로 목록**에서
찾기 때문에 이름 충돌이 생깁니다.

> 💡 핵심: 표준 라이브러리 이름으로 파일을 만들지 않는다.

### 1-5. if __name__ == "__main__"

모듈마다 `__name__`이라는 변수가 있습니다.
import되면 모듈 이름(`"utils"`)이, **직접 실행**되면 `"__main__"`이 들어갑니다.
이걸로 "직접 실행할 때만 도는 코드"를 분리합니다.
이 가드가 없으면 import만 했는데 스크립트가 돌아가 버립니다.

```python
def main():
    print("run!")

if __name__ == "__main__":
    main()
```

`python tool.py`면 실행되고, `import tool`이면 `main`만 정의됩니다.
Django의 `manage.py`도 정확히 이 구조입니다.

**JS에서는:** CommonJS의 `require.main === module`과 같습니다.

> 💡 핵심: `__main__` 가드 = "import 시 부작용 없음" 보장.

### 1-6. 순환 import는 왜 터지나

A가 B를 import하고 B가 다시 A를 import하면 **순환 import**입니다.
Python은 A를 실행하다가 B로 넘어가는데, 이때 A는 `sys.modules`에
**반쯤 만들어진 상태**로 들어 있습니다. B가 A에서 아직 정의되지 않은
이름을 `from A import X`로 꺼내려 하면 실패합니다.
Django에서 `models.py`끼리, 혹은 `models`↔`services` 사이에 자주 납니다.

```python
# shop/orders.py
from shop.users import User

class Order:
    pass
```

```python
# shop/users.py
from shop.orders import Order

class User:
    pass
```

```text
ImportError: cannot import name 'Order'
from partially initialized module
'shop.orders' (most likely due to a
circular import)
```

`orders` 1행에서 `users`로 갔는데, `users`가 찾는 `Order`는
`orders`의 3행이라 아직 실행되지 않았습니다.

**JS에서는:** 순환이 에러 없이 통과하고 값이 `undefined`로 보이는
경우가 많아 더 늦게 발견됩니다. Python은 import 시점에 바로 터집니다.

> 💡 핵심: 순환 import = "반쯤 초기화된 모듈"에서 이름을 꺼내려다 실패.

### 1-7. 순환 import 푸는 세 가지 방법

가장 좋은 해결은 **구조를 고치는 것**입니다.
두 모듈이 공유하는 것을 제3의 모듈로 빼면 화살표가 한쪽으로만 흐릅니다.
급할 때는 **함수 안에서 import**(지연 import)해서
실행 시점을 "모듈 로딩이 다 끝난 뒤"로 미룹니다.
타입 힌트 때문에만 필요하면 `TYPE_CHECKING`을 씁니다.

```python
# 방법 1: 함수 안에서 지연 import
def get_orders(user):
    from shop.orders import Order
    return Order.for_user(user)
```

```python
# 방법 2: 타입 힌트용 import만 분리
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from shop.orders import Order
```

`TYPE_CHECKING`은 런타임에 `False`라서 실제 import가 일어나지 않고,
mypy 같은 타입 검사기만 읽습니다.
방법 3은 공통 코드를 `shop/common.py`로 옮기는 것입니다.

**JS에서는:** 동적 `import()`나 함수 안 `require()`로 미루는 것과 같은 발상입니다.

> 💡 핵심: 1순위 구조 분리, 2순위 지연 import, 타입만이면 TYPE_CHECKING.

### 1-8. Django가 순환 import를 피하는 방식

Django는 모델끼리 서로 참조하는 일이 많아서
**문자열 참조**라는 장치를 제공합니다.
`"앱이름.모델이름"`을 넘기면 실제 클래스는 앱 로딩이 끝난 뒤에 찾습니다.
User 모델은 `settings.AUTH_USER_MODEL`로 가리키는 게 표준입니다.

```python
from django.conf import settings
from django.db import models

class Order(models.Model):
    user = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
    )
```

```python
# 다른 앱 모델도 문자열로
coupon = models.ForeignKey(
    "promotions.Coupon",
    on_delete=models.SET_NULL,
    null=True,
)
```

**JS에서는:** TypeORM의 `@ManyToOne(() => User)`처럼
함수로 감싸 지연 평가하는 것과 같은 목적입니다.

> 💡 핵심: Django 모델 참조는 문자열로 → import 없이 지연 해석.

## Part 2. 패키지

### 2-1. 패키지 = 모듈을 담은 디렉터리

모듈이 많아지면 디렉터리로 묶습니다. 이게 **패키지**입니다.
디렉터리에 `__init__.py`를 두면 일반 패키지가 되고,
`import shop`을 하면 이 `__init__.py`가 실행됩니다.
점(`.`)으로 하위 모듈을 가리킵니다.

```text
shop/
├── __init__.py
├── orders.py
└── payments/
    ├── __init__.py
    └── card.py
```

```python
import shop.payments.card
from shop.payments import card
from shop.payments.card import charge
```

세 줄 모두 같은 `card` 모듈을 씁니다(sys.modules에 한 번 등록).
`import shop.payments.card`는 `shop`, `shop.payments`의
`__init__.py`를 **차례로 실행**합니다.

**JS에서는:** 폴더 + `index.js`와 비슷합니다.
`__init__.py` ≈ `index.js`라고 보면 됩니다.

> 💡 핵심: 패키지 = 디렉터리 + `__init__.py`. 점 경로로 접근.

### 2-2. 절대 import vs 상대 import

패키지 안에서는 `.`(현재 패키지), `..`(부모 패키지)로 시작하는
**상대 import**를 쓸 수 있습니다. 패키지 이름이 바뀌어도
내부 import를 고칠 필요가 없다는 장점이 있습니다.
단, 상대 import는 "내가 어느 패키지 소속인지" 알아야 동작합니다.

```python
# shop/payments/card.py 안에서
from . import utils
from .utils import fmt
from ..orders import Order
```

그래서 이 파일을 `python shop/payments/card.py`로 직접 실행하면
소속 패키지가 없어서 실패합니다.

```bash
python shop/payments/card.py
# ImportError: attempted relative import
#   with no known parent package
python -m shop.payments.card
# 정상 실행
```

**JS에서는:** `./`, `../`가 **파일 경로** 기준이라 항상 동작합니다.
Python의 `.`은 **패키지 이름** 기준이라 `-m`으로 실행해야 합니다.

> 💡 핵심: 상대 import는 패키지 기준. 직접 실행 말고 `python -m`.

### 2-3. __init__.py로 공개 API 정리하기

`__init__.py`에서 하위 모듈의 이름을 다시 꺼내 두면
사용자는 긴 경로를 몰라도 됩니다. 라이브러리들이 흔히 쓰는 패턴입니다.
`__all__`은 `from shop import *`가 가져갈 이름 목록을 정합니다.
다만 `__init__.py`가 무거우면 패키지를 건드리기만 해도 모든 게 로딩되고,
순환 import의 원인이 되기도 하니 가볍게 유지합니다.

```python
# shop/__init__.py
from .orders import Order
from .payments.card import charge

__all__ = ["Order", "charge"]
```

```python
from shop import Order, charge
```

**JS에서는:** `index.js`에서 `export { Order } from './orders'`로
모아 내보내는 **배럴 파일**과 같습니다. 부작용(무거워짐)도 같습니다.

> 💡 핵심: `__init__.py` = 패키지의 공개 창구. 가볍게.

### 2-4. 네임스페이스 패키지

Python 3.3부터는 `__init__.py`가 **없는** 디렉터리도 import됩니다.
이를 **네임스페이스 패키지**(PEP 420)라고 하며, 여러 위치에 흩어진
같은 이름의 디렉터리를 하나의 패키지로 합칠 때 쓰입니다.
편해 보이지만 테스트 도구나 Django 앱 탐색이 헷갈릴 수 있어,
일반 프로젝트에서는 `__init__.py`를 **항상 두는 것**이 안전합니다.

```python
import shop
print(shop.__file__)
# 출력: .../shop/__init__.py
# (네임스페이스 패키지면 None)
```

**JS에서는:** 대응 개념이 없습니다. npm 스코프(`@org/pkg`)가
이름을 묶는다는 점에서 비슷할 뿐입니다.

> 💡 핵심: 의도가 없다면 `__init__.py`는 항상 만든다.

### 2-5. Django 앱 = 패키지

`python manage.py startapp orders`가 만드는 것은 그냥 패키지입니다.
Django는 `INSTALLED_APPS`에 적힌 **패키지 경로**를 import하고,
각 앱의 `apps.py`에 있는 `AppConfig`로 앱을 등록합니다.
`ready()`는 모든 앱 로딩이 끝난 뒤 한 번 불리므로,
시그널 등록처럼 다른 앱 모델이 필요한 import를 두기 좋은 곳입니다.

```text
orders/
├── __init__.py
├── apps.py
├── models.py
├── views.py
└── migrations/
    └── __init__.py
```

```python
# orders/apps.py
from django.apps import AppConfig

class OrdersConfig(AppConfig):
    name = "orders"

    def ready(self):
        from . import signals
```

`ready()` 안의 import는 1-7의 **지연 import** 그 자체입니다.

**JS에서는:** NestJS의 모듈(`@Module`)이 앱 단위 등록 역할을 합니다.

> 💡 핵심: 앱 = 패키지, AppConfig = 앱 등록증, `ready()` = 지연 초기화 지점.

## Part 3. 예외

### 3-1. try / except / else / finally

Python의 예외 구문은 블록이 네 개입니다.
`except`는 에러가 났을 때, `else`는 **에러가 안 났을 때만**,
`finally`는 **무슨 일이 있어도** 실행됩니다.
`else`가 있는 이유는 try 블록을 "실패할 수 있는 한 줄"로
최소화하기 위해서입니다. 성공 후 처리까지 try에 넣으면
엉뚱한 에러까지 같은 except로 삼켜 버립니다.

```python
def parse(s):
    try:
        n = int(s)
    except ValueError:
        return None
    else:
        return n * 2
    finally:
        print("done")
```

```python
print(parse("21"))
# 출력: done
# 출력: 42
```

**JS에서는:** `try/catch/finally`만 있고 `else`가 없습니다.
JS에선 성공 처리를 try 안에 두는 수밖에 없죠.

> 💡 핵심: try는 짧게, 성공 후 처리는 else, 정리는 finally.

### 3-2. 구체적인 예외부터 잡는다

`except`는 위에서부터 차례로 검사하고 **처음 맞는 하나**만 실행합니다.
부모 클래스를 먼저 쓰면 자식 예외가 전부 거기서 걸립니다.
여러 예외를 같은 방식으로 처리할 때는 튜플로 묶습니다.
`as e`로 예외 객체를 받아 메시지나 속성을 볼 수 있습니다.

```python
try:
    value = data["age"] / 0
except KeyError as e:
    print("키 없음:", e)
except (ZeroDivisionError, TypeError):
    print("계산 불가")
```

**JS에서는:** `catch`는 하나뿐이라 `if (e instanceof X)`로
직접 분기해야 합니다. Python은 타입 분기가 문법에 들어 있습니다.

> 💡 핵심: except는 좁은 것 → 넓은 것 순서로.

### 3-3. finally는 return보다 늦다

`finally`는 try 안에서 `return`을 해도 **그 뒤에** 실행됩니다.
DB 커넥션 반납, 락 해제 같은 정리 코드가 반드시 돈다는 보장입니다.
반대로 `finally` 안에서 `return`하면 진행 중이던 예외가
**조용히 사라지는** 심각한 버그가 생깁니다.
그래서 Python 3.14부터는 이 코드에 경고(PEP 765)가 뜹니다.

```python
def f():
    try:
        return "try"
    finally:
        print("finally")
```

```python
print(f())
# 출력: finally
# 출력: try
```

```python
# 나쁜 예: 예외가 삼켜짐
def g():
    try:
        1 / 0
    finally:
        return "ok"
```

**JS에서는:** 동작이 같습니다. `finally`의 `return`이
예외를 덮어쓰는 함정도 똑같습니다.

> 💡 핵심: finally는 정리만. 그 안에서 return 금지.

### 3-4. 예외 계층: BaseException vs Exception

모든 예외의 뿌리는 `BaseException`이고,
우리가 잡아야 하는 "프로그램 오류"는 그 아래 `Exception`입니다.
`KeyboardInterrupt`(Ctrl+C)와 `SystemExit`(`sys.exit()`)는
`Exception`의 자식이 **아닙니다**. 그래서 맨 `except:`나
`except BaseException:`을 쓰면 Ctrl+C로도 서버가 안 꺼집니다.

```text
BaseException
├── SystemExit
├── KeyboardInterrupt
└── Exception
    ├── ValueError
    ├── KeyError (← LookupError)
    └── OSError
        └── FileNotFoundError
```

```python
print(issubclass(
    KeyboardInterrupt, Exception))
# 출력: False
```

**JS에서는:** 아무 값이나 `throw`할 수 있고(`throw "x"`도 가능)
계층 규칙이 없습니다. Python은 `BaseException` 자손만 던질 수 있습니다.

> 💡 핵심: 넓게 잡아도 `except Exception`까지. 맨 except는 금지.

### 3-5. raise: 던지기와 다시 던지기

`raise ValueError("msg")`로 예외를 던집니다.
except 안에서 인자 없이 `raise`만 쓰면 **지금 잡은 예외를
원래 traceback 그대로** 다시 던집니다.
"로그만 남기고 위로 올리기" 패턴에 꼭 필요합니다.
`raise e`로 다시 던지면 traceback에 현재 줄이 추가되어 원인 추적이 흐려집니다.

```python
import logging
logger = logging.getLogger(__name__)

try:
    charge(order)
except PaymentError:
    logger.exception("결제 실패")
    raise
```

`logger.exception`은 traceback까지 로그에 남깁니다.

**JS에서는:** `catch (e) { log(e); throw e; }`와 같습니다.
JS는 스택이 Error 생성 시점에 고정돼서 `throw e`도 괜찮지만,
Python은 맨 `raise`가 관례입니다.

> 💡 핵심: 잡았다가 다시 올릴 땐 맨 `raise`.

### 3-6. raise from: 예외 체이닝

저수준 예외를 도메인 예외로 **번역**할 때는 `raise 새예외 from 원인`을 씁니다.
원인은 새 예외의 `__cause__`에 저장되고, traceback에
"The above exception was the direct cause..."로 두 예외가 함께 찍힙니다.
`from` 없이 except 안에서 다른 예외를 던져도 `__context__`에 남지만,
메시지가 "During handling... another exception occurred"로 바뀌어
**의도한 번역인지 실수인지** 구분되지 않습니다.

```python
class ConfigError(Exception):
    pass

def load_port(env):
    try:
        return int(env["PORT"])
    except (KeyError, ValueError) as e:
        raise ConfigError("PORT 오류") from e
```

```python
try:
    load_port({"PORT": "abc"})
except ConfigError as e:
    print(type(e.__cause__).__name__)
# 출력: ValueError
```

원인을 숨기고 싶다면 `raise ConfigError(...) from None`을 씁니다.

**JS에서는:** ES2022의 `new Error("msg", { cause: e })`가 같은 기능입니다.

> 💡 핵심: 예외를 번역할 땐 `from e`로 원인을 남긴다.

### 3-7. 커스텀 예외 만들기

도메인 오류는 **자기 예외 클래스**로 표현하면 호출하는 쪽이
타입으로 정확히 골라 잡을 수 있습니다. 앱 공통 부모를 하나 두고
그 아래에 구체 예외를 두는 2단 구조가 실무 표준입니다.
필요한 정보(주문 ID, 사유 코드)는 속성으로 들고 다니게 합니다.

```python
class ShopError(Exception):
    pass

class OutOfStock(ShopError):
    def __init__(self, sku):
        super().__init__(f"재고 없음: {sku}")
        self.sku = sku
```

```python
try:
    raise OutOfStock("A-1")
except ShopError as e:
    print(e, e.sku)
# 출력: 재고 없음: A-1 A-1
```

이름은 `...Error`로 끝내는 것이 PEP 8 관례입니다
(`OutOfStock`처럼 상태 이름도 흔히 씁니다).

**JS에서는:** `class OutOfStock extends Error {}`와 같습니다.
JS처럼 `this.name`을 따로 설정할 필요는 없습니다.

> 💡 핵심: 앱 공통 부모 예외 + 구체 예외 + 속성으로 정보 전달.

### 3-8. EAFP vs LBYL

**LBYL**(Look Before You Leap)은 "먼저 확인하고 실행",
**EAFP**(Easier to Ask Forgiveness than Permission)는
"일단 하고 실패하면 처리"입니다. Python 커뮤니티는 EAFP를 선호합니다.
확인과 실행 사이에 상태가 바뀌는 **경쟁 조건**(TOCTOU)을 피할 수 있고,
3.11부터는 예외가 안 날 때 try의 비용이 사실상 0(zero-cost)이기 때문입니다.

```python
# LBYL: 확인 후 실행 (경쟁 조건 가능)
import os

if os.path.exists(path):
    with open(path) as f:
        data = f.read()
```

```python
# EAFP: 일단 열고 실패를 처리
try:
    with open(path) as f:
        data = f.read()
except FileNotFoundError:
    data = ""
```

LBYL 쪽은 `exists` 직후 다른 프로세스가 파일을 지우면 그대로 터집니다.
단, 예외가 **자주** 나는 경로(절반이 실패)라면 예외 생성 비용이 커서
`dict.get`, `in` 같은 확인이 더 낫습니다.

**JS에서는:** `if (obj.key !== undefined)`, `?.` 같은
LBYL 스타일이 일반적입니다. Python은 반대 문화라는 점을 기억하세요.

> 💡 핵심: 드문 실패는 EAFP, 흔한 분기는 확인(get/in).

### 3-9. Django의 예외: 던지면 응답이 된다

Django에서 예외는 **흐름 제어 도구**입니다.
뷰에서 `Http404`를 던지면 404, `PermissionDenied`면 403 응답이 됩니다.
요청을 감싸는 핸들러가 예외를 잡아 응답으로 바꿔 주기 때문입니다.
그래서 뷰 깊은 곳(서비스 함수)에서도 바로 던질 수 있습니다.

```python
from django.http import Http404, HttpResponse

def detail(request, pk):
    try:
        post = Post.objects.get(pk=pk)
    except Post.DoesNotExist:
        raise Http404("글 없음")
    return HttpResponse(post.title)
```

```python
from django.shortcuts import (
    get_object_or_404,
)

post = get_object_or_404(Post, pk=pk)
```

`get_object_or_404`가 위의 try/except를 한 줄로 줄여 줍니다.
`Model.DoesNotExist`는 모델마다 자동으로 생기는 예외 클래스입니다.

**JS에서는:** Express에서 `next(err)` 후 에러 미들웨어가
상태 코드를 정하는 것과 같은 구조입니다.

> 💡 핵심: Http404 → 404, PermissionDenied → 403. 던지면 Django가 응답으로.

### 3-10. ValidationError: 사용자 입력 오류

`django.core.exceptions.ValidationError`는 폼/모델 검증 실패를
표현합니다. 폼의 `clean_필드()`에서 던지면 500이 아니라
**그 필드의 에러 메시지**로 화면에 표시됩니다.
DRF에는 같은 이름의 `rest_framework.exceptions.ValidationError`가 있고,
이건 400 응답으로 바뀝니다. 이름이 같아 import를 헷갈리기 쉽습니다.

```python
from django import forms
from django.core.exceptions import (
    ValidationError,
)
```

```python
class SignupForm(forms.Form):
    age = forms.IntegerField()

    def clean_age(self):
        age = self.cleaned_data["age"]
        if age < 14:
            raise ValidationError("14세 이상")
        return age
```

**JS에서는:** Zod/Joi가 에러 객체를 모아 400으로 돌려주는 역할입니다.

> 💡 핵심: 입력 오류는 ValidationError. Django용과 DRF용을 구분한다.

## Part 4. 파일 I/O

### 4-1. with open: 왜 with인가

파일을 열면 OS가 **파일 디스크립터**(열린 파일 번호표)를 하나 내줍니다.
닫지 않으면 이 번호표가 쌓여 결국 `Too many open files`로 서버가 멈춥니다.
`with` 블록은 블록을 빠져나갈 때 **예외가 나도** 자동으로 `close()`를 부릅니다.
Day 4의 던더 메서드 중 `__enter__`/`__exit__`(컨텍스트 매니저 프로토콜)가
그 원리이며, 직접 만드는 법은 이후 레슨에서 다룹니다.

```python
with open("memo.txt", "w",
          encoding="utf-8") as f:
    f.write("안녕\n")

print(f.closed)
# 출력: True
```

`with`가 하는 일을 풀어 쓰면 `try: ... finally: f.close()`입니다.

**JS에서는:** `fs.promises.open()` 후 `finally { await fh.close() }`를
직접 써야 했습니다. TS 5.2+의 `using`이 Python `with`에 해당합니다.

> 💡 핵심: 파일은 항상 with로 연다. 닫기는 Python이 보장한다.

### 4-2. encoding="utf-8"은 항상 명시

`open()`의 기본 인코딩은 **OS 로캘**을 따릅니다.
macOS/Linux는 대개 UTF-8이지만, 한국어 Windows는 **cp949**입니다.
그래서 맥에서 잘 되던 코드가 동료의 Windows에서
`UnicodeDecodeError`로 깨집니다. PEP 686으로 3.15부터
기본이 UTF-8로 바뀌지만, 버전 호환을 위해 명시하는 습관이 안전합니다.

```python
with open("ko.txt",
          encoding="utf-8") as f:
    text = f.read()
```

```python
# BOM이 붙은 엑셀 CSV는 utf-8-sig
with open("excel.csv",
          encoding="utf-8-sig") as f:
    header = f.readline()
```

**JS에서는:** `fs.readFileSync(p, "utf8")`처럼 인코딩을 넘기는 것과 같습니다.
Node는 인코딩을 안 주면 Buffer가 나오고, Python은 로캘로 추측합니다.

> 💡 핵심: 텍스트 파일 = `encoding="utf-8"`. 예외 없이.

### 4-3. 모드: 텍스트 vs 바이너리

모드 문자열은 "무엇을 할지"와 "무엇으로 받을지"를 정합니다.
`r` 읽기, `w` 덮어쓰기, `a` 이어쓰기, `x` 새 파일만(있으면 에러)입니다.
`b`를 붙이면 바이너리 모드라 `str`이 아니라 `bytes`를 주고받고,
인코딩 변환을 하지 않습니다. 이미지·PDF·업로드 파일은 반드시 `b`입니다.

```python
with open("logo.png", "rb") as f:
    head = f.read(4)

print(type(head), head)
# 출력: <class 'bytes'> b'\x89PNG'
```

```python
# 이미 있으면 FileExistsError
with open("lock", "x") as f:
    f.write("1")
```

`x` 모드는 "없을 때만 만들기"를 **원자적으로** 해 줘서
`exists()` 확인 후 쓰는 LBYL보다 안전합니다(3-8 참고).

**JS에서는:** Buffer ↔ `bytes`, 문자열 ↔ `str`입니다.
플래그 `'wx'`가 Python의 `'x'`입니다.

> 💡 핵심: 텍스트는 str + 인코딩, 바이너리는 `b` + bytes.

### 4-4. 큰 파일은 줄 단위로 순회

`f.read()`는 파일 전체를 메모리에 올립니다. 5GB 로그라면 그대로 5GB입니다.
파일 객체는 **이터레이터**라서 `for line in f`로 돌면
한 번에 한 줄씩만 읽어 메모리를 일정하게 씁니다.
Day 6에서 배울 제너레이터의 예고편이기도 합니다.

```python
errors = 0
with open("app.log",
          encoding="utf-8") as f:
    for line in f:
        if "ERROR" in line:
            errors += 1
print(errors)
```

각 `line` 끝에는 `\n`이 붙어 있으니 필요하면 `line.rstrip("\n")`을 씁니다.

**JS에서는:** `readline.createInterface({ input: stream })`와
`for await (const line of rl)`에 해당합니다. Python은 그냥 `for`입니다.

> 💡 핵심: 큰 파일은 `for line in f`. 메모리 O(1).

### 4-5. pathlib.Path: 경로는 객체로

`os.path.join(a, b)` 같은 문자열 조합은 읽기 어렵고 실수가 잦습니다.
`pathlib.Path`는 경로를 **객체**로 다루며, `/` 연산자로 이어 붙이고
이름·확장자·부모 디렉터리를 속성으로 꺼냅니다.
Django 3.1부터 기본 `settings.py`도 `Path`를 씁니다.

```python
from pathlib import Path

p = Path("/srv/app") / "media" / "a.tar.gz"
print(p.name, p.suffix)
# 출력: a.tar.gz .gz
print(p.stem, p.parent)
# 출력: a.tar /srv/app/media
```

```python
# settings.py 맨 위
BASE_DIR = (
    Path(__file__).resolve().parent.parent
)
```

`__file__`은 현재 모듈의 파일 경로입니다. `resolve()`로 절대 경로를 만들고
`parent` 두 번으로 프로젝트 루트까지 올라갑니다.

**JS에서는:** `path.join(__dirname, "..", "media")`에 해당합니다.

> 💡 핵심: 경로 = Path 객체, 이어 붙이기 = `/`.

### 4-6. Path로 읽고, 만들고, 찾기

`Path`에는 자주 쓰는 파일 작업이 메서드로 들어 있어서
짧은 파일은 `open` 없이 한 줄로 읽고 씁니다.
`mkdir(parents=True, exist_ok=True)`는 `mkdir -p`와 같고,
`glob`/`rglob`은 패턴으로 파일을 찾습니다(rglob = 하위 폴더까지).

```python
out = Path("build") / "reports"
out.mkdir(parents=True, exist_ok=True)

f = out / "hello.txt"
f.write_text("hi", encoding="utf-8")
print(f.read_text(encoding="utf-8"))
# 출력: hi
```

```python
for py in Path("src").rglob("*.py"):
    print(py)
```

**JS에서는:** `fs.mkdirSync(p, { recursive: true })`, glob 패키지 조합입니다.
Python은 표준 라이브러리 하나로 끝납니다.

> 💡 핵심: 짧은 파일은 read_text/write_text, 탐색은 rglob.

### 4-7. JSON 읽기·쓰기

`json` 모듈은 dict/list ↔ JSON 문자열을 변환합니다.
`load`/`dump`는 **파일**, `loads`/`dumps`는 **문자열**(s = string)입니다.
한글을 쓸 땐 `ensure_ascii=False`를 줘야 `\uc774`처럼
이스케이프되지 않고 사람이 읽을 수 있게 저장됩니다.

```python
import json

data = {"이름": "동현", "레벨": 5}
p = Path("user.json")
with p.open("w", encoding="utf-8") as f:
    json.dump(data, f, ensure_ascii=False,
              indent=2)
```

```python
with p.open(encoding="utf-8") as f:
    loaded = json.load(f)
print(loaded["이름"])
# 출력: 동현
```

깨진 JSON은 `json.JSONDecodeError`(ValueError의 자식)를 던집니다.

**JS에서는:** `JSON.parse`/`JSON.stringify`와 같습니다.
JS는 기본으로 한글을 그대로 쓰지만 Python은 옵션이 필요합니다.

> 💡 핵심: 파일은 load/dump, 문자열은 loads/dumps, 한글은 ensure_ascii=False.

### 4-8. Django: 업로드 파일과 MEDIA_ROOT

사용자가 올린 파일은 `MEDIA_ROOT`(디스크 경로) 아래에 저장되고
`MEDIA_URL`로 서빙됩니다. 업로드 파일을 `read()`로 한 번에 읽으면
큰 파일에서 메모리가 터지므로 `chunks()`로 나눠 씁니다.
실무에서는 `open()`을 직접 쓰기보다 **Storage API**를 거칩니다.
그래야 나중에 로컬 디스크를 S3로 바꿔도 코드가 그대로입니다.

```python
# settings.py
MEDIA_ROOT = BASE_DIR / "media"
MEDIA_URL = "/media/"
```

```python
def save_upload(f, dest):
    with dest.open("wb") as out:
        for chunk in f.chunks():
            out.write(chunk)
```

```python
from django.core.files.storage import (
    default_storage,
)

name = default_storage.save(
    "avatars/me.png", request.FILES["img"])
```

**JS에서는:** multer의 `diskStorage` ↔ `multer-s3`를 갈아끼우는 것과 같은 추상화입니다.

> 💡 핵심: 업로드는 바이너리 + chunks, 저장은 Storage API로.

## Part 5. CS 심화: 해시 테이블 내부

Day 2에서 "dict는 해시 테이블이라 평균 O(1)"이라고 배웠습니다.
오늘은 한 단계 내려가 CPython이 **실제로 어떻게** 칸을 고르고,
충돌을 피하고, 언제 테이블을 키우는지 봅니다.
면접에서 "왜 O(1)인가요?"에 "해시니까요"보다 깊게 답하는 게 목표입니다.

### 5-1. 해시 → 인덱스: 비트 마스크

**해시 함수**는 키를 고정 크기 정수로 바꿉니다.
CPython은 테이블 크기를 항상 **2의 거듭제곱**(8, 16, 32...)으로 두고,
`hash(key) & (size - 1)`로 칸 번호를 구합니다.
나머지 연산(`%`)보다 비트 AND가 훨씬 빠르기 때문입니다.

```python
mask = 8 - 1
for k in (1, 9, 42):
    print(k, hash(k) & mask)
# 출력: 1 1
# 출력: 9 1
# 출력: 42 2
```

정수의 해시는 대부분 자기 자신입니다. 그래서 1과 9가 **같은 칸**(충돌)입니다.
문자열 해시는 프로세스마다 랜덤 시드가 섞여(PYTHONHASHSEED)
실행할 때마다 값이 다릅니다. 해시 충돌 공격(Hash DoS)을 막기 위해서입니다.

**JS에서는:** V8의 Map도 해시 테이블이지만 해시 함수를 직접 볼 수 없습니다.
Python은 `hash()`와 `__hash__`로 노출되어 있습니다.

> 💡 핵심: 칸 번호 = `hash & (2^k - 1)`. 해시는 저장 위치의 근거.

### 5-2. 충돌 해결: CPython의 오픈 어드레싱

두 키가 같은 칸을 원하면 **충돌**입니다. Java HashMap은 칸마다 리스트를
다는 **체이닝**을 쓰지만, CPython dict는 다른 빈칸을 찾아가는
**오픈 어드레싱**을 씁니다. 별도 노드 할당이 없고 배열 하나라
CPU 캐시에 유리합니다. 다음 칸은 단순히 +1이 아니라
해시의 상위 비트(`perturb`)를 섞어 계산해, 같은 칸에서 출발해도 경로가 갈라집니다.

```python
def probes(h, mask, n=4):
    perturb = h
    i = h & mask
    for _ in range(n):
        yield i
        perturb >>= 5
        i = (i*5 + perturb + 1) & mask
```

```python
print(list(probes(1, 7)))
# 출력: [1, 6, 7, 4]
print(list(probes(33, 7)))
# 출력: [1, 7, 4, 5]
```

1과 33은 둘 다 1번 칸에서 시작하지만 두 번째 칸부터 다릅니다.
이게 CPython `dictobject.c`의 탐사(probing) 공식과 같은 구조입니다.

**JS에서는:** 엔진 내부라 코드로 볼 수 없습니다.
V8의 Map은 오히려 **체이닝** 기반(결정적 해시 테이블)입니다.

> 💡 핵심: 체이닝 = 칸에 리스트, 오픈 어드레싱 = 다른 빈칸 탐사. CPython은 후자.

### 5-3. 삭제는 "비우기"가 아니라 "더미 표시"

오픈 어드레싱에서 키를 지울 때 칸을 그냥 비우면 문제가 생깁니다.
그 칸을 **거쳐 지나갔던** 다른 키를 찾다가 빈칸에서 "없음"으로 멈추기 때문입니다.
그래서 CPython은 지운 칸에 **DUMMY**(묘비, tombstone) 표시를 남깁니다.
탐색은 DUMMY를 건너뛰고, 삽입은 그 자리를 재사용할 수 있습니다.

```text
삽입: A→1번, B→1번 충돌→6번
삭제: A 칸을 그냥 비우면?
조회 B: 1번이 빈칸 → "없음"(오답!)
그래서: 1번 = DUMMY → 계속 탐사 → 6번
```

```python
d = {1: "a", 9: "b"}
del d[1]
print(d[9])
# 출력: b
```

1과 9는 8칸 테이블에서 같은 1번 칸을 원합니다(5-1).
1번 칸이 DUMMY로 남아 있어서 9를 찾는 탐사가 끊기지 않습니다.
삭제가 많으면 DUMMY가 쌓여 탐사가 길어지고,
리사이즈 때 한꺼번에 청소됩니다.

**JS에서는:** 같은 문제가 모든 오픈 어드레싱 구현에 있습니다.
"묘비"는 언어와 무관한 자료구조 용어입니다.

> 💡 핵심: 삭제 = 묘비 표시. 탐사 경로를 끊지 않기 위해.

### 5-4. 부하율 2/3와 리사이즈

**부하율**(load factor)은 "칸 중 몇 %가 찼나"입니다.
꽉 찰수록 충돌과 탐사가 급격히 늘어나므로,
CPython dict는 **2/3**가 차면 테이블을 키우고 모든 키를 새 칸에 다시 넣습니다.
새 크기는 "사용 중인 키 × 3"보다 큰 2의 거듭제곱입니다.

```python
import sys

d, last = {}, sys.getsizeof({})
for i in range(30):
    d[i] = i
    if sys.getsizeof(d) != last:
        print("grow at", len(d))
        last = sys.getsizeof(d)
```

```text
grow at 1    (빈 dict → 8칸)
grow at 6    (8칸의 2/3 초과 → 16칸)
grow at 11   (16칸의 2/3 초과 → 32칸)
grow at 22   (32칸의 2/3 초과 → 64칸)
```

(Python 3.13 기준. 버전에 따라 숫자가 조금 다를 수 있습니다.)
빈 칸을 1/3 이상 남겨 두는 것이 평균 탐사 횟수를 작게 유지하는 비결입니다.

**JS에서는:** V8 Map도 가득 차면 두 배 크기로 새로 만듭니다.
배열의 오버얼로케이션(Day 2)과 같은 아이디어입니다.

> 💡 핵심: 2/3 차면 키운다. 빈칸 여유 = 짧은 탐사 = 빠른 조회.

### 5-5. amortized O(1): 리사이즈 비용은 나눠 낸다

리사이즈 순간에는 모든 키를 다시 넣으니 그 한 번은 **O(n)**입니다.
그런데 크기를 **배수로** 키우기 때문에 리사이즈는 드물게 일어납니다.
n개를 넣는 동안 재배치하는 총량은 n + n/2 + n/4 + ... < 2n이라
삽입 1번당 평균 비용은 **상수**입니다. 이것을 **분할 상환(amortized) O(1)**이라고 합니다.

```text
리사이즈 시점의 재배치 수:
  5 + 10 + 21 + 42 + ... ≈ 2n 이하
n번 삽입 총비용 = n + 2n = 3n
→ 1번당 평균 O(1)
```

```python
import sys

d, grows, last = {}, 0, 0
for i in range(1_000_000):
    d[i] = i
    if sys.getsizeof(d) != last:
        grows += 1
        last = sys.getsizeof(d)
```

```python
print(grows)
# 출력: 19
```

100만 번 넣는 동안 리사이즈는 19번뿐입니다(약 log₂ n).
나머지 999,981번은 칸 하나를 채우는 O(1) 작업입니다.

최악은 따로 있습니다. 모든 키가 같은 해시면 탐사가 매번 끝까지 가서
조회가 **O(n)**이 됩니다. "평균 O(1), 최악 O(n)"을 같이 말해야 정답입니다.

**JS에서는:** `Array.push`의 amortized O(1)과 같은 논리입니다.

> 💡 핵심: 배수 성장 → 리사이즈 비용 분산 → 삽입 amortized O(1).

### 5-6. compact dict: 순서가 보장되는 이유

3.6부터 CPython dict는 배열을 **두 개**로 나눴습니다.
작은 정수만 담는 희소 **인덱스 배열**과, (해시, 키, 값)을
**삽입 순서대로** 쌓는 조밀한 **엔트리 배열**입니다.
순회는 엔트리 배열을 앞에서부터 읽으니 삽입 순서가 자연히 유지되고,
빈칸이 1바이트짜리 인덱스뿐이라 메모리도 20~25% 줄었습니다.
3.7부터 이 순서 보장은 언어 **명세**가 되었습니다.

```text
d = {"b": 1, "a": 2}

indices: [-, 1, -, -, 0, -, -, -]
entries: 0 → (hash_b, "b", 1)
         1 → (hash_a, "a", 2)
```

```python
d = {"b": 1, "a": 2}
d["c"] = 3
print(list(d))
# 출력: ['b', 'a', 'c']
```

`hash("b")`가 4번, `hash("a")`가 1번 칸이라고 하면,
인덱스 배열은 엔트리 번호만 가리키고 실제 데이터는 순서대로 쌓입니다.

**JS에서는:** Map과 일반 객체의 문자열 키도 삽입 순서를 지킵니다.
(단, JS 객체는 정수형 키를 먼저 오름차순 정렬합니다.)

> 💡 핵심: 인덱스 배열 + 순서대로 쌓는 엔트리 배열 = 순서 보장 + 메모리 절약.

### 5-7. 키 비교 순서: is → hash → ==

dict는 키를 찾을 때 세 단계로 비교합니다.
① 같은 객체(`is`)면 바로 일치, ② 저장된 해시가 다르면 바로 불일치,
③ 해시가 같을 때만 비싼 `__eq__`를 호출합니다.
그래서 `==`이면 `hash`도 같아야 한다는 계약이 중요하고,
이 계약 때문에 의외의 결과가 생깁니다.

```python
d = {1: "a", True: "b", 1.0: "c"}
print(d)
# 출력: {1: 'c'}
```

`1 == True == 1.0`이고 해시도 모두 1이라 **같은 키**입니다.
첫 키 객체(`1`)는 남고 값만 덮어써집니다.

```python
nan = float("nan")
print(nan == nan, nan in [nan])
# 출력: False True
```

NaN은 자기 자신과도 같지 않지만 컨테이너는 `is`를 먼저 보기 때문에 찾아집니다.

**JS에서는:** Map은 SameValueZero로 비교해서 `1`과 `true`가 **다른** 키입니다.
Python 출신 버그로 자주 언급되는 차이입니다.

> 💡 핵심: 같은 해시 + `==` 참이면 같은 키. 1·True·1.0은 하나.

### 5-8. 키가 해시 가능해야 하는 이유

키의 해시는 **저장 위치**를 정했습니다. 저장 뒤에 키 내용이 바뀌어
해시가 달라지면, 키는 엉뚱한 칸에 갇혀 다시 찾을 수 없습니다.
그래서 list·dict·set 같은 가변 타입은 `__hash__`가 `None`입니다.
tuple은 불변이지만 안에 list가 있으면 역시 해시가 불가능합니다.

```python
key = (1, [2])
try:
    {key: "x"}
except TypeError as e:
    print(e)
# 출력: unhashable type: 'list'
```

```python
# 대안: 불변 타입으로 바꿔 키로
key = (1, (2,))
tags = frozenset({"a", "b"})
cache = {key: 1, tags: 2}
```

**JS에서는:** Map은 객체를 **참조**로 키로 써서 가변 객체도 됩니다.
대신 내용이 같은 두 배열은 다른 키입니다. Python은 **값** 기준이라 불변이 필요합니다.

> 💡 핵심: 해시 가능 ≈ 불변. 키로 쓰려면 tuple/frozenset으로.

### 5-9. set은 값 없는 해시 테이블

set도 해시 테이블이지만 dict와 **구현이 따로** 있습니다.
값 칸이 없고, 순서 보장이 **없습니다**(compact 구조를 안 씀).
충돌 시 먼저 바로 옆 칸 몇 개를 선형으로 본 뒤 perturb로 점프해서
캐시 효율을 높이고, 부하율 약 60%에서 키웁니다.
그래서 `in` 검사는 list가 O(n), set이 평균 O(1)입니다.

```python
ids_list = list(range(1_000_000))
ids_set = set(ids_list)

print(999_999 in ids_list)
# 출력: True  (100만 번 비교)
print(999_999 in ids_set)
# 출력: True  (해시 1번 + 탐사 1~2번)
```

**JS에서는:** `Set.has`가 같은 역할입니다.
단, JS Set은 삽입 순서를 지키고 Python set은 지키지 않습니다.

> 💡 핵심: 멤버십 검사는 set. 순서가 필요하면 `dict.fromkeys`.

### 5-10. Django 연결: 해시로 N+1과 O(n·m)을 없앤다

Django 실무에서 해시 테이블은 "쿼리 결과를 메모리에서 빠르게 맞추는" 도구입니다.
두 목록을 이중 for로 맞추면 O(n·m)인데, 한쪽을 `{pk: obj}` dict로 만들면 O(n+m)입니다.
`in_bulk()`는 이 dict를 쿼리 한 번으로 만들어 줍니다.
DB 쪽에서는 pk 조회가 **B-tree 인덱스**(O(log n))로 같은 역할을 합니다.

```python
ids = [o.user_id for o in orders]
users = User.objects.in_bulk(ids)

for o in orders:
    u = users.get(o.user_id)
    print(o.id, u.username if u else "-")
```

```python
# 멤버십은 set으로
blocked = set(
    Block.objects.values_list(
        "user_id", flat=True))
visible = [p for p in posts
           if p.author_id not in blocked]
```

모델 인스턴스의 `__hash__`는 **pk 기반**이라 저장 전(pk=None)
객체를 set/dict 키로 쓰면 `TypeError`가 납니다(Day 4 Q2 참고).

**JS에서는:** Prisma 결과를 `new Map(users.map(u => [u.id, u]))`로
만들어 조인하는 것과 똑같은 패턴입니다.

> 💡 핵심: 리스트끼리 맞추지 말고 dict/set으로. 쿼리는 in_bulk·values_list.

from __future__ import annotations

class Order:

**해설**

- 런타임에도 `User`가 필요하다면 `users.py`의 `new_order` 안에서
  `from shop.orders import Order`로 **지연 import**하는 방법이 있습니다.

### 문제 3. Path로 코드 줄 수 세기

폴더를 받아 그 아래 모든 `.py` 파일의 줄 수를 세고,
많은 순서로 출력하는 도구를 만드세요.
`.venv`, `.git`, `node_modules` 안은 건너뜁니다.
큰 파일도 메모리를 적게 써야 합니다.

<details>
<summary>정답 보기</summary>

```python
from pathlib import Path

SKIP = {".venv", "node_modules", ".git"}

def count_lines(path):
    with path.open(encoding="utf-8") as f:
        return sum(1 for _ in f)
```

```python
def report(root):
    result = {}
    for p in Path(root).rglob("*.py"):
        if SKIP & set(p.parts):
            continue
        rel = p.relative_to(root)
        result[str(rel)] = count_lines(p)
    return result
```

```python
stats = report(".")
top = sorted(stats.items(),
             key=lambda kv: kv[1],
             reverse=True)
for name, n in top:
    print(f"{n:>5} {name}")
```

**해설**

- `rglob("*.py")`가 하위 폴더까지 찾습니다.
- `p.parts`는 경로 조각 튜플입니다. `SKIP & set(...)`은
  **set 교집합**이라, 조각 중 하나라도 SKIP에 있으면 참입니다.
  (SKIP을 list로 두면 매번 선형 검색입니다.)
- `sum(1 for _ in f)`는 한 줄씩 읽으며 세므로 메모리 O(1)입니다.
  `len(f.readlines())`는 전체를 메모리에 올립니다.
- `with`로 열었기 때문에 파일 수천 개를 돌아도 디스크립터가 새지 않습니다.

</details>

### 문제 4. EAFP로 다시 쓰기

아래 LBYL 코드를 EAFP 스타일로 바꾸세요.
그리고 어떤 상황이면 원래 방식(또는 `.get`)이 더 나은지 쓰세요.

```python
def get_email(data):
    if "user" in data:
        user = data["user"]
        if user and "email" in user:
            email = user["email"]
            if isinstance(email, str):
                return email.lower()
    return None
```

<details>
<summary>정답 보기</summary>

```python
def get_email(data):
    try:
        email = data["user"]["email"]
        return email.lower()
    except (KeyError, TypeError,
            AttributeError):
        return None
```

```python
data = {"user": {"email": "A@B.C"}}
print(get_email(data))
# 출력: a@b.c
print(get_email({"user": None}))
# 출력: None
```

**잡는 예외의 의미**

- `KeyError`: `user`나 `email` 키가 없음
- `TypeError`: `data["user"]`가 None이라 `None["email"]`
- `AttributeError`: email이 문자열이 아니라 `.lower()`가 없음

**LBYL/get이 더 나은 경우**

- 키가 없는 경우가 **흔하다면**(예: 절반이 비어 있음) 예외 생성 비용이 쌓입니다.

- try 블록이 길어지면 의도하지 않은 에러까지 삼킬 수 있습니다.
  try 안에는 "실패할 수 있는 줄"만 둡니다.

### 문제 5. (심화) 오픈 어드레싱 미니 dict

선형 탐사(+1씩 다음 칸)를 쓰는 `MiniDict`를 구현하세요.
`d[k] = v`, `d[k]`를 지원하고, 키 수가 칸 수의 2/3 이상이면
두 배로 키워 재배치합니다. (삭제는 생략)

<details>
<summary>정답 보기</summary>

```python
class MiniDict:
    def __init__(self, cap=8):
        self.slots = [None] * cap
        self.n = 0
```

```python
    def _find(self, key):
        mask = len(self.slots) - 1
        i = hash(key) & mask
        while True:
            s = self.slots[i]
            if s is None or s[0] == key:
                return i
            i = (i + 1) & mask
```

```python
    def __setitem__(self, key, val):
        i = self._find(key)
        if self.slots[i] is None:
            self.n += 1
        self.slots[i] = (key, val)
        if self.n * 3 >= len(self.slots) * 2:
            self._resize()
```

```python
    def __getitem__(self, key):
        s = self.slots[self._find(key)]
        if s is None:
            raise KeyError(key)
        return s[1]
```

```python
    def _resize(self):
        old = self.slots
        self.slots = [None] * (len(old) * 2)
        self.n = 0
        for s in old:
            if s is not None:
                self[s[0]] = s[1]
```

```python
d = MiniDict()
d[1] = "a"
d[9] = "b"
print(d[1], d[9], d._find(9))
# 출력: a b 2
```

**해설**

- `1 & 7`과 `9 & 7`은 둘 다 1이라 충돌합니다.
  9는 탐사로 다음 빈칸인 2번에 들어갑니다.
- `_find`는 "그 키가 있는 칸 또는 처음 만난 빈칸"을 돌려줍니다.
  빈칸이 항상 1/3 이상 남아 있으니 무한 루프가 없습니다.
- `_resize`는 모든 키를 **새 마스크**로 다시 넣습니다.
  크기가 바뀌면 `hash & mask` 결과도 바뀌기 때문입니다.
- 삭제를 넣으려면 칸을 None으로 비우면 안 되고 DUMMY 표시가 필요합니다(5-3).
- CPython과 차이: perturb 탐사, 해시값 캐시, compact 레이아웃.

</details>

### 문제 6. 결과 예측: 해시와 동등성

각 줄의 출력을 예측하고 이유를 설명하세요.

```python
print({True: "x", 1: "y"})
print(len({0, 0.0, False, ""}))
print(hash((1, 2)) == hash((1, 2)))
```

<details>
<summary>정답 보기</summary>

```python
print({True: "x", 1: "y"})
# 출력: {True: 'y'}
print(len({0, 0.0, False, ""}))
# 출력: 2
print(hash((1, 2)) == hash((1, 2)))
# 출력: True
```

**해설**

- `True == 1`이고 `hash(True) == hash(1) == 1`이라 같은 키입니다.
  **처음 넣은 키 객체**(`True`)는 남고 값만 `"y"`로 덮입니다.
- `0`, `0.0`, `False`는 모두 같은 값·같은 해시라 하나로 합쳐지고,
  `""`만 따로 남아 2개입니다.
- tuple은 원소들의 해시를 조합해 해시를 만들기 때문에
  내용이 같으면 해시도 같습니다. 그래서 dict 키로 쓸 수 있습니다.
- 실무 함의: JSON에서 온 `1`과 `True`, `"1"`을 섞어 키로 쓰면
  예상과 다르게 합쳐지거나(1·True) 갈라집니다("1"은 별개).

</details>

## 면접 질문

<details>
<summary>Q1. import를 여러 번 해도 모듈이 한 번만 실행되는 이유는? sys.modules란?</summary>

**정의:** `sys.modules`는 "모듈 이름 → 모듈 객체" dict로,
이미 로딩한 모듈의 캐시입니다.

**원리:** `import x`는 ① `sys.modules`에서 찾고, 있으면 바로 반환합니다.
② 없으면 `sys.path`를 따라 파일을 찾아, ③ 빈 모듈 객체를 **먼저**
`sys.modules`에 넣고, ④ 파일을 실행해 네임스페이스를 채웁니다.
③이 먼저라서 순환 import 때 "반쯤 초기화된 모듈"이 보이는 것입니다.

**실무 함의:** 모듈은 프로세스당 싱글턴입니다. 그래서 모듈 최상위의
설정 로딩·커넥션 생성은 1회만 일어납니다. 반대로 import 시점에
무거운 작업이나 DB 접근을 하면 서버 기동과 테스트가 느려집니다.
Django에서 모델 import 시점에 쿼리를 날리면 안 되는 이유이기도 합니다.

</details>

<details>
<summary>Q2. 순환 import는 왜 생기고, Django에서는 어떻게 해결하나요?</summary>

**정의:** 두 모듈이 서로를 (직·간접으로) import하는 구조입니다.

**원리:** A 실행 중 B를 import하면, B는 `sys.modules`에 있는
**미완성 A**를 받습니다. B가 `from A import X`로 아직 정의 안 된
X를 꺼내면 `ImportError: ... partially initialized module`이 납니다.

**해결 순서:**

- 의존 방향 재설계: 공통 코드를 제3 모듈로 분리
- 지연 import: 함수 안에서 import해 실행 시점으로 미룸
- 타입 힌트만 필요하면 `TYPE_CHECKING`

**Django:** `ForeignKey("app.Model")` 문자열 참조와
`settings.AUTH_USER_MODEL`로 모델 import 자체를 피합니다.
시그널처럼 앱 간 연결 코드는 `AppConfig.ready()` 안에서 import합니다.

</details>

<details>
<summary>Q3. EAFP와 LBYL의 차이와, Python이 EAFP를 선호하는 이유는?</summary>

**정의:** LBYL은 "확인 후 실행"(`if key in d`), EAFP는
"실행 후 실패 처리"(`try: d[key] except KeyError`)입니다.

**선호 이유:**

- **경쟁 조건 회피:** 확인과 실행 사이에 상태가 바뀌는
  TOCTOU 문제가 없습니다(파일 존재 확인 후 열기 등).
- **중복 제거:** 확인과 실행이 같은 조회를 두 번 하지 않습니다.
- **비용:** 3.11의 zero-cost 예외 덕에 예외가 안 나면 try는 거의 공짜입니다.

**실무 판단:** 실패가 드물면 EAFP, 흔하면 `.get()`/`in`.
try 블록은 실패 가능한 최소 범위만 감싸고, 구체 예외만 잡습니다.
JS는 `?.`/`!== undefined` 같은 LBYL 문화라 의식적으로 바꿔야 합니다.

</details>

<details>
<summary>Q4. dict 조회의 평균·최악 시간 복잡도와 그 이유를 설명해 보세요.</summary>

**답:** 평균 O(1), 최악 O(n). 삽입은 amortized O(1)입니다.

**평균 O(1)인 이유:** `hash(key) & mask`로 칸을 바로 계산하고,
부하율을 2/3 이하로 유지해 탐사 횟수의 기댓값이 상수입니다.
비교도 `is` → 저장된 해시 → `__eq__` 순이라 대부분 정수 비교로 끝납니다.

**최악 O(n)인 경우:** 해시가 한곳에 몰리면 탐사가 테이블을 훑습니다.
악의적 입력으로 이를 노리는 Hash DoS를 막으려고
문자열 해시는 프로세스마다 랜덤 시드(SipHash)를 씁니다.

**amortized:** 2/3를 넘으면 더 큰 2의 거듭제곱으로 재배치(O(n))하지만,
배수 성장이라 n번 삽입의 총 재배치가 O(n)이어서 1회 평균 O(1)입니다.

**CPython 디테일:** 3.6+ compact dict(인덱스 배열 + 엔트리 배열)로
순서 보장과 메모리 절약을 동시에 얻었습니다.

</details>

<details>
<summary>Q5. list는 왜 dict 키가 될 수 없나요? 커스텀 객체는요?</summary>

**정의:** dict 키는 **해시 가능**해야 합니다. 즉 `__hash__`가 있고,
객체 수명 동안 해시가 변하지 않으며, `a == b`이면 `hash(a) == hash(b)`입니다.

**list가 안 되는 이유:** 키의 해시가 저장 칸을 정합니다.
list는 가변이라 내용이 바뀌면 해시도 바뀌어야 하는데,
그러면 키가 옛 칸에 남아 다시 찾을 수 없습니다.
그래서 `list.__hash__ is None`이고 `TypeError: unhashable type`이 납니다.
대안은 `tuple`/`frozenset`입니다(단, 원소도 해시 가능해야 함).

**커스텀 객체:** 기본은 `id` 기반 해시라 키가 됩니다.
`__eq__`를 오버라이드하면 `__hash__`가 None이 되므로,
불변 필드로 `__hash__`를 정의하거나 `@dataclass(frozen=True)`를 씁니다.

**Django:** 모델은 pk로 해시합니다. 저장 전(pk=None) 인스턴스를
set에 넣으면 `TypeError`가 납니다.

</details>

<details>
<summary>Q6. raise from은 언제 쓰나요? 그리고 else와 finally의 차이는?</summary>

**raise from 정의:** `raise New(...) from e`는 원인 예외를
`__cause__`에 저장해 "직접 원인"으로 연결합니다.

**원리:** except 안에서 그냥 다른 예외를 던져도 `__context__`에 남지만,
traceback 문구가 "처리 중 또 다른 예외 발생"이라 실수와 구분이 안 됩니다.
`from e`는 **의도적 번역**임을 명시하고, `from None`은 원인을 숨깁니다.

**실무:** 저수준 예외(`KeyError`, `JSONDecodeError`, DB 에러)를
도메인 예외(`ConfigError`, `PaymentFailed`)로 바꿀 때 씁니다.
호출자는 도메인 예외만 알면 되고, 원인 정보는 로그에 남습니다.

**else vs finally:** `else`는 try가 **예외 없이 끝났을 때만**,
`finally`는 **항상**(return·예외 포함) 실행됩니다.
`else`는 성공 후 처리를 try 밖으로 빼서 잘못 잡는 것을 막고,
`finally`는 자원 해제용입니다. `finally` 안의 `return`은 예외를 삼키므로 금지입니다.

</details>
