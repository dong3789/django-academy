## 1. 권한은 두 겹: "볼 수 있나" 다음 "해도 되나"

함께하는 목표가 생기면 질문이 둘로 나뉩니다. 첫째, **이 목표가 내 눈에 보여야 하나?**(멤버인가). 둘째, **보이는 목표에 이 행동을 해도 되나?**(방장인가).

이 둘을 한 곳에서 처리하면 구멍이 생깁니다. 특히 목록 API는 object 권한이 **아예 불리지 않습니다**. 그래서 첫 번째는 `get_queryset`, 두 번째는 permission 클래스가 맡습니다.

![권한 두 겹: 요청이 통과하는 길](assets/gif/day46-perm.gif)

**비유:** 아파트 출입문(get_queryset)은 주민만 들여보냅니다. 집 안의 금고(permission)는 그중 집주인만 엽니다. 출입문이 없으면, 금고가 잠겨 있어도 남의 집 구경은 다 합니다.

**결과를 맞혀 보세요:** 권한을 object 단계에만 걸었습니다. 목록을 요청하면 몇 개가 보일까요?

```python-run
goals = [{"id": 1, "members": ["나"]},
         {"id": 2, "members": ["친구"]}]
def can_see(user, g):
    return user in g["members"]
def list_view(user):
    return [g["id"] for g in goals]
print(list_view("나"))
```

<details>
<summary>정답</summary>

`[1, 2]`입니다. `can_see`를 만들어 놓고 목록에선 부르지 않았습니다. DRF도 똑같습니다. `has_object_permission`은 `get_object()`(단건 조회) 때만 불리고, `list`는 `get_queryset()` 결과를 그대로 내보냅니다. 남의 목표 제목이 목록에 다 새어 나갑니다.

</details>

첫 겹: **내가 멤버인 목표만** 꺼냅니다.

```python
class GoalViewSet(viewsets.ModelViewSet):
    serializer_class = GoalSerializer

    def get_queryset(self):
        me = self.request.user
        return Goal.objects.filter(
            memberships__user=me).distinct()
```

`distinct()`는 JOIN 때문에 같은 목표가 두 번 나올 수 있어서 붙입니다. 이렇게 하면 남의 목표 `/goals/2/`는 **404**가 됩니다. 403(금지)이 아니라 404(없음)라서, "그런 목표가 있다"는 사실조차 숨겨집니다.

둘째 겹: 수정·삭제는 **방장만**.

```python
class IsGoalOwner(BasePermission):
    def has_object_permission(
            self, request, view, goal):
        if request.method in SAFE_METHODS:
            return True
        return goal.memberships.filter(
            user=request.user,
            role="owner").exists()
```

`SAFE_METHODS`는 GET·HEAD·OPTIONS(읽기만 하는 요청)입니다. 멤버는 읽기, 방장은 쓰기까지. 첫 겹을 통과한 사람만 여기에 오므로 "멤버인가"는 다시 검사하지 않습니다.

**JS (Node)** — Express에선 보통 쿼리에 조건을 직접 넣습니다.

```javascript
// 범위: 내 목표만 (첫 겹)
const goal = await prisma.goal.findFirst({
  where: { id,
    members: { some: { userId: me } } },
});
if (!goal) return res.sendStatus(404);
```

`findUnique({ where: { id } })`로 꺼낸 뒤 검사를 깜빡하는 실수가 Node에서도 가장 흔합니다. Django는 `get_queryset` 한 곳에 범위를 모아 **모든 액션이 자동으로** 같은 필터를 쓰게 합니다.

> 💡 "보이나"는 get_queryset(목록까지 막힘, 남의 것은 404), "해도 되나"는 has_object_permission.

<details>
<summary>🔍 더 깊이 (면접용)</summary>

**IDOR**(Insecure Direct Object Reference, 아이디만 바꿔 남의 데이터에 접근)는 OWASP API Top 10의 1위(BOLA, Broken Object Level Authorization)입니다. 방어의 정석이 바로 "쿼리 자체를 사용자 범위로 좁히기"입니다.

**404 vs 403:** 존재를 숨겨야 하면 404, 존재가 공개된 자원에 권한만 없으면 403. GitHub도 비공개 저장소에 404를 줍니다.

**쿼리 수 줄이기:** permission에서 매번 `exists()`를 부르면 요청마다 쿼리가 하나 늘어납니다. `get_queryset`에서 내 역할을 붙여 오면 추가 쿼리가 없습니다.

```python
mine = GoalMember.objects.filter(
    goal=OuterRef("pk"), user=me)
qs = qs.annotate(my_role=Subquery(
    mine.values("role")[:1]))
```

그러면 permission은 `goal.my_role == "owner"`만 봅니다. 이 경우 `memberships__user` 필터 대신 `Exists(mine)`로 거르면 `distinct()`도 필요 없습니다.

**create는 object 권한이 없다:** POST 생성 시엔 객체가 아직 없어서 `has_object_permission`이 안 불립니다. "남의 목표에 체크인 생성" 같은 건 `perform_create`나 시리얼라이저에서 대상 목표를 **범위 안의 queryset으로** 다시 찾아 막아야 합니다.

</details>

## 2. 초대 흐름: 추측 불가능한 토큰, 여러 번 눌러도 안전한 수락

친구를 들이는 방법은 두 가지입니다. 아이디로 바로 추가하거나, **초대 링크**를 보내 상대가 수락하게 하거나. 남을 동의 없이 목표에 넣으면 안 되니 링크 방식을 씁니다.

링크에는 **토큰**(비밀 문자열)이 들어갑니다. 토큰이 `/invite/17/`처럼 순서대로라면, 숫자만 바꿔 남의 초대를 훔칠 수 있습니다. 그래서 **추측 불가능**해야 합니다.

**결과를 맞혀 보세요:** 두 방식으로 토큰을 만듭니다. 어느 쪽이 안전할까요?

```python-run
import random, secrets
random.seed(46)
a = random.randint(0, 999999)
b = secrets.token_urlsafe(16)
print(len(str(a)) <= 6, len(b))
```

<details>
<summary>정답</summary>

`True 22`입니다. `random`은 **예측 가능한** 의사난수입니다(시드를 알면 결과를 재현). 게다가 6자리면 100만 번 시도로 다 뚫립니다. `secrets.token_urlsafe(16)`은 운영체제의 암호학적 난수 16바이트(128비트)를 URL에 안전한 22글자로 만든 것이라 사실상 추측이 불가능합니다. 토큰·비밀번호 재설정 링크는 **항상 `secrets`**입니다.

</details>

초대는 별도 모델로 둡니다. 만료일과 누가 만들었는지가 붙으니까요(Day 45의 "관계에 정보가 붙으면 엔티티").

```python
class Invite(models.Model):
    goal = models.ForeignKey(Goal,
        on_delete=models.CASCADE)
    token = models.CharField(max_length=43,
        unique=True, default=new_token)
    expires_at = models.DateTimeField()
```

`new_token`은 `secrets.token_urlsafe(32)`를 돌려주는 함수입니다. `default=`에 **함수 자체**를 넘겨야 행마다 새 토큰이 생깁니다. `default=secrets.token_urlsafe(32)`라고 쓰면 서버 시작 때 한 번만 계산돼 모든 초대가 같은 토큰을 갖습니다.

이제 수락 API입니다. 사용자는 링크를 **두 번** 누르기도 하고, 네트워크가 끊겨 앱이 **재시도**하기도 합니다. 몇 번 불러도 결과가 같아야 합니다. 이걸 **멱등성**(idempotency, Day 38)이라 합니다.

```python
@action(detail=False, methods=["post"],
        url_path="join/(?P<token>[^/]+)")
def join(self, request, token=None):
    inv = get_object_or_404(Invite,
        token=token,
        expires_at__gt=timezone.now())
```

```python
    m, created = GoalMember.objects \
        .get_or_create(goal=inv.goal,
            user=request.user)
    code = 201 if created else 200
    return Response(
        {"goal": inv.goal_id,
         "role": m.role}, status=code)
```

처음 수락하면 **201 Created**, 이미 멤버면 **200 OK**로 같은 결과를 돌려줍니다. 에러를 내지 않으니 화면은 둘 다 "목표로 이동"만 하면 됩니다. 만료됐거나 없는 토큰은 똑같이 404라서, 어느 쪽인지 공격자에게 알려 주지 않습니다.

**JS (Node)**

```javascript
import { randomBytes } from "node:crypto";
const token = randomBytes(32)
  .toString("base64url");
// upsert: 있으면 두고 없으면 생성
const key = { goalId, userId };
await prisma.goalMember.upsert({
  where: { goalId_userId: key },
  create: key, update: {} });
```

`Math.random()`이 Python의 `random`, `crypto.randomBytes`가 `secrets`에 해당합니다.

> 💡 초대 토큰은 secrets로, 수락은 get_or_create로 멱등하게(처음 201, 다시 200).

<details>
<summary>🔍 더 깊이 (면접용)</summary>

**get_or_create도 경쟁한다:** 내부는 "SELECT → 없으면 INSERT"입니다. 두 요청이 동시에 오면 둘 다 SELECT에서 못 찾고 INSERT합니다. 이때 Day 45의 UniqueConstraint가 두 번째를 거절하고, Django는 `IntegrityError`를 잡아 **다시 get**합니다. 즉, get_or_create의 안전성은 **DB 유일 제약이 있을 때만** 보장됩니다. 제약이 없으면 중복 행이 생깁니다.

**토큰을 해시로 저장:** DB가 유출되면 원문 토큰으로 바로 가입할 수 있습니다. 비밀번호처럼 `sha256(token)`만 저장하고, 요청의 토큰을 해시해서 찾으면 유출돼도 안전합니다. 비교할 땐 `hmac.compare_digest`로 **타이밍 공격**(비교 시간 차이로 글자를 맞히는 공격)을 막습니다.

**DB 없는 토큰:** `django.core.signing.TimestampSigner`로 `goal_id`에 서명하면 테이블 없이 만료까지 검사할 수 있습니다. 대신 **개별 취소가 안 됩니다**(키를 바꾸면 전부 무효). 취소·사용 횟수 제한이 필요하면 DB 모델이 맞습니다.

**정원 제한:** "멤버 최대 10명"은 셈과 추가 사이에 경쟁이 있습니다. `select_for_update()`로 Goal 행을 잠근 뒤 세고 추가합니다(Day 28).

</details>

## 3. 체크인 API: 하루 한 번을 멱등하게, 화면이 쓰기 좋은 응답으로

체크인은 앱에서 **가장 자주 누르는 버튼**입니다. 지하철에서 누르다 끊기고, 다시 누르고, 두 번 누릅니다. 그래서 규칙을 정합니다. "한 사람은 한 목표에 **하루 한 번** 체크인, 다시 보내면 그날 값을 **덮어쓴다**."

**결과를 맞혀 보세요:** 네트워크가 불안해 같은 체크인을 세 번 보냈습니다. 두 방식의 합계는?

```python-run
log, by_day = [], {}
def create(day, n):
    log.append(n)
def upsert(day, n):
    by_day[day] = n
for _ in range(3):
    create("11-28", 30); upsert("11-28", 30)
print(sum(log), sum(by_day.values()))
```

<details>
<summary>정답</summary>

`90 30`입니다. 매번 새로 만드는 방식은 재시도마다 기록이 쌓여 피아노 30분이 90분이 됩니다. 날짜를 키로 덮어쓰는 방식은 몇 번 보내도 30입니다. **"하루 한 번"이라는 업무 규칙이 그대로 멱등성 키**가 됩니다.

</details>

DB에는 Day 45의 `(goal, user, day)` 유일 제약이 이미 있습니다. 뷰는 `update_or_create`로 그 키를 씁니다.

```python
def perform_create(self, ser):
    goal = get_object_or_404(
        self.member_goals(),
        pk=self.kwargs["goal_pk"])
```

```python
    obj, new = CheckIn.objects \
        .update_or_create(goal=goal,
            user=self.request.user,
            day=timezone.localdate(),
            defaults=ser.validated_data)
```

두 가지를 눈여겨보세요. `member_goals()`(1장의 범위 queryset)에서 목표를 찾으니 **남의 목표엔 체크인할 수 없습니다**(create엔 object 권한이 없어서 여기서 막습니다). `day`는 클라이언트가 보내지 않고 **서버가 정합니다**. 클라이언트가 날짜를 보내면 어제·내일 체크인을 조작할 수 있습니다.

다음은 **응답 모양**입니다. 체크인 직후 화면은 "이번 주 진행률"과 "연속 일수"를 다시 그려야 합니다. 응답에 체크인만 주면 앱이 목표를 **한 번 더** 요청해야 합니다.

```json
{
  "checkin": {"day": "2026-11-28",
              "amount": 30},
  "goal": {"id": 7, "week_done": 120,
           "week_target": 150, "streak": 4}
}
```

이렇게 **화면이 다음에 필요한 값**을 함께 돌려주면 왕복이 한 번 줄어듭니다. 값은 Day 45처럼 저장하지 않고 `annotate`로 계산합니다.

에러도 모양을 통일합니다. 화면은 `field`를 보고 해당 입력칸 아래에 빨간 글씨를 띄웁니다.

```json
{"error": "validation",
 "fields": {
   "amount": ["0보다 커야 합니다."]}}
```

**JS (Node)** — 같은 생각을 Express로.

```javascript
const c = await prisma.checkIn.upsert({
  where: { goalId_userId_day:
    { goalId, userId: me, day: today() } },
  create: { goalId, userId: me,
    day: today(), amount },
  update: { amount },
});
```

**비유:** 출석부는 날짜 칸이 하나뿐입니다. 같은 날 두 번 도장을 찍어도 칸은 하나라, 출석이 두 번이 되지 않습니다.

> 💡 업무 규칙(하루 한 번)을 유일 키로 → update_or_create로 멱등. 날짜는 서버가, 응답엔 화면이 다음에 그릴 값까지.

<details>
<summary>🔍 더 깊이 (면접용)</summary>

**자연 키가 없을 때: Idempotency-Key.** 결제처럼 "하루 한 번" 같은 키가 없으면 클라이언트가 요청마다 UUID를 `Idempotency-Key` 헤더로 보냅니다. 서버는 (사용자, 키) → 응답을 저장해 두고, 같은 키가 다시 오면 **저장된 응답을 그대로** 돌려줍니다. Stripe API가 이 방식입니다.

**PUT vs POST:** HTTP 명세상 PUT·DELETE는 멱등, POST는 아닙니다. 그래서 `PUT /goals/7/checkins/2026-11-28/`처럼 **날짜를 URL 자원으로** 만드는 설계도 있습니다. 둘 다 정답이며, 면접에선 "왜 그렇게 정했는지"를 말하면 됩니다.

**DRF 에러 모양 바꾸기:** `REST_FRAMEWORK["EXCEPTION_HANDLER"]`에 함수를 지정하고, 기본 `exception_handler` 결과를 감싸 `{"error", "fields"}`로 바꿉니다. 표준을 원하면 RFC 9457(Problem Details, `application/problem+json`)을 따릅니다.

**streak 계산과 시간대:** "오늘"은 사용자 시간대 기준입니다(Day 45). 서울 사용자가 0시 30분에 체크인하면 UTC로는 전날입니다. `timezone.localdate()`는 **현재 활성화된 시간대**를 쓰므로, 미들웨어에서 사용자 시간대를 `timezone.activate()`해야 정확합니다.

**낙관적 UI:** 앱은 응답을 기다리지 않고 버튼을 먼저 "완료"로 바꾼 뒤, 실패하면 되돌립니다. 서버가 멱등하니 재시도해도 안전해서 이 방식이 가능합니다.

</details>

## 연습문제

**1.** 멤버 목록 API `GET /goals/7/members/`를 만듭니다. 멤버는 누구나 볼 수 있고, 멤버가 아니면 404여야 합니다. 핵심 코드를 쓰세요.

<details>
<summary>정답</summary>

```python
@action(detail=True, methods=["get"])
def members(self, request, pk=None):
    goal = self.get_object()
    qs = goal.memberships \
        .select_related("user")
    ser = MemberSerializer(qs, many=True)
    return Response(ser.data)
```

`self.get_object()`는 **`get_queryset()` 안에서** pk를 찾습니다. 그래서 멤버가 아니면 자동으로 404입니다. 직접 `Goal.objects.get(pk=pk)`를 쓰면 범위 필터를 건너뛰어 아무나 볼 수 있게 됩니다. `select_related("user")`는 멤버마다 User 쿼리가 나가는 N+1을 막습니다(Day 26).

</details>

**2.** 방장이 멤버를 내보내는 API를 만듭니다. 방장만 할 수 있고, 방장 **자신**은 내보낼 수 없어야 합니다(방장이 없는 목표 방지). 핵심 코드를 쓰세요.

<details>
<summary>정답</summary>

```python
@action(detail=True, methods=["delete"],
        url_path="members/(?P<uid>[0-9]+)",
        permission_classes=[IsGoalOwner])
def kick(self, request, pk=None, uid=None):
    goal = self.get_object()
    get_object_or_404(goal.memberships,
        user_id=uid, role="member").delete()
    return Response(status=204)
```

DELETE는 SAFE_METHODS가 아니므로 `IsGoalOwner`가 방장인지 봅니다(`get_object()` 호출 시점에). `role="member"`로 찾으니 방장 행은 애초에 안 잡혀 404가 됩니다. "방장은 자기 자신을 못 내보낸다"를 if문 대신 **조회 조건**으로 표현한 것입니다. 삭제 성공은 본문 없는 **204 No Content**입니다.

</details>

**3.** 아래 체크인 시리얼라이저의 보안 문제 두 가지를 찾고 고치세요.

```python
class CheckInSerializer(ModelSerializer):
    class Meta:
        model = CheckIn
        fields = "__all__"
```

<details>
<summary>정답</summary>

`"__all__"`이라 `user`와 `day`(그리고 `goal`)를 **클라이언트가 보낼 수 있습니다**. (1) `user`를 친구 id로 보내면 남의 이름으로 체크인합니다. (2) `day`를 바꾸면 지난 날짜를 채워 streak를 조작합니다. 이런 걸 **Mass Assignment**(대량 할당) 취약점이라 합니다.

```python
class CheckInSerializer(ModelSerializer):
    class Meta:
        model = CheckIn
        fields = ["id", "day", "amount"]
        read_only_fields = ["day"]
```

입력은 `amount`만 받고, `goal`·`user`·`day`는 뷰가 정합니다(3장의 `perform_create`). 필드는 **허용 목록**으로 명시하는 게 원칙입니다. 모델에 필드가 추가될 때 실수로 노출되지 않습니다.

</details>

## 면접 질문

**Q1.** "사용자가 다른 사람의 리소스에 접근하지 못하게 DRF에서 어떻게 막나요?"

<details>
<summary>모범 답안</summary>

두 겹으로 막습니다. 첫째, `get_queryset()`에서 **요청 사용자의 범위로 쿼리 자체를 좁힙니다**. 예를 들어 `Goal.objects.filter(memberships__user=request.user)`입니다. 이러면 목록에도 안 보이고, 상세는 `get_object()`가 이 queryset 안에서 찾으므로 남의 것은 404가 됩니다. 존재 자체를 숨길 수 있습니다.

둘째, 보이는 객체 안에서 행동 권한은 `has_object_permission`으로 봅니다(방장만 수정). 주의할 점은 이 메서드가 **목록과 생성에선 불리지 않는다**는 것입니다. 그래서 생성 시 대상(목표)은 범위 queryset에서 다시 찾아야 합니다.

이게 OWASP API 1위인 BOLA(IDOR) 방어의 정석이고, 테스트로는 "다른 사용자로 로그인해 404가 나는지"를 꼭 넣습니다(Day 33).

</details>

**Q2.** "멱등성이 무엇이고, API에서 어떻게 보장했나요?"

<details>
<summary>모범 답안</summary>

같은 요청을 여러 번 보내도 **결과가 한 번 보낸 것과 같은** 성질입니다. 모바일은 재시도와 중복 클릭이 흔해서 쓰기 API에 꼭 필요합니다.

Goals에선 업무 규칙을 키로 썼습니다. 체크인은 "사용자·목표·날짜당 하나"라 DB에 `(goal, user, day)` 유일 제약을 걸고 `update_or_create`로 덮어씁니다. 초대 수락은 `get_or_create`로 처음엔 201, 이미 멤버면 200을 돌려줍니다. 이 메서드들은 동시 요청 시 **DB 유일 제약이 있어야** 안전합니다.

자연 키가 없는 결제 같은 경우엔 클라이언트가 `Idempotency-Key` 헤더를 보내고, 서버가 키별 응답을 저장해 재요청에 같은 응답을 돌려줍니다.

</details>

## 오늘 정리

- **권한 두 겹**: get_queryset으로 "내 것만"(목록까지, 남의 것은 404), permission으로 "방장만".
- **초대**: 토큰은 `secrets`, 수락은 get_or_create로 멱등(201/200), 만료·없음은 같은 404.
- **체크인**: 유일 키 + update_or_create, 날짜는 서버가, 응답엔 화면이 다음에 그릴 값까지.
