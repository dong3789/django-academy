</details>

## 1. 집계: DB에게 세게 하자

대시보드에 "목표마다 체크인 몇 번?"을 보여 주고 싶습니다. 체크인을 전부 Python으로 가져와 세면, 데이터가 많을수록 메모리와 시간이 낭비됩니다.

DB는 세기·더하기·평균을 아주 잘합니다. **집계**(aggregation)는 이 계산을 SQL의 `COUNT`·`SUM`·`AVG`로 DB에 맡기는 것입니다. Django에는 두 가지 도구가 있습니다.

| 메서드 | 결과 | SQL |
|---|---|---|
| `aggregate()` | dict 하나 | `SELECT COUNT(*)` |
| `annotate()` | 행마다 값 추가 | `GROUP BY` |

**결과를 맞혀 보세요:** 둘의 반환값은 각각 어떤 모양일까요?

```python
from django.db.models import Count
CheckIn.objects.aggregate(n=Count("id"))
Goal.objects.annotate(n=Count("checkins"))
```

<details>
<summary>정답</summary>

- `aggregate` → **dict 하나**: `{"n": 1532}`. 전체 체크인 수입니다.
- `annotate` → **QuerySet**. 각 Goal 객체에 `n` 속성이 붙습니다: `goal.n == 12`.

`aggregate`는 "표 전체를 한 줄로 요약", `annotate`는 "각 줄에 요약 칸 추가"입니다.

</details>

**비유:** `aggregate`는 "반 전체 평균 점수", `annotate`는 "학생 명단 옆에 각자 평균 점수 칸 추가"입니다.

SQL의 `GROUP BY`가 하는 일을 순수 Python으로 흉내 내 봅시다.

```python-run
from collections import Counter
checkins = ["독서", "운동", "독서",
            "독서", "운동", "기타"]
by_goal = Counter(checkins)
print(dict(by_goal))
print("전체:", sum(by_goal.values()))
# 출력: {'독서': 3, '운동': 2, '기타': 1}
# 출력: 전체: 6
```

`Counter`가 annotate, `sum`이 aggregate에 해당합니다. 다만 DB는 이걸 **데이터를 옮기지 않고** 해냅니다.

**JS (Node)** — Prisma의 groupBy

```javascript
await prisma.checkIn.groupBy({
  by: ["goalId"],
  _count: { _all: true },
});
```

**Python** — Goals 대시보드 쿼리 (로컬)

```python
from django.db.models import Count, Q
week = now() - timedelta(days=7)
goals = Goal.objects.annotate(
    total=Count("checkins"),
    recent=Count("checkins", filter=Q(
        checkins__created__gte=week)),
).order_by("-recent")
```

`filter=Q(...)`로 "조건부 개수"도 한 쿼리에 셉니다. 템플릿이나 시리얼라이저에서 `g.total`, `g.recent`를 바로 씁니다.

> 💡 세기·합계는 DB에 맡긴다. 전체 요약은 `aggregate`, 행마다 요약은 `annotate`.

<details>
<summary>🔍 더 깊이 (면접용)</summary>

- **annotate 두 개가 JOIN을 부풀린다.** `annotate(c=Count("checkins"), t=Count("tags"))`는 두 테이블을 동시에 JOIN해서 행이 곱해집니다(체크인 5 × 태그 3 = 15). `Count(..., distinct=True)`나 `Subquery`로 고칩니다. `Sum`은 distinct로도 못 고치니 서브쿼리를 씁니다.
- **순서가 의미를 바꾼다.** `filter()` 뒤 `annotate()`는 거른 뒤 셉니다. `annotate()` 뒤 `filter(n__gt=3)`는 SQL의 `HAVING`이 됩니다.
- `values("owner").annotate(n=Count("id"))`는 owner별 GROUP BY입니다. 모델의 `Meta.ordering`이 GROUP BY에 끼어들 수 있어 `order_by()`로 비우는 습관이 안전합니다.
- 빈 집합의 `Sum`은 `None`입니다. `Coalesce(Sum("x"), 0)` 또는 Django 4.0+의 `Sum("x", default=0)`.

</details>

## 2. bulk 연산: 왕복을 줄여라

사용자가 예전 기록 CSV(체크인 1000개)를 올렸습니다. 루프에서 `save()`를 부르면 **INSERT 1000번**, 즉 DB와 1000번 왕복합니다.

느린 이유는 SQL 자체보다 **네트워크 왕복**(round trip)입니다. 왕복 한 번이 1ms만 걸려도 1000번이면 1초입니다.

**결과를 맞혀 보세요:** 아래 두 코드는 쿼리를 몇 번 보낼까요?

```python
for row in rows:
    CheckIn.objects.create(**row)

CheckIn.objects.bulk_create(
    [CheckIn(**r) for r in rows],
    batch_size=500)
```

<details>
<summary>정답</summary>

1000행 기준으로 첫 번째는 **1000번**, 두 번째는 **2번**입니다. `bulk_create`는 `INSERT ... VALUES (..), (..), ...`처럼 여러 행을 한 문장에 담고, `batch_size=500`이면 500개씩 나눠 보냅니다.

</details>

![save 루프 vs bulk_create](assets/gif/day30-bulk.gif)

**비유:** 택배 1000개를 오토바이로 하나씩 나르기 vs 트럭 두 번에 싣기입니다.

수정도 마찬가지입니다. 상황에 맞게 셋 중 고릅니다.

| 도구 | 언제 | 쿼리 |
|---|---|---|
| `bulk_create` | 새 행 여러 개 | 배치당 1 |
| `bulk_update` | 행마다 다른 값 | 배치당 1 |
| `qs.update()` | 모두 같은 규칙 | 1 |

```python
# 모두 같은 규칙: UPDATE 한 문장
Goal.objects.filter(owner=u).update(
    streak=F("streak") + 1)

# 행마다 다른 값
for g in goals:
    g.score = calc(g)
Goal.objects.bulk_update(goals, ["score"])
```

`sqlite3`로 "하나씩 vs 한 번에"를 직접 재 봅시다. 여기선 DB가 같은 메모리 안에 있어 **네트워크 왕복이 없는** 가장 유리한 조건입니다.

```python-run
import sqlite3, time
db = sqlite3.connect(":memory:")
db.execute("create table c(goal int)")
t = time.time()
sql = "insert into c values (?)"
for i in range(20000):
    db.execute(sql, (i,))
print("하나씩:", round(time.time() - t, 3))
```

```python-run
import sqlite3, time
db = sqlite3.connect(":memory:")
db.execute("create table c(goal int)")
t = time.time()
db.executemany("insert into c values (?)",
               [(i,) for i in range(20000)])
print("한 번에:", round(time.time() - t, 3))
```

<details>
<summary>결과 해설</summary>

네트워크가 없는데도 보통 "한 번에"가 조금 더 빠릅니다 (숫자는 기기마다 다름). 문장마다 드는 준비·호출 비용이 줄기 때문입니다. 실제 서버에선 여기에 **왕복 1회당 지연(보통 수백 μs~수 ms)**이 1000번 곱해지므로 차이가 수십~수백 배로 벌어집니다.

</details>

**JS (Node)** — 같은 아이디어

```javascript
await prisma.checkIn.createMany({
  data: rows,
  skipDuplicates: true,
});
```

**주의할 점이 하나 있습니다.** bulk 연산은 `save()`를 부르지 않습니다. 그래서 `save()`를 오버라이드한 로직, `pre_save`/`post_save` 시그널, `auto_now` 필드 갱신이 **실행되지 않습니다**.

> 💡 많이 넣고 고칠 땐 `bulk_create`·`bulk_update`·`update()`. 단, `save()`·시그널은 건너뛴다.

<details>
<summary>🔍 더 깊이 (면접용)</summary>

- **PK 반환:** `bulk_create` 뒤 객체에 `pk`가 채워지는 DB는 PostgreSQL, MariaDB 10.5+, SQLite 3.35+입니다. MySQL에선 `None`이라 이어서 관계를 만들 때 주의합니다.
- **upsert:** Django 4.1+ `bulk_create(objs, update_conflicts=True, unique_fields=["goal","date"], update_fields=["note"])`는 `ON CONFLICT DO UPDATE`가 됩니다. `ignore_conflicts=True`는 중복을 조용히 버립니다(이때 PK는 안 채워짐).
- `bulk_update`는 `CASE WHEN id=1 THEN ... END` SQL을 만듭니다. 행이 아주 많으면 SQL이 거대해지니 `batch_size`를 줍니다.
- `update()`는 영향받은 **행 수**를 반환합니다. `auto_now` 필드는 직접 `updated=now()`를 넣어야 합니다.
- 대량 작업은 `transaction.atomic()`으로 감싸 "절반만 들어간" 상태를 막습니다 (Day 28).
- 아주 큰 데이터(수십만 행)는 PostgreSQL `COPY`가 가장 빠릅니다.

</details>

## 3. raw SQL: 탈출구, 그러나 안전하게

ORM으로 표현하기 어려운 쿼리도 있습니다. 윈도 함수, DB 전용 기능, 아주 복잡한 리포트가 그렇습니다. 이럴 때 Django는 **raw SQL** 탈출구를 줍니다.

가장 큰 위험은 **SQL 인젝션**(사용자 입력이 SQL 명령으로 해석되는 공격)입니다. 규칙은 하나입니다. **값은 절대 문자열로 이어 붙이지 말고, 파라미터로 따로 넘긴다.**

**결과를 맞혀 보세요:** 검색어로 `x' OR '1'='1`이 들어오면?

```python
q = request.GET["q"]
sql = f"SELECT * FROM goal " \
      f"WHERE title = '{q}'"
Goal.objects.raw(sql)
```

<details>
<summary>정답</summary>

SQL이 `WHERE title = 'x' OR '1'='1'`이 되어 **모든 사용자의 목표**가 나옵니다. 입력이 데이터가 아니라 SQL 문법의 일부가 된 것입니다. 더 나쁜 입력이면 데이터를 지울 수도 있습니다.

</details>

직접 확인해 봅시다.

```python-run
import sqlite3
db = sqlite3.connect(":memory:")
db.execute("create table g(t text)")
db.execute("insert into g values ('비밀')")
q = "x' OR '1'='1"
w = "select t from g where t = "
print(db.execute(w + f"'{q}'").fetchall())
print(db.execute(w + "?", (q,)).fetchall())
```

<details>
<summary>출력과 해설</summary>

첫 줄은 `[('비밀',)]` — 조건과 상관없이 전부 새어 나옵니다. 둘째 줄은 `[]`입니다. 파라미터로 넘기면 DB가 `q`를 **그냥 글자 하나의 값**으로 다루기 때문입니다.

</details>

Django에서 안전한 raw SQL은 두 가지 모양입니다.

```python
# 1) 모델 객체로 받기 (PK 컬럼 필수)
Goal.objects.raw(
    "SELECT * FROM goals_goal"
    " WHERE title = %s", [q])
```

```python
# 2) 모델과 무관한 결과 (로컬)
from django.db import connection
with connection.cursor() as cur:
    cur.execute(SQL, [user.id])
    rows = cur.fetchall()
```

자리표시자는 DB 종류와 상관없이 `%s`입니다. 따옴표로 감싸지 않습니다(`'%s'` ❌).

**JS (Node)** — pg도 같은 원칙

```javascript
await pool.query(
  "SELECT * FROM goal WHERE title = $1",
  [q]
);
```

**비유:** 은행 서식의 "금액" 칸에 무엇을 적든 그건 금액일 뿐, "모든 계좌 출금"이라는 명령이 되지 않습니다. 파라미터가 바로 그 칸입니다.

> 💡 raw SQL은 마지막 수단. 쓰더라도 값은 항상 `%s` + 파라미터 리스트로.

<details>
<summary>🔍 더 깊이 (면접용)</summary>

- 탈출구는 단계가 있습니다: ORM 표현식(`F`, `Func`, `Window`, `Subquery`) → `RawSQL` 표현식 → `.raw()` → `connection.cursor()`. 위쪽일수록 ORM 기능(체이닝·필터)을 더 유지합니다.
- `.raw()`는 lazy이고, PK 컬럼이 결과에 없으면 `FieldDoesNotExist` 에러가 납니다 (Django 3.x 이전은 `InvalidQuery`). 모델에 없는 컬럼은 속성으로 붙습니다.
- **파라미터로 못 넣는 것:** 테이블·컬럼 이름, `ORDER BY` 방향. 이런 건 화이트리스트(`if col not in {"title","created"}`)로 검증한 뒤 넣습니다.
- `.extra()`는 폐기 예정 API이니 쓰지 않습니다.
- `cursor.fetchall()`은 튜플 리스트입니다. dict가 필요하면 `cursor.description`의 컬럼명과 `zip`합니다.

</details>

## 연습문제

**1.** 사용자별로 "완료한 목표 수"와 "전체 목표 수"를 한 쿼리로 가져오세요. (`Goal`에 `owner` FK, `done` 불리언)

<details>
<summary>정답</summary>

```python
from django.db.models import Count, Q
stats = (Goal.objects
    .values("owner")
    .annotate(
        total=Count("id"),
        done=Count("id",
                   filter=Q(done=True)))
    .order_by())
```

`values("owner")` 뒤 `annotate`는 owner별 `GROUP BY`가 됩니다. 결과는 `{"owner": 1, "total": 5, "done": 2}` 같은 dict들입니다. `order_by()`로 기본 정렬을 비워 GROUP BY가 깨지지 않게 합니다.

</details>

**2.** CSV 체크인 3000개(`rows`: `goal_id`·`date`·`note` 키를 가진 dict 리스트)를 저장하되, 같은 (목표, 날짜)가 이미 있으면 메모만 덮어쓰게 하세요. 중간에 실패하면 전부 취소돼야 합니다. (Django 4.1+, `(goal, date)` 유니크 제약 있음)

<details>
<summary>정답</summary>

```python
objs = [CheckIn(**r) for r in rows]
with transaction.atomic():
    CheckIn.objects.bulk_create(
        objs, batch_size=500,
        update_conflicts=True,
        unique_fields=["goal", "date"],
        update_fields=["note"])
```

`update_conflicts`가 `ON CONFLICT ... DO UPDATE`(upsert)를 만듭니다. `atomic`으로 감싸서 6개 배치 중 하나라도 실패하면 모두 롤백됩니다. `unique_fields`에 맞는 유니크 제약이 DB에 있어야 합니다.

</details>

**3.** 아래 코드의 문제 두 가지를 찾고 고치세요.

```python
col = request.GET["sort"]
cur.execute(
  f"SELECT * FROM goal ORDER BY {col}")
```

<details>
<summary>정답</summary>

1) 사용자 입력을 SQL에 이어 붙여 **인젝션** 위험이 있습니다. 2) 컬럼 이름은 `%s` 파라미터로 넣을 수 **없습니다**(값이 아니라 식별자라서). 그래서 화이트리스트로 검증합니다.

```python
ALLOWED = {"title", "created"}
col = request.GET.get("sort", "created")
if col not in ALLOWED:
    col = "created"
cur.execute(
  f"SELECT * FROM goal ORDER BY {col}")
```

사실 이 경우는 ORM의 `Goal.objects.order_by(col)`에 검증된 값을 넘기는 편이 더 간단합니다.

</details>

## 면접 질문

**Q1. `aggregate`와 `annotate`의 차이, 그리고 annotate를 여러 개 쓸 때 주의점은?**

<details>
<summary>모범 답안</summary>

`aggregate`는 QuerySet 전체를 하나로 요약해 dict를 반환하고, `annotate`는 각 행에 집계 값을 붙여 QuerySet을 반환합니다(SQL `GROUP BY`). annotate 뒤의 filter는 `HAVING`, 앞의 filter는 `WHERE`가 됩니다.

서로 다른 다대일 관계를 동시에 annotate하면 JOIN이 겹치며 행이 곱해져 개수가 부풀려집니다. `Count(distinct=True)`로 막거나, `Sum`처럼 distinct로 해결 안 되는 경우 `Subquery`로 각각 따로 집계합니다. 쿼리는 `str(qs.query)`나 debug toolbar로 확인합니다.

</details>

**Q2. 대량 데이터를 넣을 때 `save()` 루프 대신 `bulk_create`를 쓰는 이유와 트레이드오프는?**

<details>
<summary>모범 답안</summary>

`save()` 루프는 행마다 INSERT와 네트워크 왕복이 생겨 N번의 쿼리가 나갑니다. `bulk_create`는 여러 행을 한 INSERT에 묶어 `batch_size` 단위로 보내므로 쿼리 수가 N/batch로 줄어듭니다.

트레이드오프는 `save()` 오버라이드, `pre_save`/`post_save` 시그널, 일부 필드 자동 처리가 실행되지 않는다는 점입니다. MySQL 등에선 생성된 PK가 객체에 안 채워집니다. 그래서 부수 효과가 필요하면 따로 처리하고, 전체를 `atomic`으로 감싸 부분 저장을 막습니다. 아주 큰 적재는 PostgreSQL `COPY`도 고려합니다.

</details>
