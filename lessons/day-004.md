# Day 4 · 클래스·던더 메서드·데이터클래스

> 목표: Python 클래스가 **JS의 prototype/class와 어디가 같고 어디가 다른지** 정확히 말할 수 있고, `self`·클래스/인스턴스 속성·`super()`·MRO·던더 메서드·`dataclass`를 실무(Django 모델·DRF 시리얼라이저 읽기) 수준으로 다룬다. CS 파트에서는 **속성 탐색 알고리즘과 객체 메모리 레이아웃(`__dict__` vs `__slots__`)** 을 해시테이블 관점에서 본다.

## 1. 기본형 — JS class와 나란히

```javascript
class User {
  static count = 0;            // 클래스(정적) 필드
  constructor(name) {
    this.name = name;          // 인스턴스 필드
    User.count++;
  }
  greet() { return `hi ${this.name}`; }
}
const u = new User("dh");
```
```python
class User:
    count = 0                   # 클래스 속성 (모든 인스턴스가 공유)

    def __init__(self, name):   # 생성자가 아니라 "초기화자"
        self.name = name        # 인스턴스 속성
        User.count += 1

    def greet(self):
        return f"hi {self.name}"

u = User("dh")                  # new 없음
u.greet()                       # 'hi dh'
User.greet(u)                   # 똑같음 — 메서드는 그냥 "첫 인자가 self인 함수"
```

| 개념 | JS | Python |
|---|---|---|
| 인스턴스 참조 | 암묵적 `this` (호출 방식에 따라 바뀜) | **명시적 첫 인자 `self`** (이름은 관례) |
| 생성 | `new` + `constructor` | `Cls()` → `__new__`(생성) → `__init__`(초기화) |
| 정적 멤버 | `static` | `@classmethod` / `@staticmethod` / 클래스 속성 |
| private | `#field` (진짜 private) | `_x`(관례), `__x`(이름 맹글링 — 보호용이지 보안 아님) |
| 상속 | 단일 상속 + prototype chain | **다중 상속** + MRO(C3) |
| getter | `get x()` | `@property` |

### `this` 문제가 없는 이유: 바운드 메서드

JS에서 `const f = u.greet; f()` 하면 `this`가 날아가죠. Python은 `u.greet`에 접근하는 순간 **함수 + 인스턴스를 묶은 bound method 객체**가 만들어집니다.

```python
f = u.greet
f()                 # 'hi dh' — self가 이미 묶여 있음
f.__self__ is u     # True
f.__func__ is User.greet  # True
```

이 묶는 동작이 **디스크립터 프로토콜**(함수 객체의 `__get__`)입니다. 6절에서 다시 봅니다. 그래서 콜백으로 메서드를 넘길 때 `bind`가 필요 없습니다.

## 2. 클래스 속성 vs 인스턴스 속성 — 실무 버그 1순위

```python
class Cart:
    items = []                  # ❌ 클래스 속성 = 모든 Cart가 공유

    def add(self, x):
        self.items.append(x)    # self.items → 인스턴스에 없으니 클래스에서 찾음 → 공유 리스트 변경

a, b = Cart(), Cart()
a.add(1)
b.items                         # [1]  😱
```

```python
class Cart:
    def __init__(self):
        self.items = []         # ✅ 인스턴스마다 새 리스트
```

규칙: **읽기**는 인스턴스 → 클래스 → 부모 순으로 찾고, **대입**(`self.x = ...`)은 항상 인스턴스 `__dict__`에 씁니다. 그래서 `self.count += 1`은 클래스 속성을 바꾸는 게 아니라 인스턴스에 **그림자 속성**을 새로 만듭니다(Day 3의 "대입은 로컬 바인딩"과 같은 결).

```python
class C:
    n = 0
c = C()
c.n += 1        # c.n = C.n + 1 → 인스턴스에 n 생성
C.n, c.n        # (0, 1)
```

> Django 연결: `class Post(models.Model): title = models.CharField(...)`의 `title`은 클래스 속성(필드 정의)이지만, 메타클래스가 이를 수집해 **인스턴스마다 실제 값**을 갖게 바꿉니다. "클래스 속성 = 스키마 선언"이라는 Django 문법이 왜 가능한지 Week 3에서 이어집니다.

## 3. `@property`, `@classmethod`, `@staticmethod`

```python
from datetime import date

class Member:
    def __init__(self, name, birth_year):
        self.name = name
        self._birth_year = birth_year

    @property
    def age(self):                       # u.age 처럼 속성처럼 읽음 (괄호 X)
        return date.today().year - self._birth_year

    @property
    def birth_year(self):
        return self._birth_year

    @birth_year.setter
    def birth_year(self, v):
        if v < 1900:
            raise ValueError("invalid year")
        self._birth_year = v

    @classmethod
    def from_dict(cls, d):               # 대체 생성자 — cls라서 서브클래스도 올바르게 생성
        return cls(d["name"], d["birth_year"])

    @staticmethod
    def is_valid_name(s):                # self/cls 둘 다 필요 없는 유틸
        return bool(s.strip())
```

- **`classmethod`**: 첫 인자가 클래스. "팩토리/대체 생성자"에 씁니다. `Member.from_dict` 를 서브클래스에서 호출하면 서브클래스 인스턴스가 나옵니다 — `staticmethod`로 짜면 이게 깨집니다.
- **`property`**: 처음엔 public 속성으로 두고, 나중에 검증이 필요해지면 **호출부를 안 바꾸고** property로 교체할 수 있습니다. 그래서 Python에선 Java식 `getX()/setX()`를 미리 만들지 않습니다.

> Django 연결: `Model.objects`(매니저), `@property def full_name`, `@classmethod def create(cls, ...)` 패턴이 모델 코드에 아주 흔합니다.

## 4. 상속 · `super()` · MRO

```python
class Animal:
    def __init__(self, name):
        self.name = name
    def speak(self):
        return "..."

class Dog(Animal):
    def __init__(self, name, breed):
        super().__init__(name)      # JS: super(name)
        self.breed = breed
    def speak(self):
        return "멍"

isinstance(Dog("a", "b"), Animal)   # True
issubclass(Dog, Animal)             # True
```

### 다중 상속과 MRO

```python
class Base:
    def hello(self): return ["Base"]

class A(Base):
    def hello(self): return ["A"] + super().hello()

class B(Base):
    def hello(self): return ["B"] + super().hello()

class C(A, B):
    def hello(self): return ["C"] + super().hello()

C().hello()        # ['C', 'A', 'B', 'Base']
C.__mro__          # (C, A, B, Base, object)
```

핵심: **`super()`는 "부모"가 아니라 "MRO상 다음 클래스"** 입니다. `A.hello` 안의 `super()`는 `C`의 MRO 기준으로 `B`를 가리킵니다(`Base`가 아님!). 덕분에 다이아몬드 상속에서도 `Base.hello`가 **한 번만** 호출됩니다. 이것이 **협력적 다중 상속(cooperative multiple inheritance)** 이고, 모든 클래스가 `super()`를 일관되게 불러야 동작합니다.

> Django/DRF 연결: CBV와 DRF는 **믹스인** 덩어리입니다. `class PostViewSet(mixins.ListModelMixin, mixins.CreateModelMixin, GenericViewSet)` — 믹스인을 왼쪽에, 베이스를 오른쪽에 두는 순서 규칙이 바로 MRO 때문입니다. `LoginRequiredMixin`이 반드시 **맨 왼쪽**이어야 하는 이유도 같습니다.

## 5. 던더(dunder) 메서드 — 파이썬의 프로토콜

`__x__` 메서드는 **언어 문법에 연결된 훅**입니다. JS의 `Symbol.iterator`, `toString`, `valueOf`, `Symbol.toPrimitive`의 훨씬 넓은 버전이라고 보면 됩니다.

| 문법 / 내장 | 호출되는 던더 | JS 비슷한 것 |
|---|---|---|
| `repr(x)`, 디버거 출력 | `__repr__` | `util.inspect.custom` |
| `str(x)`, `print(x)`, f-string | `__str__` | `toString()` |
| `a == b` | `__eq__` | (없음 — `===`는 항상 참조 비교) |
| `hash(x)`, dict 키, set 원소 | `__hash__` | (Map 키는 참조 기준) |
| `a < b`, `sorted` | `__lt__` 등 | (없음) |
| `len(x)` | `__len__` | `.length` |
| `x[i]`, `x[k] = v` | `__getitem__` / `__setitem__` | Proxy |
| `for v in x` | `__iter__` (없으면 `__getitem__`) | `[Symbol.iterator]` |
| `v in x` | `__contains__` | `.includes()` |
| `x(...)` | `__call__` | 함수 자체 |
| `a + b` | `__add__` / `__radd__` | (연산자 오버로딩 없음) |
| `with x:` | `__enter__` / `__exit__` | (Day 8) |
| `bool(x)`, `if x:` | `__bool__` → 없으면 `__len__` | truthiness 규칙 고정 |

```python
class Money:
    def __init__(self, amount, currency="KRW"):
        self.amount = amount
        self.currency = currency

    def __repr__(self):                         # 개발자용: 가능하면 재생성 가능한 형태
        return f"Money({self.amount!r}, {self.currency!r})"

    def __str__(self):                          # 사용자용
        return f"{self.amount:,} {self.currency}"

    def __eq__(self, other):
        if not isinstance(other, Money):
            return NotImplemented               # False가 아니라 NotImplemented!
        return (self.amount, self.currency) == (other.amount, other.currency)

    def __hash__(self):                         # __eq__를 정의하면 __hash__는 None이 됨 → 직접 정의
        return hash((self.amount, self.currency))

    def __add__(self, other):
        if not isinstance(other, Money) or other.currency != self.currency:
            return NotImplemented
        return Money(self.amount + other.amount, self.currency)

    def __radd__(self, other):                  # sum()이 0 + Money 로 시작하므로 필요
        if other == 0:
            return self
        return NotImplemented

    def __bool__(self):
        return self.amount != 0

m = Money(1000) + Money(500)
print(m)                                        # 1,500 KRW
sum([Money(1), Money(2)])                       # Money(3, 'KRW')
{Money(1), Money(1)}                            # 원소 1개
```

### 반드시 기억할 규칙 3개

1. **`__eq__`를 정의하면 `__hash__`가 자동으로 `None`** 이 됩니다(해시 불가). "같다고 판정되는 객체는 해시도 같아야 한다"는 계약을 깨지 않으려는 장치입니다. 값 객체라면 비교에 쓰는 필드로 `__hash__`도 정의하고, **해시에 쓰는 필드는 변경 불가**여야 합니다.
2. 모르는 타입이면 `False`/예외 대신 **`NotImplemented`를 반환**하세요. 그래야 Python이 반대편의 `__eq__`/`__radd__`를 시도합니다.
3. `__repr__`은 항상 만들고, `__str__`은 필요할 때만. `__str__`이 없으면 `__repr__`이 쓰입니다.

> Django 연결: 모델에 `def __str__(self): return self.title`을 정의하는 이유 — Admin 목록, 셸, 로그 출력이 전부 이걸 씁니다. Django 모델의 `__eq__`/`__hash__`는 **pk 기준**이라, 저장 전(pk=None) 인스턴스를 set에 넣으면 `TypeError`가 납니다.

### 컨테이너 프로토콜 예

```python
class Playlist:
    def __init__(self, songs):
        self._songs = list(songs)
    def __len__(self):
        return len(self._songs)
    def __getitem__(self, i):          # 인덱싱, 슬라이싱, 그리고 for 루프까지 지원됨
        return self._songs[i]
    def __contains__(self, s):
        return s in self._songs

p = Playlist(["a", "b", "c"])
len(p), p[0], p[1:], "b" in p          # (3, 'a', ['b', 'c'], True)
for s in p: ...                        # __iter__ 없이도 동작 (__getitem__ 폴백)
```

이게 **덕 타이핑**입니다. 상속이 아니라 "필요한 메서드가 있으면 그 타입처럼 취급". `collections.abc.Sequence`를 상속하면 `__len__`+`__getitem__`만 구현해도 `index`, `count`, `__reversed__`가 공짜로 생깁니다.

## 6. dataclass — 보일러플레이트 제거

위 `Money`의 `__init__`/`__repr__`/`__eq__`/`__hash__`를 손으로 쓰는 건 지루하고 실수가 잦습니다.

```python
from dataclasses import dataclass, field, asdict, replace

@dataclass(frozen=True, order=True, slots=True)   # slots=True 는 3.10+
class Point:
    x: int
    y: int = 0

p = Point(1, 2)
p                       # Point(x=1, y=2)       ← __repr__ 자동
p == Point(1, 2)        # True                  ← __eq__ 자동 (필드 튜플 비교)
{p}                     # frozen=True → __hash__ 자동 생성
Point(1, 2) < Point(2, 0)  # True              ← order=True: 필드 순서대로 비교
# p.x = 10              # FrozenInstanceError
replace(p, y=5)         # Point(x=1, y=5)       ← 불변 객체 "수정본" (JS 객체 스프레드 {...p, y:5})
asdict(p)               # {'x': 1, 'y': 2}      ← JSON 직렬화 전처리
```

### mutable 기본값과 `field(default_factory=...)`

```python
@dataclass
class Order:
    id: int
    items: list[str] = field(default_factory=list)  # ✅ 인스턴스마다 새 list
    # items: list[str] = []                         # ❌ ValueError: mutable default
    total: int = field(init=False, default=0)        # __init__ 인자에서 제외

    def __post_init__(self):                         # 자동 __init__ 직후 검증/파생값
        if self.id <= 0:
            raise ValueError("id must be positive")
        self.total = len(self.items)
```

dataclass는 2절의 "공유 리스트" 버그를 **정의 시점에 에러로** 막아 줍니다. (Day 3의 mutable default 함정과 같은 뿌리입니다.)

### 언제 무엇을 쓰나

| 도구 | 용도 | 검증 |
|---|---|---|
| `tuple` / `NamedTuple` | 가볍고 불변인 레코드, 언패킹 | ❌ |
| `@dataclass` | 내부 도메인 객체, DTO | ❌ (타입 힌트는 **검사 안 함**) |
| `TypedDict` | dict 모양에 타입만 붙임 (JSON 그대로 다룰 때) | ❌ (정적 검사만) |
| pydantic / DRF Serializer | **외부 입력** 파싱·검증 | ✅ 런타임 검증 |

> 함정: `Point("1", "2")`도 에러 없이 만들어집니다. 타입 힌트는 TS처럼 컴파일 단계에서도 강제되지 않고, mypy 같은 도구를 돌려야 잡힙니다(Day 10). 외부 입력 검증은 DRF Serializer(Week 5)의 몫입니다.

## 7. CS 심화: 속성 탐색 알고리즘과 객체 메모리 레이아웃

### 7-1. 인스턴스 = 해시테이블 하나

일반 클래스 인스턴스는 속성을 **`__dict__`라는 dict(해시테이블)** 에 저장합니다. Day 2에서 본 그 해시테이블입니다.

```python
class P:
    def __init__(self, x, y):
        self.x, self.y = x, y

p = P(1, 2)
p.__dict__          # {'x': 1, 'y': 2}
p.z = 3             # 런타임에 아무 속성이나 추가 가능 (JS 객체처럼)
```

- 속성 읽기/쓰기는 평균 **O(1)** 해시 조회.
- 대가: 인스턴스마다 해시테이블 하나 → **메모리 오버헤드**. CPython 3.3+는 같은 클래스 인스턴스끼리 **키 배열을 공유하는 key-sharing dict**(PEP 412)로 이를 줄이고, 3.11+는 더 최적화했지만 여전히 객체 수가 수백만이면 체감됩니다.

### 7-2. `__slots__` — 해시테이블 대신 고정 오프셋 배열

```python
class PS:
    __slots__ = ("x", "y")
    def __init__(self, x, y):
        self.x, self.y = x, y

ps = PS(1, 2)
# ps.z = 3          # AttributeError — 선언 안 한 속성 불가
# ps.__dict__       # AttributeError — dict 자체가 없음
```

`__slots__`는 클래스에 각 이름의 **고정 메모리 오프셋**을 가리키는 디스크립터를 만들고, 인스턴스는 C 구조체처럼 **배열 슬롯**에 값을 담습니다.

| | `__dict__` | `__slots__` |
|---|---|---|
| 저장 구조 | 해시테이블 | 고정 크기 배열(구조체) |
| 속성 추가 | 자유 | 선언된 것만 |
| 메모리 | 큼 | 작음 (대략 수십 % 절감, 버전·필드 수 따라 다름) |
| 접근 속도 | O(1) 해시 | O(1) 오프셋 — 보통 약간 빠름 |
| 주의 | — | 다중 상속 시 슬롯 충돌, 약한 참조는 `__weakref__` 슬롯 필요 |

JS 비교: V8은 같은 순서로 속성을 추가한 객체들에 **hidden class(shape)** 를 부여해 내부적으로 오프셋 접근을 합니다. 속성을 아무 순서로 막 추가/삭제하면 "dictionary mode"로 떨어져 느려지죠. `__slots__`는 이 최적화를 **개발자가 명시적으로 선언**하는 것에 가깝습니다. `@dataclass(slots=True)`로 간단히 켤 수 있습니다.

### 7-3. 속성 탐색 순서 (`obj.attr`가 실제로 하는 일)

`type(obj).__getattribute__`의 기본 동작(요약):

1. `type(obj).__mro__`를 순서대로 훑어 클래스 쪽에서 `attr`을 찾는다.
2. 찾은 게 **데이터 디스크립터**(`__get__` + `__set__`/`__delete__` 보유, 예: `property`, `__slots__` 멤버)면 → 그걸 실행. **인스턴스 dict보다 우선.**
3. 아니면 **인스턴스 `__dict__`** 에 있으면 그 값.
4. 아니면 1에서 찾은 게 **비데이터 디스크립터**(`__get__`만, 예: 일반 함수)면 `__get__` 호출 → **바운드 메서드 생성**. 일반 값이면 그대로.
5. 다 없으면 `__getattr__`(정의됐다면) → 그래도 없으면 `AttributeError`.

```python
class D:
    @property
    def v(self): return "property"

d = D()
d.__dict__["v"] = "instance"
d.v                 # 'property' — 데이터 디스크립터가 인스턴스 dict를 이김

class E:
    def m(self): return "method"
e = E()
e.__dict__["m"] = lambda: "instance"
e.m()               # 'instance' — 함수는 비데이터 디스크립터라 인스턴스 dict가 이김
```

복잡도 관점: 클래스 쪽 탐색은 MRO 길이 k에 대해 최악 O(k) 번의 dict 조회입니다. CPython은 **타입 속성 캐시**(method cache)로 반복 조회를 사실상 O(1)로 만듭니다. JS의 prototype chain 탐색 + inline cache와 같은 아이디어입니다.

### 7-4. MRO는 어떻게 계산되나 — C3 선형화

```
L[C] = C + merge(L[A], L[B], [A, B])
```

merge 규칙: 각 리스트의 **머리(head)** 중에서 **다른 어떤 리스트의 꼬리(tail)에도 없는** 첫 번째 것을 뽑아 결과에 붙이고, 모든 리스트에서 제거 → 반복. 뽑을 게 없으면 `TypeError: Cannot create a consistent MRO`.

4절 예시로 손 계산:

```
L[Base] = [Base, object]
L[A]    = [A, Base, object]
L[B]    = [B, Base, object]
L[C]    = C + merge([A, Base, object], [B, Base, object], [A, B])
        = C, A          (A는 어떤 꼬리에도 없음)
        = C, A, B       (Base는 [B, Base, object]의 꼬리에 있으므로 건너뛰고 B)
        = C, A, B, Base, object
```

보장되는 성질: ① 자식은 부모보다 앞, ② `class C(A, B)`에 적은 **왼쪽→오른쪽 순서 유지**, ③ 각 부모의 MRO 순서 유지(단조성). 그래프 관점에선 상속 DAG의 **위상 정렬** 중 이 제약을 만족하는 하나를 고르는 것입니다.

## 8. 흔한 함정 정리

```python
# 1) 클래스 속성에 mutable → 인스턴스 간 공유 (2절)
# 2) self 빼먹기
class A:
    def f():        # A().f() → TypeError: takes 0 positional arguments but 1 was given
        ...
# 3) __eq__만 정의하고 set/dict 키로 사용 → TypeError: unhashable type
# 4) __eq__에서 다른 타입이면 False 반환 → NotImplemented 써야 대칭성 유지
# 5) super().__init__() 호출 누락 → 부모 초기화 안 됨 (다중 상속이면 체인이 끊김)
# 6) 이름 맹글링 오해: self.__x 는 _ClassName__x 로 바뀔 뿐, 접근은 가능
# 7) dataclass 타입 힌트를 런타임 검증으로 착각
# 8) 해시에 쓰이는 필드를 나중에 변경 → set/dict에서 "사라지는" 객체
```

## 9. 연습문제

1. `Vector2(x, y)` 클래스를 작성하라: `+`, `-`, 스칼라 `*`(양쪽 모두: `v * 2`, `2 * v`), `abs(v)`(길이), `==`, `repr`. dict 키로 쓸 수 있어야 한다.
2. 위 `Vector2`를 `@dataclass(frozen=True)`로 다시 작성하고, 손으로 쓴 버전과 줄 수를 비교하라. 어떤 던더가 자동 생성되고 어떤 건 여전히 직접 써야 하는가?
3. 아래 코드의 출력을 **실행 전에** 예측하고, MRO를 C3로 손 계산해 근거를 적어라.
   ```python
   class X:
       def who(self): return "X"
   class Y(X):
       def who(self): return "Y>" + super().who()
   class Z(X):
       def who(self): return "Z>" + super().who()
   class W(Z, Y):
       def who(self): return "W>" + super().who()
   print(W().who(), [k.__name__ for k in W.__mro__])
   ```
4. `class Bad(X, Y): pass`(위의 X, Y)가 왜 `TypeError`인지 C3 merge로 설명하라.
5. `@dataclass class Config: tags: list = []` 가 왜 에러인지, 그리고 2절의 `Cart` 버그와 어떤 관계인지 3줄로 설명하라.
6. (심화) `__slots__`가 있는 클래스와 없는 클래스로 각각 인스턴스 100만 개를 만들고 `tracemalloc`으로 메모리를 측정하라. 결과 수치와 함께 "왜 차이가 나는가"를 해시테이블 관점에서 설명하라.

<details><summary>힌트 / 해설</summary>

- 1: `__mul__(self, k)` + `__rmul__ = __mul__`, `__abs__`는 `math.hypot(self.x, self.y)`. `__eq__`를 정의했으니 `__hash__`로 `hash((self.x, self.y))`를 반드시 추가. 다른 타입이면 `NotImplemented`.
- 2: frozen dataclass는 `__init__`, `__repr__`, `__eq__`, `__hash__`를 만들어 준다. 산술(`__add__`, `__mul__`, `__rmul__`, `__abs__`)은 여전히 직접.
- 3: `W>Z>Y>X`, MRO `['W', 'Z', 'Y', 'X', 'object']`. `Z.who`의 `super()`는 W의 MRO에서 Z 다음인 **Y**다(X가 아님).
- 4: `L[Bad] = Bad + merge([X, object], [Y, X, object], [X, Y])`. 머리 X는 `[Y, X, object]`의 꼬리에 있고, 머리 Y는 `[X, Y]`의 꼬리에 있어서 뽑을 수 있는 게 없다 → 일관된 MRO 없음. "부모(X)를 자식(Y)보다 앞에 둘 수 없다"는 뜻.
- 5: 클래스 정의 시 기본값 객체가 한 번 만들어져 모든 인스턴스가 공유된다. dataclass는 list/dict/set 기본값을 감지해 `ValueError`로 막고 `field(default_factory=list)`를 쓰게 한다. Cart의 클래스 속성 리스트 공유와 같은 문제다.
- 6: `tracemalloc.start()` → 생성 → `tracemalloc.get_traced_memory()`. slots 쪽이 확연히 작다. 일반 인스턴스는 각자 `__dict__`(해시테이블: 키/값/해시 슬롯 + 여유 공간)를 갖지만 slots는 고정 오프셋 배열만 둔다. 실제 수치는 Python 버전마다 다르니 직접 측정한 값을 적을 것.
</details>

## 10. 면접 질문

<details><summary>Q1. 파이썬 메서드의 <code>self</code>는 어떻게 전달되나요? JS의 <code>this</code>와 무엇이 다른가요?</summary>

클래스에 정의된 함수는 비데이터 디스크립터라서, `obj.method`로 접근하는 순간 `function.__get__`이 호출돼 함수와 인스턴스를 묶은 **bound method**가 만들어집니다. 호출 시 그 인스턴스가 첫 인자 `self`로 들어갑니다. 바인딩이 "접근 시점"에 고정되므로, JS처럼 호출 방식에 따라 `this`가 바뀌거나 콜백으로 넘길 때 `bind`가 필요한 문제가 없습니다. `User.greet(u)`처럼 직접 넘겨도 동일합니다.
</details>

<details><summary>Q2. <code>__eq__</code>를 오버라이드하면 <code>__hash__</code>는 어떻게 되고, 왜 그런가요?</summary>

`__hash__`가 `None`으로 설정돼 해시 불가 객체가 됩니다. dict/set은 "a == b이면 hash(a) == hash(b)"라는 계약에 의존하는데, 동등성 기준을 바꿔 놓고 기본(id 기반) 해시를 그대로 두면 계약이 깨지기 때문입니다. 값 객체라면 비교에 쓰는 **불변** 필드로 `__hash__`를 정의하거나 `@dataclass(frozen=True)`를 씁니다. 해시 필드가 변하면 해시테이블의 다른 버킷에 있게 돼 조회가 실패합니다.
</details>

<details><summary>Q3. <code>super()</code>는 부모 클래스를 호출하나요? 다중 상속에서 어떻게 동작하나요?</summary>

`super()`는 "부모"가 아니라 **인스턴스 타입의 MRO에서 현재 클래스 다음 클래스**에 위임합니다. MRO는 C3 선형화로 계산되며 자식이 부모보다 앞, 선언된 베이스 순서 유지, 부모 MRO 순서 유지를 보장합니다. 그래서 다이아몬드 상속에서 공통 조상의 메서드가 한 번만 호출됩니다. 모든 클래스가 `super()`를 협력적으로 호출해야 체인이 이어지고, Django CBV/DRF 믹스인을 왼쪽에 두는 관례도 이 때문입니다.
</details>

<details><summary>Q4. <code>classmethod</code>와 <code>staticmethod</code> 차이와 각각의 실무 용도는?</summary>

`classmethod`는 첫 인자로 클래스(`cls`)를 받아 대체 생성자/팩토리(`from_dict`, `create`)에 쓰며, 서브클래스에서 호출하면 서브클래스 인스턴스를 만듭니다. `staticmethod`는 아무것도 바인딩하지 않는 함수로, 클래스와 개념적으로 묶인 유틸에 씁니다. 상속 시 다형성이 필요하면 classmethod가 맞습니다. 사실 모듈 수준 함수로 충분한 경우가 많아 staticmethod는 남용하지 않는 편이 좋습니다.
</details>

<details><summary>Q5. <code>__slots__</code>는 무엇이고 언제 쓰나요? 단점은?</summary>

인스턴스 속성을 `__dict__` 해시테이블 대신 고정 오프셋 배열에 저장하게 해서 메모리를 줄이고 접근을 약간 빠르게 합니다. 수백만 개 인스턴스를 만드는 값 객체/레코드에 적합합니다. 단점은 선언하지 않은 속성 추가 불가, 다중 상속 시 비어 있지 않은 슬롯 베이스끼리 충돌, `__weakref__`를 슬롯에 넣지 않으면 약한 참조 불가, 동적 몽키패칭 불가 등입니다. V8의 hidden class 최적화를 명시적으로 선언하는 것과 비슷합니다.
</details>

<details><summary>Q6. dataclass와 pydantic(또는 DRF Serializer)의 차이는?</summary>

dataclass는 `__init__`/`__repr__`/`__eq__` 등 보일러플레이트를 생성할 뿐 **타입 힌트를 런타임에 검증하지 않습니다**. pydantic과 DRF Serializer는 외부 입력을 파싱·형 변환·검증하고 에러 메시지를 만듭니다. 그래서 신뢰된 내부 데이터는 dataclass, API 경계의 외부 입력은 Serializer/pydantic이라는 식으로 나눕니다.
</details>
