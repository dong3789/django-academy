## Part 1. 클래스 기본

### 1-1. 생김새: self가 명시적이다

구조는 JS class와 거의 같지만 세 가지가 다릅니다.
`new`가 없고, 생성자 이름이 `__init__`이며,
**인스턴스를 첫 인자 `self`로 명시적으로 받습니다**.

```python
class User:
    def __init__(self, name):
        self.name = name

    def greet(self):
        return f"hi {self.name}"
```

```python
u = User("dh")
print(u.greet())
# hi dh
```

**JS에서는:**

```javascript
class User {
  constructor(name) { this.name = name; }
  greet() { return `hi ${this.name}`; }
}
```

> 💡 핵심: `this` → `self`(명시적 첫 인자), `constructor` → `__init__`.

### 1-2. 메서드는 그냥 함수다

`u.greet()`는 사실 `User.greet(u)`와 같습니다.
메서드는 "첫 인자로 인스턴스를 받는 평범한 함수"이고,
점(`.`)으로 접근할 때 Python이 인스턴스를 끼워 넣어 줍니다.

```python
print(User.greet(u))
# hi dh
f = u.greet
print(f())
# hi dh
```

`u.greet`에 접근하는 순간 함수와 `u`를 묶은 **bound method**가
만들어지므로, 변수에 담았다 호출해도 `self`가 유지됩니다.

**JS에서는:** `const f = u.greet; f()`는 `this`가 `undefined`가 되어
에러. 그래서 `bind`나 화살표 함수가 필요했죠. Python엔 이 문제가 없습니다.

> 💡 핵심: 메서드 접근 시 self가 묶인다. bind 불필요.

### 1-3. __init__은 생성자가 아니다

엄밀히 객체를 **만드는** 건 `__new__`, 만들어진 객체를
**초기화**하는 게 `__init__`입니다. `User("dh")`는 내부적으로
두 단계를 거칩니다.

```python
obj = User.__new__(User)
User.__init__(obj, "dh")
print(obj.name)
# dh
```

`__new__`를 직접 쓸 일은 드뭅니다(싱글턴, 불변 타입 상속 정도).
그래서 `__init__`은 아무것도 반환하지 않아야 합니다.

> 💡 핵심: 생성 = `__new__`, 초기화 = `__init__`.

## Part 2. 클래스 속성 vs 인스턴스 속성

### 2-1. 클래스 속성은 공유된다

클래스 본문에 바로 쓴 변수는 **클래스 속성**이고,
모든 인스턴스가 하나를 공유합니다.
여기에 리스트를 두면 실무 버그 1순위가 됩니다.

```python
class Cart:
    items = []

    def add(self, x):
        self.items.append(x)
```

```python
a, b = Cart(), Cart()
a.add(1)
print(b.items)
# [1]  ← b에도 들어감!
```

`self.items`를 찾을 때 인스턴스에 없으니 클래스에서 찾았고,
그 **공유 리스트**를 변경했기 때문입니다.

**해결:** 인스턴스별 상태는 `__init__`에서 만듭니다.

```python
class Cart:
    def __init__(self):
        self.items = []
```

**JS에서는:** `class Cart { items = []; }`(클래스 필드)는
**인스턴스마다** 새로 만들어집니다. 문법이 비슷해 보여 더 위험합니다.

> 💡 핵심: 클래스 본문의 가변 값 = 전 인스턴스 공유. 상태는 `__init__`에서.

### 2-2. 읽기와 쓰기의 비대칭

**읽기**는 인스턴스 → 클래스 → 부모 순으로 찾지만,
**대입**(`self.x = ...`)은 항상 인스턴스에 씁니다.
그래서 `+=`는 클래스 값을 바꾸지 않고 인스턴스에 새 속성을 만듭니다.

```python
class C:
    n = 0

c = C()
c.n += 1
print(C.n, c.n)
# 0 1
```

`c.n += 1`은 `c.n = c.n + 1`. 오른쪽은 클래스에서 0을 읽고,
왼쪽은 인스턴스에 1을 씁니다(그림자 속성).
Day 3의 "대입하면 로컬"과 같은 결입니다.

> 💡 핵심: 읽기는 위로 찾아 올라가고, 쓰기는 항상 인스턴스에.

### 2-3. Django와의 연결

Django 모델은 필드를 **클래스 속성**으로 선언합니다.
그런데 왜 모든 인스턴스가 같은 `title`을 공유하지 않을까요?

```python
class Post(models.Model):
    title = models.CharField(
        max_length=100)
```

메타클래스(클래스를 만드는 클래스)가 클래스 생성 시 이 필드들을
수집해 **스키마**로 등록하고, 인스턴스마다 실제 값을 따로 갖게 만듭니다.
"클래스 속성 = 스키마 선언"이 Django 문법의 비밀입니다(Week 3).

> 💡 핵심: Django 필드는 클래스 속성이지만 메타클래스가 인스턴스 값으로 바꾼다.

## Part 3. property · classmethod · staticmethod

### 3-1. @property — 메서드를 속성처럼

`age`처럼 **계산되는 값**을 괄호 없이 읽게 해 줍니다.
더 중요한 이유: 처음엔 평범한 속성으로 두었다가, 나중에 검증이
필요해지면 **호출 코드를 안 바꾸고** property로 교체할 수 있습니다.
그래서 Python에선 Java식 `getX()/setX()`를 미리 만들지 않습니다.

```python
class Member:
    def __init__(self, born):
        self.born = born

    @property
    def age(self):
        return 2026 - self.born
```

```python
m = Member(1990)
print(m.age)
# 36
```

**JS에서는:** `get age() { ... }`와 같습니다.

> 💡 핵심: getter가 필요해질 때까지는 그냥 public 속성.

### 3-2. setter로 검증 추가

`@이름.setter`로 대입 시 검증을 넣습니다.
실제 값은 관례상 `_born`처럼 밑줄 붙은 이름에 저장합니다.

```python
class Member:
    @property
    def born(self):
        return self._born

    @born.setter
    def born(self, v):
        if v < 1900:
            raise ValueError("bad year")
        self._born = v
```

이제 `__init__`의 `self.born = born`도 setter를 거쳐 검증됩니다.

**JS에서는:** `set born(v) { ... }`. 같습니다.

> 💡 핵심: 검증이 필요하면 property + setter, 저장은 `_이름`.

### 3-3. @classmethod — 대체 생성자

첫 인자로 **인스턴스 대신 클래스(`cls`)** 를 받습니다.
`from_dict`, `from_json` 같은 "다른 형태로부터 만들기"에 씁니다.
`cls(...)`로 만들기 때문에 **서브클래스에서 호출하면
서브클래스 인스턴스**가 나옵니다.

```python
class Member:
    def __init__(self, name):
        self.name = name

    @classmethod
    def from_dict(cls, d):
        return cls(d["name"])
```

```python
class Admin(Member):
    pass

a = Admin.from_dict({"name": "dh"})
print(type(a).__name__)
# Admin
```

**JS에서는:** `static fromDict(d) { return new this(d.name); }`.

> 💡 핵심: 대체 생성자 = classmethod + `cls(...)`.

### 3-4. @staticmethod — 그냥 함수

아무것도 자동으로 받지 않는 함수를 클래스 이름공간에 둔 것입니다.
서브클래스 다형성이 깨지므로 생성자 용도로는 쓰지 마세요.
사실 모듈 수준 함수로 충분한 경우가 많습니다.

```python
class Member:
    @staticmethod
    def valid_name(s):
        return bool(s.strip())
```

**JS에서는:** `static validName(s)`. 다만 JS의 `static`은
Python의 classmethod/staticmethod 두 역할을 다 합니다.

> 💡 핵심: cls가 필요하면 classmethod, 아니면 모듈 함수를 먼저 고려.

## Part 4. 상속 · super() · MRO

### 4-1. 단일 상속과 super()

부모 클래스는 `class Dog(Animal):`처럼 괄호에 씁니다.
자식 `__init__`에서 `super().__init__()`을 **잊으면
부모 초기화가 실행되지 않아** 속성이 없다는 에러가 납니다.

```python
class Animal:
    def __init__(self, name):
        self.name = name

class Dog(Animal):
    def __init__(self, name, breed):
        super().__init__(name)
        self.breed = breed
```

**JS에서는:** `super(name)`. JS는 `super()` 전에 `this`를 쓰면
에러를 내서 강제하지만, Python은 **강제하지 않습니다**.

> 💡 핵심: 자식 `__init__`에서 `super().__init__()` 호출은 직접 챙긴다.

### 4-2. 다중 상속과 MRO

Python은 부모를 여러 개 둘 수 있습니다. 그러면
"메서드를 어느 부모에서 찾나?"를 정한 순서가 필요합니다.
이것이 **MRO(Method Resolution Order)** 입니다.

```python
class Base:
    def hi(self): return ["Base"]
class A(Base):
    def hi(self): return ["A"] + super().hi()
class B(Base):
    def hi(self): return ["B"] + super().hi()
class C(A, B):
    def hi(self): return ["C"] + super().hi()
```

```python
print(C().hi())
# ['C', 'A', 'B', 'Base']
print([k.__name__ for k in C.__mro__])
# ['C', 'A', 'B', 'Base', 'object']
```

**JS에서는:** 단일 상속뿐이라 MRO 개념이 없습니다.
믹스인은 `Object.assign`이나 함수 합성으로 흉내 냅니다.

> 💡 핵심: 다중 상속 시 탐색 순서 = `Cls.__mro__`.

### 4-3. super()는 "부모"가 아니다

위 출력에서 `A.hi`의 `super()`가 `Base`가 아니라 **`B`** 를 불렀습니다.
`super()`는 "내 부모"가 아니라 **"현재 인스턴스 MRO에서 내 다음"** 입니다.
덕분에 다이아몬드 상속에서도 `Base.hi`가 **한 번만** 호출됩니다.

이게 동작하려면 모든 클래스가 빠짐없이 `super()`를 불러야 합니다
(**협력적 다중 상속**). 하나라도 부모를 직접 호출하면 체인이 끊깁니다.

```python
class A(Base):
    def hi(self):
        # 나쁨: 체인이 끊겨 B가 빠짐
        return ["A"] + Base.hi(self)
```

> 💡 핵심: super() = MRO상 다음 클래스. 모두가 super()를 불러야 한다.

### 4-4. Django에서 MRO가 보이는 곳

Django CBV와 DRF는 **믹스인 조합**으로 만들어집니다.
믹스인을 **왼쪽**, 베이스 클래스를 **오른쪽**에 두는 규칙이 MRO 때문입니다.
`LoginRequiredMixin`이 왼쪽에 있어야 `dispatch`가 먼저 가로챕니다.

```python
class PostList(
    LoginRequiredMixin,
    ListView,
):
    model = Post
```

순서를 뒤집으면 `ListView.dispatch`가 먼저 실행되어
로그인 검사가 건너뛰어질 수 있습니다.

> 💡 핵심: 믹스인 왼쪽, 베이스 오른쪽 — MRO가 이유다.

## Part 5. 던더 메서드 — 파이썬의 프로토콜

### 5-1. 던더란

`__이름__` 형태의 메서드는 **언어 문법에 연결된 훅**입니다.
`len(x)`는 `x.__len__()`을, `a + b`는 `a.__add__(b)`를,
`print(x)`는 `x.__str__()`을 부릅니다.
내 클래스가 내장 타입처럼 행동하게 만드는 방법입니다.

| 문법 | 던더 |
|---|---|
| `repr(x)` | `__repr__` |
| `str(x)`, `print` | `__str__` |
| `a == b` | `__eq__` |
| `hash(x)`, dict 키 | `__hash__` |
| `len(x)` | `__len__` |
| `x[i]` | `__getitem__` |
| `a + b` | `__add__` |
| `if x:` | `__bool__` |

**JS에서는:** `toString`, `[Symbol.iterator]` 정도가 비슷합니다.
JS엔 **연산자 오버로딩**과 값 기반 `==`가 없습니다.

> 💡 핵심: 던더 = 문법이 호출하는 메서드. 구현하면 내장처럼 동작.

### 5-2. __repr__과 __str__

`__repr__`은 **개발자용**(디버거, 셸, 로그),
`__str__`은 **사용자용** 표현입니다.
`__str__`이 없으면 `__repr__`이 대신 쓰이므로, `__repr__`부터 만드세요.

```python
class Money:
    def __init__(self, amount):
        self.amount = amount

    def __repr__(self):
        return f"Money({self.amount!r})"

    def __str__(self):
        return f"{self.amount:,}원"
```

```python
m = Money(1500)
print(m)
# 1,500원
print([m])
# [Money(1500)]
```

리스트 안에선 `__repr__`이 쓰입니다.
Django 모델에 `__str__`을 정의하는 이유: Admin 목록·셸이 그걸 씁니다.

> 💡 핵심: `__repr__`은 항상, `__str__`은 필요할 때.

### 5-3. __eq__를 정의하면 __hash__가 사라진다

값이 같으면 같은 객체로 보고 싶을 때 `__eq__`를 정의합니다.
그 순간 Python은 **`__hash__`를 `None`으로** 만들어
set·dict 키로 못 쓰게 합니다.

왜? dict/set은 "`a == b`이면 `hash(a) == hash(b)`"라는 계약에 의존합니다.
같다고 판정되는 두 객체가 기본(id 기반) 해시로 다른 버킷에 들어가면
중복 검출이 깨지기 때문입니다.

```python
class Money:
    def __init__(self, amount):
        self.amount = amount

    def __eq__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        return self.amount == other.amount
```

```python
    def __hash__(self):
        return hash(self.amount)
```

해시에 쓰는 필드는 **바뀌면 안 됩니다**(Day 2: 키가 변하면 못 찾음).

> 💡 핵심: `__eq__`를 만들면 불변 필드로 `__hash__`도 만든다.

### 5-4. False 대신 NotImplemented

모르는 타입과 비교될 때 `False`를 반환하면
상대편이 비교를 처리할 기회를 빼앗습니다.
`NotImplemented`를 반환하면 Python이 **반대쪽 메서드**를 시도하고,
그래도 안 되면 기본 동작(`==`는 False, `+`는 TypeError)을 합니다.

```python
class Money:
    def __add__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        return Money(
            self.amount + other.amount)
```

```python
    def __radd__(self, other):
        if other == 0:
            return self
        return NotImplemented
```

`__radd__`는 왼쪽이 처리 못 할 때 불립니다.
`sum()`이 `0 + 첫원소`로 시작하므로 `sum([Money(1), Money(2)])`에 필요합니다.

> 💡 핵심: 모르는 타입이면 `return NotImplemented`.

### 5-5. 덕 타이핑: 컨테이너 프로토콜

상속 없이도 `__len__`과 `__getitem__`만 있으면
`len()`, 인덱싱, 슬라이싱, `for` 루프까지 동작합니다.
"오리처럼 꽥꽥대면 오리" — 타입이 아니라 **행동**으로 판단합니다.

```python
class Playlist:
    def __init__(self, songs):
        self._songs = list(songs)

    def __len__(self):
        return len(self._songs)

    def __getitem__(self, i):
        return self._songs[i]
```

```python
p = Playlist(["a", "b", "c"])
print(len(p), p[0], p[1:])
# 3 a ['b', 'c']
for s in p:
    print(s)
```

`__iter__`가 없으면 `for`는 `__getitem__(0, 1, 2...)`을
`IndexError`가 날 때까지 부릅니다.

**JS에서는:** `[Symbol.iterator]`를 구현해야 `for...of`가 됩니다.
인덱싱 `p[0]`은 Proxy 없이는 불가능합니다.

> 💡 핵심: 프로토콜만 맞추면 내장 타입처럼 쓸 수 있다.

## Part 6. dataclass

### 6-1. 보일러플레이트 제거

위 `Money`처럼 `__init__`, `__repr__`, `__eq__`, `__hash__`를
손으로 쓰는 건 지루하고 실수가 잦습니다(`__hash__` 빠뜨리기 등).
`@dataclass`는 **타입 힌트가 붙은 필드 선언**만 보고 이것들을 생성합니다.

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Point:
    x: int
    y: int = 0
```

```python
p = Point(1, 2)
print(p)
# Point(x=1, y=2)
print(p == Point(1, 2))
# True
print({p, Point(1, 2)})
# {Point(x=1, y=2)}
```

`frozen=True`면 불변이 되고 `__hash__`도 생성됩니다.

**JS에서는:** 대응 기능이 없습니다. TS의 `class` + 생성자
파라미터 프로퍼티가 `__init__` 부분만 비슷합니다.

> 💡 핵심: 값 객체는 `@dataclass(frozen=True)`부터 시작.

### 6-2. 불변 객체 수정: replace

frozen 객체는 필드를 바꿀 수 없습니다.
대신 **일부만 바꾼 새 객체**를 만듭니다.

```python
from dataclasses import replace, asdict
p2 = replace(p, y=5)
print(p2)
# Point(x=1, y=5)
print(asdict(p2))
# {'x': 1, 'y': 5}
```

`p.x = 10`은 `FrozenInstanceError`.
`asdict`는 JSON 직렬화 전처리에 씁니다.

**JS에서는:** `{...p, y: 5}`와 같은 발상입니다.

> 💡 핵심: 불변 수정 = `replace`, 직렬화 = `asdict`.

### 6-3. 가변 기본값: field(default_factory)

`items: list = []`는 `ValueError`로 **정의 시점에 거부**됩니다.
2-1의 `Cart` 버그를 dataclass가 미리 막아 주는 것입니다.
인스턴스마다 새 리스트가 필요하면 팩토리를 넘깁니다.

```python
from dataclasses import dataclass, field

@dataclass
class Order:
    id: int
    items: list[str] = field(
        default_factory=list)
```

생성 직후 검증은 `__post_init__`에서 합니다.

```python
    def __post_init__(self):
        if self.id <= 0:
            raise ValueError("id > 0")
```

> 💡 핵심: 가변 기본값은 `field(default_factory=...)`.

### 6-4. 타입 힌트는 검사하지 않는다

dataclass의 타입 힌트는 **런타임에 검증되지 않습니다**.
TS처럼 컴파일 단계도 없어서, `mypy`를 돌려야 잡힙니다.

```python
p = Point("1", "2")
print(p)
# Point(x='1', y='2') 에러 없음!
```

그래서 **외부 입력**(API 요청 바디)은 DRF Serializer나
pydantic처럼 런타임 검증 도구로 받고,
검증된 내부 데이터를 dataclass로 다룹니다.

| 도구 | 용도 |
|---|---|
| `NamedTuple` | 가벼운 불변 레코드 |
| `@dataclass` | 내부 도메인 객체 |
| `TypedDict` | dict 모양에 타입만 |
| pydantic/DRF | 외부 입력 검증 |

> 💡 핵심: dataclass는 생성기일 뿐 검증기가 아니다.

## Part 7. CS 심화: 객체 메모리와 속성 탐색

### 7-1. 인스턴스 = 해시 테이블 하나

일반 인스턴스는 속성을 **`__dict__`라는 dict**에 저장합니다.
그래서 런타임에 아무 속성이나 추가할 수 있고, 접근은 평균 O(1)입니다.
대가는 **인스턴스마다 해시 테이블 하나**라는 메모리 비용입니다.

```python
class P:
    def __init__(self, x):
        self.x = x

p = P(1)
p.z = 3
print(p.__dict__)
# {'x': 1, 'z': 3}
```

CPython은 같은 클래스 인스턴스끼리 **키 배열을 공유**하는
key-sharing dict(PEP 412)로 비용을 줄이지만,
객체가 수백만 개면 여전히 체감됩니다.

> 💡 핵심: 기본 인스턴스 = 속성 dict. 유연하지만 무겁다.

### 7-2. __slots__ — 해시 테이블 대신 고정 배열

`__slots__`로 속성 이름을 미리 선언하면 `__dict__`를 만들지 않고,
C 구조체처럼 **고정 오프셋 슬롯**에 값을 저장합니다.
메모리가 크게 줄고 접근이 약간 빨라집니다.

```python
class PS:
    __slots__ = ("x", "y")

    def __init__(self, x, y):
        self.x = x
        self.y = y
```

```python
ps = PS(1, 2)
ps.z = 3
# AttributeError
```

단점: 선언 안 한 속성 추가 불가, 다중 상속 시 충돌 가능,
weakref가 필요하면 `__weakref__` 슬롯 추가.
`@dataclass(slots=True)`(3.10+)로 쉽게 켤 수 있습니다.

**JS에서는:** V8은 같은 순서로 속성을 만든 객체에 **hidden class**를
붙여 오프셋으로 접근합니다. `__slots__`는 이걸 **명시적으로 선언**하는 셈.

> 💡 핵심: 객체가 아주 많으면 `__slots__`로 dict 비용 제거.

### 7-3. obj.attr의 실제 탐색 순서

`obj.attr`은 단순한 dict 조회가 아닙니다.
**디스크립터**(`__get__`을 가진 객체: 함수, property, 슬롯)가
끼어들기 때문입니다. 순서는 다음과 같습니다.

1. `type(obj).__mro__`를 따라 **클래스 쪽**에서 `attr`을 찾는다.
2. 그게 **데이터 디스크립터**(`__get__`+`__set__`, 예: property)면
   그걸 실행. **인스턴스 dict보다 우선.**
3. 아니면 **인스턴스 `__dict__`** 에 있으면 그 값.
4. 아니면 1에서 찾은 것이 함수(비데이터 디스크립터)면
   `__get__` → **bound method** 생성. 일반 값이면 그대로.
5. 다 없으면 `__getattr__` → 그래도 없으면 `AttributeError`.

```python
class D:
    @property
    def v(self):
        return "property"

d = D()
d.__dict__["v"] = "instance"
print(d.v)
# property
```

property(데이터 디스크립터)가 인스턴스 dict를 이겼습니다.
1-2의 "self가 자동으로 묶이는" 현상이 바로 4단계입니다.

> 💡 핵심: property > 인스턴스 dict > 메서드/클래스 값.

### 7-4. MRO 계산: C3 선형화

MRO는 아무렇게나 정하지 않고 **C3 선형화** 알고리즘으로 계산합니다.
보장하는 성질은 세 가지입니다.

1. 자식은 항상 부모보다 앞
2. `class C(A, B)`에 쓴 **왼쪽→오른쪽 순서** 유지
3. 각 부모의 MRO 순서도 유지

```text
L[C] = C + merge(L[A], L[B], [A, B])
```

**merge 규칙:** 각 리스트의 **첫 원소(head)** 중에서,
다른 어떤 리스트의 **나머지(tail)** 에도 없는 첫 번째 것을 뽑아
결과에 붙이고 모든 리스트에서 지운다. 반복.
뽑을 게 없으면 `TypeError`.

4-2 예시를 손으로 계산하면:

```text
L[A] = [A, Base, object]
L[B] = [B, Base, object]
merge([A,Base,obj],[B,Base,obj],[A,B])
→ A   (어떤 tail에도 없음)
→ B   (Base는 [B,Base,obj] tail에 있음)
→ Base → object
L[C] = [C, A, B, Base, object]
```

그래프 관점에서 상속 DAG의 **위상 정렬** 중 위 제약을 만족하는 하나입니다.

> 💡 핵심: MRO = 제약을 지키는 위상 정렬(C3). 불가능하면 TypeError.

### 문제 1. Vector2 직접 구현

`Vector2(x, y)` 클래스를 작성하세요.
`+`, `-`, 스칼라 `*`(`v * 2`와 `2 * v` 모두), `abs(v)`(길이),
`==`, `repr`을 지원하고 dict 키로 쓸 수 있어야 합니다.

<details>
<summary>정답 보기</summary>

```python
import math

class Vector2:
    def __init__(self, x, y):
        self._x = x
        self._y = y

    @property
    def x(self):
        return self._x
```

```python
    @property
    def y(self):
        return self._y

    def __repr__(self):
        return f"Vector2({self.x}, {self.y})"
```

```python
    def __add__(self, o):
        if not isinstance(o, Vector2):
            return NotImplemented
        return Vector2(self.x + o.x,
                       self.y + o.y)

    def __sub__(self, o):
        if not isinstance(o, Vector2):
            return NotImplemented
        return Vector2(self.x - o.x,
                       self.y - o.y)
```

```python
    def __mul__(self, k):
        if not isinstance(k, (int, float)):
            return NotImplemented
        return Vector2(self.x * k,
                       self.y * k)

    __rmul__ = __mul__

    def __abs__(self):
        return math.hypot(self.x, self.y)
```

```python
    def __eq__(self, o):
        if not isinstance(o, Vector2):
            return NotImplemented
        return (self.x, self.y) == (o.x, o.y)

    def __hash__(self):
        return hash((self.x, self.y))
```

```python
v = Vector2(3, 4)
print(2 * v, abs(v))
# Vector2(6, 8) 5.0
print({v: "ok"}[Vector2(3, 4)])
# ok
```

**설명**

- `2 * v`는 먼저 `int.__mul__(2, v)`를 시도 → `NotImplemented`
  → `v.__rmul__(2)` 호출. 그래서 `__rmul__ = __mul__`.
- `__eq__`를 정의했으니 `__hash__`를 반드시 같이 정의합니다.
  같은 필드 튜플로 해시해 "같으면 해시도 같다"를 지킵니다.
- 해시에 쓰는 x, y가 바뀌면 안 되므로 읽기 전용 property로 노출.
- 모르는 타입이면 `NotImplemented`를 반환해 파이썬이
  반대편 메서드나 기본 동작을 시도하게 합니다.

### 문제 3. MRO 예측

실행 전에 출력을 예측하고, C3로 MRO를 계산해 근거를 적으세요.

```python
class X:
    def who(self): return "X"
class Y(X):
    def who(self):
        return "Y>" + super().who()
class Z(X):
    def who(self):
        return "Z>" + super().who()
class W(Z, Y):
    def who(self):
        return "W>" + super().who()

print(W().who())
```

<details>
<summary>정답 보기</summary>

**출력:** `W>Z>Y>X`

**MRO 계산**

```text
L[X] = [X, object]
L[Y] = [Y, X, object]
L[Z] = [Z, X, object]
L[W] = W + merge(
  [Z,X,obj], [Y,X,obj], [Z,Y])
→ Z  (어떤 tail에도 없음)
→ X? [Y,X,obj]의 tail에 있음 → 건너뜀
→ Y
→ X → object
L[W] = [W, Z, Y, X, object]
```

**설명:** `Z.who` 안의 `super()`는 `Z`의 부모 `X`가 아니라
**W의 MRO에서 Z 다음인 `Y`** 를 가리킵니다.
그래서 `Z>` 다음에 `Y>`가 오고, X는 마지막에 한 번만 호출됩니다.

</details>

### 문제 4. 불가능한 MRO

위의 X, Y로 `class Bad(X, Y): pass`를 만들면
왜 `TypeError`인지 C3 merge로 설명하세요.

<details>
<summary>정답 보기</summary>

```text
L[Bad] = Bad + merge(
  [X, obj], [Y, X, obj], [X, Y])
```

- head **X**: `[Y, X, obj]`의 tail에 있음 → 못 뽑음
- head **Y**: `[X, Y]`의 tail에 있음 → 못 뽑음
- 뽑을 수 있는 head가 없음 → 실패

```text
TypeError: Cannot create a consistent
method resolution order (MRO)
```

**의미:** `(X, Y)` 선언은 "X를 Y보다 먼저"를 요구하지만,
Y는 X의 자식이라 "Y가 X보다 먼저"여야 합니다. 모순입니다.
**자식 클래스를 부모보다 오른쪽에 둘 수 없다**는 뜻이고,
`class Bad(Y, X)`로 바꾸면 동작합니다.

</details>

## 면접 질문

<details>
<summary>Q1. 메서드의 self는 어떻게 전달되나요? JS의 this와 무엇이 다른가요?</summary>

**원리:** 클래스에 정의된 함수는 **비데이터 디스크립터**입니다.
`obj.method`로 접근하는 순간 `function.__get__(obj, type)`이 호출되어
함수와 인스턴스를 묶은 **bound method**가 만들어집니다.
호출하면 그 인스턴스가 첫 인자 `self`로 들어갑니다.

**JS와 차이:** JS `this`는 **호출 방식**(`obj.f()` vs `f()`)에 따라
런타임에 결정됩니다. Python은 **접근 시점**에 묶이므로,
메서드를 콜백으로 넘겨도 `bind`가 필요 없습니다.

**확인:** `u.greet.__self__ is u`, `u.greet.__func__ is User.greet`.

</details>

<details>
<summary>Q2. __eq__를 오버라이드하면 __hash__는 어떻게 되고, 왜 그런가요?</summary>

**결과:** `__hash__`가 `None`이 되어 해시 불가 객체가 됩니다.

**이유:** dict/set은 "`a == b`이면 `hash(a) == hash(b)`" 계약에 의존합니다.
동등성 기준을 바꿨는데 기본(id 기반) 해시를 그대로 두면,
같은 값의 두 객체가 다른 버킷에 들어가 중복 검출이 실패합니다.
Python은 이 위험을 막으려 해시를 아예 꺼 버립니다.

**해결:** 비교에 쓰는 **불변** 필드 튜플로 `__hash__`를 정의하거나
`@dataclass(frozen=True)`를 씁니다.

**Django 함의:** 모델의 `__eq__`/`__hash__`는 pk 기준이라,
저장 전(pk=None) 인스턴스를 해시하면 `TypeError`가 납니다.

</details>

<details>
<summary>Q3. super()는 부모 클래스를 호출하나요? 다중 상속에서 어떻게 동작하나요?</summary>

**답:** 아닙니다. `super()`는 **인스턴스 타입의 MRO에서
현재 클래스 다음** 클래스에 위임합니다.

**MRO:** C3 선형화로 계산하며 ① 자식이 부모보다 앞,
② 선언된 베이스 순서 유지, ③ 각 부모의 MRO 순서 유지를 보장합니다.

**효과:** 다이아몬드 상속에서 공통 조상 메서드가 한 번만 호출됩니다.
단, 모든 클래스가 `super()`를 협력적으로 호출해야 체인이 이어집니다.

**실무:** Django CBV/DRF에서 믹스인을 왼쪽, 베이스 뷰를 오른쪽에
두는 관례가 이 때문입니다.

</details>

<details>
<summary>Q4. classmethod와 staticmethod의 차이와 실무 용도는?</summary>

**classmethod:** 첫 인자로 클래스(`cls`)를 받습니다.
대체 생성자/팩토리(`from_dict`, `create`)에 쓰고,
`cls(...)`로 만들기 때문에 서브클래스에서 호출하면
서브클래스 인스턴스가 나옵니다(다형성 유지).

**staticmethod:** 아무것도 바인딩하지 않는 일반 함수입니다.
클래스와 개념적으로 묶인 유틸에 씁니다.

**판단 기준:** 상속 시 다형성이 필요하면 classmethod.
그 외엔 모듈 수준 함수로 충분한 경우가 많아 staticmethod는 아낍니다.

</details>

<details>
<summary>Q5. __slots__는 무엇이고 언제 쓰나요? 단점은?</summary>

**무엇:** 인스턴스 속성을 `__dict__` 해시 테이블 대신
**고정 오프셋 배열**에 저장하게 하는 선언입니다.

**효과:** 인스턴스당 메모리 감소, 속성 접근 약간 빠름.

**언제:** 수십만~수백만 개 만드는 값 객체/레코드.

**단점:**

- 선언 안 한 속성 추가 불가 (몽키패칭 불가)
- 다중 상속 시 슬롯 있는 베이스끼리 레이아웃 충돌
- weakref가 필요하면 `__weakref__`를 슬롯에 추가해야 함

**비유:** V8 hidden class 최적화를 개발자가 명시적으로 선언하는 것.

</details>

<details>
<summary>Q6. dataclass와 pydantic(또는 DRF Serializer)의 차이는?</summary>

**dataclass:** `__init__`/`__repr__`/`__eq__` 등 코드를
**생성**할 뿐, 타입 힌트를 **런타임에 검증하지 않습니다**.
`Point("1", "2")`도 그대로 만들어집니다.

**pydantic / DRF Serializer:** 외부 입력을 **파싱·형 변환·검증**하고
필드별 에러 메시지를 만듭니다.

**경계 나누기:** API 경계(신뢰할 수 없는 입력)는 Serializer/pydantic,
검증을 통과한 내부 도메인 데이터는 dataclass.
정적 타입 오류는 mypy로 CI에서 잡습니다.

</details>
