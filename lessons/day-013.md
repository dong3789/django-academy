## 1. 마이그레이션 파일 읽기

지금까지는 `makemigrations`가 만든 파일을 열어 보지 않았습니다. 그런데 문제가 생기면 결국 이 파일을 읽어야 합니다. 파일은 생각보다 단순한 **Python 클래스 하나**입니다.

**결과를 맞혀 보세요:** 동료가 `0005` 파일을 지웠는데, 내 DB에는 이미 `0005`가 적용돼 있습니다. Django는 "어떤 파일이 적용됐는지"를 어디에 기록해 둘까요?

<details>
<summary>정답</summary>

**DB 안의 `django_migrations` 테이블**입니다. `(앱, 파일 이름, 적용 시각)`이 한 줄씩 쌓입니다. 그래서 파일과 이 표가 어긋나면 Django가 헷갈립니다. 적용된 파일은 지우지 않는 게 원칙입니다.

</details>

**JS (Node, Knex)**

```javascript
// migrations/20261024_checkin.js
exports.up = (knex) =>
  knex.schema.createTable(
    "checkin", (t) => {
      t.increments("id");
      t.integer("amount");
    });
```

**Python (Django)** · `goals/migrations/0004_checkin.py`

```python
class Migration(migrations.Migration):
    dependencies = [
        ("goals", "0003_goal_owner"),
    ]
    operations = [
        migrations.CreateModel(
            name="CheckIn", fields=[...]),
    ]
```

Knex는 **파일 이름의 날짜 순서**로 실행합니다. Django는 다릅니다. 각 파일이 `dependencies`로 "나는 이 파일 다음"이라고 **앞 파일을 가리킵니다**. 그래서 파일들이 사슬(그래프)이 됩니다.

**비유:** 레고 설명서의 각 쪽에 "3쪽을 끝낸 뒤 보세요"라고 적힌 것과 같습니다. 쪽 번호보다 그 메모가 진짜 순서를 정합니다.

상태를 확인하는 명령 두 개를 기억하세요.

```bash
python manage.py showmigrations goals
# 출력: [X] 0003_goal_owner
# 출력: [ ] 0004_checkin
python manage.py sqlmigrate goals 0004
```

`showmigrations`는 적용 여부(`[X]`), `sqlmigrate`는 그 파일이 **실제로 실행할 SQL**을 보여 줍니다. 무서운 마이그레이션은 먼저 SQL을 읽어 보는 습관을 들이세요.

이 "가리키기" 사슬을 순수 Python으로 풀면 이렇습니다.

```python-run
deps = {"0002": "0001",
        "0003": "0002",
        "0004": "0003"}
order, cur = [], "0004"
while cur:
    order.append(cur)
    cur = deps.get(cur)
print(order[::-1])
```

> 💡 마이그레이션 = `dependencies`(앞 파일) + `operations`(할 일). 적용 기록은 `django_migrations` 표에.

<details>
<summary>🔍 더 깊이 (면접용): 마이그레이션은 모델을 읽지 않는다</summary>

`makemigrations`는 지금 `models.py`와 **기존 마이그레이션 파일들을 처음부터 재생한 상태**를 비교해 차이를 만듭니다. DB를 보지 않습니다. 그래서 DB를 손으로 고치면 Django는 모릅니다.

`migrate`는 그래프에서 아직 적용 안 된 노드를 위상 정렬(앞 노드부터 순서대로 줄 세우기) 순서로 실행합니다. 앱 사이에도 의존이 걸립니다. 예를 들어 `owner` FK가 있으면 `("auth", "0012_...")` 같은 다른 앱 파일을 dependencies에 넣습니다.

PostgreSQL에서는 마이그레이션 하나가 **트랜잭션 하나**로 묶여, 중간에 실패하면 통째로 되돌립니다. MySQL은 DDL(테이블 구조 변경)이 트랜잭션을 지원하지 않아 반쯤 적용된 상태가 남을 수 있습니다.

</details>

## 2. 데이터 마이그레이션: done → 체크인

모델을 바꾸는 마이그레이션은 **구조**(테이블·열)만 바꿉니다. 그런데 오늘은 **안의 데이터**를 옮겨야 합니다. "독서 Goal의 done=12"를 "체크인 amount=12 한 줄"로요. 이걸 **데이터 마이그레이션**이라고 합니다.

왜 그냥 `shell`에서 for문을 돌리면 안 될까요? 내 PC에서는 되지만, 운영 서버와 동료 PC에서는 **아무도 그걸 안 돌립니다**. 마이그레이션 파일로 만들면 `migrate` 한 번에 모든 환경에서 똑같이 실행됩니다.

순서는 세 단계입니다. 한 번에 하지 않는 게 핵심이에요.

```mermaid
flowchart LR
  A["① CheckIn 추가<br/>(Day 12 완료)"] --> B["② RunPython<br/>done → CheckIn"]
  B --> C["③ done 열 삭제"]
```

②번용 빈 마이그레이션 파일을 만듭니다.

```bash
python manage.py makemigrations goals \
  --empty -n move_done_to_checkins
```

**결과를 맞혀 보세요:** 아래 함수에서 `from goals.models import Goal`이 아니라 `apps.get_model(...)`을 씁니다. 왜일까요?

<details>
<summary>정답</summary>

③에서 `done`을 지우면 `models.py`의 Goal에는 `done`이 **없습니다**. 나중에 새 PC에서 처음부터 migrate하면 ②번이 지금 모델을 import해 `g.done`에서 터집니다. `apps.get_model`은 **그 시점의 과거 모델**을 줍니다. 그래서 언제 돌려도 안전합니다.

</details>

**Python (Django)** · `0005_move_done_to_checkins.py`

```python
def forwards(apps, schema_editor):
    Goal = apps.get_model("goals", "Goal")
    CheckIn = apps.get_model(
        "goals", "CheckIn")
    for g in Goal.objects.filter(done__gt=0):
        CheckIn.objects.create(
            goal=g, amount=g.done)
```

되돌리는 함수도 씁니다. `migrate goals 0004`로 뒤로 갈 때 실행됩니다.

```python
def backwards(apps, schema_editor):
    CheckIn = apps.get_model(
        "goals", "CheckIn")
    CheckIn.objects.all().delete()
```

```python
class Migration(migrations.Migration):
    dependencies = [
        ("goals", "0004_checkin")]
    operations = [
        migrations.RunPython(
            forwards, backwards)]
```

이제 `models.py`에서 `done = ...` 줄을 지우고 `makemigrations`를 하면 ③ `0006_remove_goal_done`이 생깁니다. `migrate` 한 번에 ②③이 순서대로 돕니다.

**JS (Node, Knex)** 로 하면 직접 SQL을 씁니다.

```javascript
exports.up = async (knex) => {
  const gs = await knex("goal")
    .where("done", ">", 0);
  for (const g of gs)
    await knex("checkin").insert(
      { goal_id: g.id, amount: g.done });
};
```

**비유:** 이사입니다. 새집(CheckIn)을 먼저 짓고, 짐을 옮기고, 그다음에 옛집(`done` 열)을 허뭅니다. 옛집부터 허물면 짐이 사라집니다.

같은 흐름을 순수 Python으로 흉내 내 보세요.

```python-run
goals = [{"id": 1, "done": 12},
         {"id": 2, "done": 0}]
checkins = []
for g in goals:
    if g["done"] > 0:
        checkins.append(
            {"goal_id": g["id"],
             "amount": g["done"]})
    del g["done"]
print(checkins, goals)
```

> 💡 구조 추가 → 데이터 옮기기(`RunPython`) → 옛 구조 삭제. 모델은 꼭 `apps.get_model`로.

<details>
<summary>🔍 더 깊이 (면접용): 대량 데이터·무중단 배포</summary>

Goal이 100만 개면 `create()`를 100만 번 부르는 것은 너무 느립니다. `bulk_create(objs, batch_size=1000)`로 묶어서 넣습니다. 더 크면 `RunSQL("INSERT INTO ... SELECT ...")`로 DB 안에서 한 번에 옮깁니다.

무중단 배포에서는 ②와 ③을 **다른 배포로 나눕니다.** 새 코드가 다 깔리기 전까지 옛 서버가 아직 `done`을 읽고 있을 수 있기 때문입니다. 순서는 "열 추가 → 코드가 양쪽에 쓰기 → 데이터 옮기기 → 코드가 새 열만 읽기 → 옛 열 삭제"입니다. 이것을 expand/contract(넓혔다가 좁히기) 패턴이라고 부릅니다.

`RunPython`에 `backwards`가 없으면 그 마이그레이션은 **되돌릴 수 없습니다.** 되돌릴 일이 없다면 `migrations.RunPython.noop`을 넣어 "되돌릴 땐 아무것도 안 함"을 명시합니다.

</details>

## 3. 충돌: 잎이 두 개일 때

혼자 할 땐 사슬이 한 줄입니다. 팀에서는 다릅니다. 나와 동료가 **같은 0004 뒤에** 각자 0005를 만들면, 사슬이 둘로 갈라집니다. 끝(잎)이 두 개가 되죠.

![마이그레이션 충돌과 merge](assets/gif/day13-merge.gif)

**결과를 맞혀 보세요:** git 충돌은 없었습니다(파일 이름이 달라서). 이 상태로 `migrate`하면?

<details>
<summary>정답</summary>

**멈춥니다.** git은 통과해도 Django는 "어느 쪽이 마지막인지" 모릅니다.

```text
CommandError: Conflicting migrations
detected; multiple leaf nodes in the
migration graph: (0005_checkin_note,
0005_goal_color in goals).
```

</details>

해결은 대부분 한 줄입니다.

```bash
python manage.py makemigrations --merge
# 0006_merge_... 생성
```

merge 파일은 할 일(`operations`)이 비어 있고, **두 0005를 모두** dependencies에 적습니다. 갈라진 두 길이 다시 하나로 모이는 것이죠.

```python
class Migration(migrations.Migration):
    dependencies = [
        ("goals", "0005_checkin_note"),
        ("goals", "0005_goal_color"),
    ]
    operations = []
```

**JS 비교:** Knex·Prisma는 날짜 순서로 그냥 다 실행합니다. 편하지만 두 파일이 **같은 열을 다르게** 바꿔도 조용히 넘어갑니다. Django는 일부러 멈춰서 "둘이 부딪히지 않는지 사람이 보라"고 합니다.

그래서 merge 전에 꼭 두 0005가 **같은 필드를 건드리는지** 확인하세요. 서로 다른 필드면 `--merge`로 끝납니다. 같은 필드면 한쪽 파일을 지우고(아직 운영에 적용 안 됐을 때만) 다시 `makemigrations`합니다.

잎(끝 노드) 찾기를 순수 Python으로 해 봅시다.

```python-run
deps = {"0004": ["0003"],
        "0005_a": ["0004"],
        "0005_b": ["0004"]}
used = {p for ps in deps.values()
        for p in ps}
leaves = [n for n in deps if n not in used]
print(leaves)
# 출력: ['0005_a', '0005_b']
```

> 💡 잎이 2개면 `migrate`가 멈춘다. 같은 필드를 안 건드리면 `makemigrations --merge`.

<details>
<summary>🔍 더 깊이 (면접용): --fake 와 squash</summary>

- `migrate --fake 앱 번호`: SQL은 실행하지 않고 `django_migrations` 표에 "적용됨"만 적습니다. 손으로 이미 테이블을 만든 경우처럼 **표와 실제 DB를 맞출 때만** 씁니다. 잘못 쓰면 표는 적용됐다는데 열은 없는 상태가 됩니다.
- `--fake-initial`: 첫 마이그레이션의 테이블이 이미 있으면 건너뜁니다. 기존 DB에 Django를 처음 붙일 때 씁니다.
- `squashmigrations goals 0001 0040`: 파일 40개를 하나로 압축합니다. 새 파일에 `replaces = [...]`가 적혀, 이미 적용된 DB와 새 DB 모두 맞게 동작합니다. 모든 환경이 새 파일로 넘어간 뒤 옛 파일을 지웁니다.

</details>

## 연습문제

### 문제 1. 제목 앞뒤 공백 정리

Goal 제목에 `"  독서 "`처럼 공백이 섞여 있습니다. 모든 제목을 `strip()`하는 데이터 마이그레이션의 `forwards`를 작성하세요.

<details>
<summary>정답 보기</summary>

```python
def forwards(apps, schema_editor):
    Goal = apps.get_model("goals", "Goal")
    for g in Goal.objects.all():
        new = g.title.strip()
        if new != g.title:
            g.title = new
            g.save(update_fields=["title"])
```

`apps.get_model`로 과거 모델을 받고, 바뀐 것만 저장합니다. `update_fields`는 UPDATE 문에 그 열만 넣어 빠르고 안전합니다. 되돌릴 수 없는 정리 작업이므로 `RunPython(forwards, migrations.RunPython.noop)`으로 등록합니다.

</details>

### 문제 2. 적용 순서 구하기

아래 `deps`에서 적용 순서를 리스트로 출력하세요. 앞 파일이 항상 먼저 와야 합니다.

```python-run
deps = {"0001": [],
        "0002": ["0001"],
        "0003_a": ["0002"],
        "0003_b": ["0002"],
        "0004_merge": ["0003_a", "0003_b"]}
# 여기에 작성
```

<details>
<summary>정답 보기</summary>

```python-run
deps = {"0001": [],
        "0002": ["0001"],
        "0003_a": ["0002"],
        "0003_b": ["0002"],
        "0004_merge": ["0003_a", "0003_b"]}
done = []
def visit(n):
    if n in done:
        return
    for p in deps[n]:
        visit(p)
    done.append(n)
for n in deps:
    visit(n)
print(done)
```

노드마다 **앞 파일을 먼저 방문**한 뒤 자신을 넣습니다. 이것이 위상 정렬(DFS 방식)이고, `migrate`가 하는 일과 같습니다. merge 노드는 두 0003이 모두 끝난 뒤에야 들어갑니다.

</details>

### 문제 3. 이 순서, 뭐가 문제?

한 마이그레이션 파일 안에서 `operations = [RemoveField("goal", "done"), RunPython(forwards)]` 순서로 썼습니다. 무엇이 잘못됐나요?

<details>
<summary>정답 보기</summary>

**열을 먼저 지우고 나서 데이터를 옮기려 합니다.** `RunPython`이 돌 때 과거 모델에는 이미 `done`이 없어서 `g.done`에서 에러가 나거나, 데이터가 사라집니다. 이사 전에 옛집을 허문 셈이죠. `RunPython`을 먼저, `RemoveField`를 나중에 두거나, 오늘처럼 **파일을 나눠** 0005(옮기기)·0006(삭제)으로 만듭니다.

</details>

## 면접 질문

<details>
<summary>Q1. 스키마 마이그레이션과 데이터 마이그레이션의 차이, 주의점은?</summary>

- **스키마 마이그레이션**: 테이블·열·인덱스 같은 구조를 바꿉니다. `makemigrations`가 모델 변경을 보고 자동 생성합니다.
- **데이터 마이그레이션**: 행의 값을 바꾸거나 옮깁니다. `--empty`로 빈 파일을 만들고 `RunPython`(또는 `RunSQL`)을 직접 씁니다.
- 주의점 1: 모델은 `apps.get_model`로 **과거 버전**을 써야 나중에 모델이 바뀌어도 깨지지 않습니다.
- 주의점 2: `backwards`를 써서 되돌릴 수 있게 하거나 `noop`으로 명시합니다.
- 주의점 3: 대량이면 `bulk_create`/`RunSQL`, 무중단이면 expand/contract로 배포를 나눕니다.

</details>

<details>
<summary>Q2. 팀에서 마이그레이션 충돌이 나면 어떻게 하나요?</summary>

- 원인: 같은 부모 뒤에 두 브랜치가 각자 마이그레이션을 만들어 **잎 노드가 2개**가 된 것. git 충돌이 없어도 `migrate`가 멈춥니다.
- 두 파일이 **다른 필드**를 건드리면 `makemigrations --merge`로 두 잎을 dependencies로 가진 빈 merge 파일을 만듭니다.
- **같은 필드**를 건드리고 아직 운영에 적용 전이면, 한쪽을 지우고 최신 main 위에서 다시 생성합니다. 이미 운영에 적용된 파일은 지우지 않습니다.
- 예방: PR 전에 main을 rebase하고, CI에서 `makemigrations --check`로 빠진 마이그레이션을 잡습니다.

</details>

## 오늘 정리

1. 마이그레이션은 `dependencies`로 앞 파일을 가리키는 그래프이고, 적용 기록은 `django_migrations` 표에 있다.
2. 데이터는 `RunPython`으로 옮기고, 모델은 `apps.get_model`, 순서는 추가 → 옮기기 → 삭제.
3. 잎이 2개면 충돌. 다른 필드면 `--merge`, 같은 필드면 다시 생성.
